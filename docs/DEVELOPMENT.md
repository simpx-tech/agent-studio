# Development and desktop builds

Use `development` for ongoing work. Merge tested changes from `development` into
`main` when publishing a release. Keep `main` as the stable/default branch, and
merge release fixes back into `development` before starting the next change.
Do not force-push either branch. The setup change is published to both branches
so the workflow is available immediately.

The [Desktop builds workflow](../.github/workflows/desktop-build.yml) only
packages releases: pushes to `main` and manual runs on `main` build and sign
every platform, then publish the release. It runs no tests, so the local
pipeline (frontend checks, unit tests, production build, browser tests, Rust
formatting, Clippy, and Rust tests) is the only verification before a release
is published; run it on the final commit candidate before every push. Pushes to
`development` start no hosted run.

The shell scripts under `src-tauri/src/*.sh` are compiled into the desktop
binary with `include_str!` and executed by bash inside WSL, so they must keep
LF line endings on every checkout. `.gitattributes` pins `*.sh` to `eol=lf`,
which overrides `core.autocrlf` on Windows build runners, and
`wsl::embedded_script` strips any remaining CRLF before a script reaches bash.
A Rust test fails if a checked-out script contains a carriage return; run
`git add --renormalize .` after updating an older Windows checkout.
On a cold machine, compile the Rust tests first (`--no-run`) and run them with
`--test-threads=1`: their fixtures start PowerShell with bounded waits, and cold
startup or competing child processes can otherwise consume protocol assertion
deadlines.
With `CI` set, as in the VPS updater's sandboxed release build, unit tests use
one worker and 15-second budgets, and browser tests use one worker against the
production preview generated by `npm run verify` with 60-second budgets and
without long-task timing budgets. Local runs keep the development server, four
browser workers, and 5- and 30-second budgets. Assertions remain unchanged, and
browser tests have no automatic retries.

Every push to `main`, including a merge, builds these downloadable artifacts:

| Platform | Architecture | Packages |
| --- | --- | --- |
| Windows | x64 | NSIS `.exe` and `.msi` installers |
| Linux | x64 | `.deb` and `.AppImage` |
| macOS | Universal, Intel and Apple Silicon | `.dmg` and the `.app.tar.gz` update archive |

NSIS, MSI, AppImage, and macOS update packages include `.sig` updater signatures.

Open **Actions → Desktop builds → the completed run → Artifacts** to download
them. Artifact names include the complete commit SHA and are retained for 30
days. Platform builds run in parallel, and any failed build fails the workflow.
Use installers from successful runs; a failed platform build does not cancel the
others. **Run workflow** on `main` rebuilds it manually; on other branches it
builds nothing.

The workflow uses Node 24, Rust stable, the npm/Cargo lockfiles, and pinned action
revisions. Builds need the `TAURI_SIGNING_PRIVATE_KEY` and
`TAURI_SIGNING_PRIVATE_KEY_PASSWORD` repository secrets to sign update packages;
the build job fails with an explanation without them. Windows packages are not
Authenticode-signed; macOS packages use ad-hoc signing and are not Apple
notarized. Trusted publisher
signing requires a separate certificate setup. Building an installer does not
verify provider sign-in or desktop runtime behavior on that platform.

After every platform build succeeds on `main`, the **Publish release** job
verifies each updater signature and its signed version, then
creates the GitHub Release `v<version>` with the installers, signatures, and the
updater's `latest.json`. Installed apps update from it. A version that already
has a release is never replaced: the job only warns. Bump the version on
`development` with `npm run release:version -- patch` (or `minor`, `major`, or
`x.y.z`) before merging a release. The bump adds the version's `CHANGELOG.md`
section from the commits since the previous release; edit it before committing,
because it becomes the release notes and the changelog in Settings → About. See
[automatic updates](UPDATES.md) for the signing key, local `--no-sign` builds,
and the release format.

The production VPS then installs the release by itself, usually within fifteen
minutes, and replaces its public Windows download. It authenticates the release
by its signed installer, builds and tests it in a sandbox, and rolls back on a
failed health check while preserving private workspaces, pairing keys, and
browser sessions. See [automatic updates](DEPLOYMENT.md#automatic-updates).

Before pushing changes, run the full local verification in `CLAUDE.md`; no
hosted job repeats it. Native packaging for other operating systems is verified
on its corresponding hosted runner. Do not treat an unrun or failed job as a
successful build.
