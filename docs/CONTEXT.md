# Model context

Choose an Agent and Model in the chat toolbar, then open **Model context** using the book icon. The inspector lists instructions, skills, memories, MCP servers, and hooks for that connection and folder. File rows show a path, scope, and discovery status; MCP rows show the server name, scope, and reported status. Filter the list or copy a file path; Refresh repeats the inspection. Conversation instructions are displayed separately.

**Hooks** lists events, handler types, source paths, matchers and available configuration metadata. Codex uses optional `hooks/list` for the selected working directory; disabled hooks and hooks requiring trust review remain distinct. An unsupported or failed catalog query means availability is unknown. Claude discovers hooks in the selected profile's settings, project settings/local settings, and enabled installed plugins, including inline plugin definitions and contained hook files. These are discovery candidates: managed policy, runtime configuration and trust can change availability. Inspection never runs hooks, and a configured hook is not evidence that it executed. Commands, HTTP/MCP targets, prompt bodies, hashes, output and raw errors are excluded. Gemini hook discovery is unavailable.

Actual Claude `hook_started` / `hook_progress` / `hook_response` events and Codex `hook/started` / `hook/completed` notifications appear in the reply's Work history. Claude chat requests `--include-hook-events`; background context/title queries remain restricted. Codex `hookPrompt` items record that hook context was supplied, with fragment counts and hook-run references but no injected text. Activity preserves child ownership, identity/revision updates, stopped/failed/blocked outcomes, and missing completion as unconfirmed through saving, exports and relay checkpoints. It is excluded from prompt replay. Startup notifications are held until the Codex thread binding is verified; stale parent-turn notifications are rejected. Some provider hooks do not emit a full lifecycle, and asynchronous events arriving after a reply ends may not be recorded. See the [Claude CLI reference](https://code.claude.com/docs/en/cli-reference) and [Codex app-server API](https://learn.chatgpt.com/docs/app-server).

**Memories** includes global entrypoints and sources associated with the current project or folder. Codex lists `memory_summary.md`, `MEMORY.md`, and existing registry references whose `cwd` belongs to the current repository (or selected folder outside Git). It does not recursively list other projects, raw memory archives, or internal extension files. These project references are candidates for task-specific lookup, not a claim they all load at startup. Claude's successful context report selects the effective memory directory, replacing filesystem guesses; its topic files remain available on demand. A configured custom directory replaces the default directory, and disabled auto memory is respected.

**MCPs** distinguishes configured, connected, disabled, connecting, failed, and sign-in-required servers. Codex uses the selected-folder app-server's effective configuration and paginated MCP status API, including reported plugin servers. Claude uses its native MCP status query. Configured does not prove a server is connected; missing status support or an incomplete query is explained in the notes. Opening or refreshing the inspector requests no model response, invokes no MCP tools, and starts no sign-in flow. Server commands, arguments, URLs, environment variables, credentials, tool schemas, and raw errors are not returned by inspection. Gemini MCP management is unavailable.

The MCPs tab also offers explicit management actions for the selected account and execution computer:

- **Add server** saves an HTTP or stdio server through the selected CLI's `mcp add`; Claude also supports SSE and writes to its user scope. Enter command arguments as a JSON array, never a shell command string. Existing server names are rejected. Only add trusted servers: a stdio command executes on the selected computer. Credential/header/environment editing is outside this form.
- **Sign in** starts Claude `mcp_authenticate` or Codex `mcpServer/oauth/login`. **Open sign-in** opens the returned authorization URL. Starting the flow does not mean sign-in succeeded. Codex waits for the matching server and native thread's `mcpServer/oauthLogin/completed`; Claude verifies the transition to connected through `mcp_status`. Already-connected Claude servers must be signed out before changing their login. Credentials remain in the CLI's own storage.
- For Claude, a failed remote browser redirect can be pasted into the temporary password-style callback field; the CLI validates OAuth state and exchanges the code. **Sign in on computer** is the explicit `claude mcp login` fallback for Windows Desktop and opens that computer's browser. Codex's callback must reach the execution computer; use a browser there when controlling a remote host.
- **Cancel sign-in**, closing the MCP panel, changing selection, renderer reload, app close, and a five-minute expiry release the owned OAuth process. Cancelling a flow using a parked chat process ends that process; its native conversation resumes on the next reply. Sign-out asks for confirmation before `mcp logout` clears the selected profile's server credentials. Saved changes cause this chat's parked process to restart on its next reply; other chats sharing that CLI profile may need to reconnect.
- Claude **Reconnect**, **Enable/Disable**, and **Live session servers** operate on an idle, still-live chat process using `mcp_reconnect`, `mcp_toggle`, and `mcp_set_servers`. Session server definitions replace the additional session servers, retain Agent Studio's SDK integration, and are not persisted by the app. These controls require a prior reply and are unavailable after the process expires. **Refresh server status** reads that live process when available.
- Codex **Reload configuration** sends `config/mcpServer/reload`. Loaded threads apply the queued refresh on their next turn. Startup notifications retain only bounded server names and status; expired authentication is shown as sign-in required. An acknowledgement is not presented as a successful connection.

Management uses the normal authenticated transport for Desktop, managed WSL, and remote/PWA controllers. Native session locks prevent concurrent replies or control operations on the same bound chat. Unsupported CLI requests fail visibly; there is no fallback to another account or computer. Authorization URLs, callback codes, operation handles, and entered configuration are transient application data, excluded from saved chats, context caches, prompt replay, exports, and logs. Relay requests/results live only in its authenticated in-memory job store and expire; they are never workspace data. Real Windows CLI checks cover local synthetic OAuth; physical remote callback routing and WSL/browser launch behavior require separate checks.

Protocol references: [Codex app-server MCP APIs](https://learn.chatgpt.com/docs/app-server) and [Claude MCP configuration and authentication](https://code.claude.com/docs/en/mcp). Installed CLI compatibility was checked with Codex 0.153.4 and Claude 2.1.277.

In Skills, **Use in next message** adds a skill request to the existing draft without sending it. Disabled skills cannot be selected, and Gemini has no invocation action. Codex's **Enable/Disable** controls persist the selected skill's setting through `skills/config/write`; the host verifies that exact path against a fresh CLI inventory for the selected folder. Actual skill invocations and observed skill-file reads appear in the reply's [tool activity](CAPABILITIES.md); inventory entries do not claim a skill was used.

Typing `/` in the composer also uses this selection's inventory/cache to offer [commands and skills](CAPABILITIES.md#slash-commands-and-skills). Claude initialization contributes bounded command names, descriptions, and argument hints, without account information or command bodies. Codex uses only enabled CLI-reported skills. The catalog remains session metadata; only an explicitly submitted Codex skill's name and path are saved on its user message.

After the first inspection, reopening shows the latest cached result immediately with an **Updating…** indicator while refreshing. A failed refresh keeps that result and its original check time visible. Reopening during an existing refresh shares the same request. The cache holds up to 32 recently viewed selections for the current app session, separated by provider, model, connection, computer, environment, folder, and conversation; restarting the app clears it.

The inspector keeps the same height while loading, refreshing, or showing errors. Its height is capped by the available viewport, with no scrollbar on the outer frame. The source list fills and scrolls within the remaining space. On narrow or short screens, the body uses one scroll area so all context details remain reachable. The header and Done footer stay in place.

Context sources belong to the CLI profile and project, so models using the same account and folder generally share sources. A fresh inspection uses the selected model. Historical replies retain their captured model settings, but the inspector is not a record of every file they read. File contents are not exported by the inspector, and inventories are not saved in conversation history.

## Plugins and temporary sources

The **Plugins** tab lists installed plugins from the selected Claude or Codex profile. **Install plugin** accepts a known identifier from an already-configured source (`plugin@source`). Claude installs into that profile's user scope; changes to existing Claude plugins preserve their reported scope. Multiple installations of the same Claude identifier in different scopes require CLI management. **Details** exposes bounded component metadata, **Enable/Disable** changes plugin configuration, and **Uninstall** requires confirmation. Marketplace browsing, source administration, sharing, publishing and remote skill-body reads are not implemented.

All actions route through `transport.ts` to the owning desktop host, including Viewer and managed WSL selections. Arguments remain separate CLI arguments or typed app-server requests. Claude uses `plugin list/install/enable/disable/details/uninstall`; Codex uses `plugin/installed`, `plugin/list/read/install/uninstall`, and a single escaped `plugins.<id>.enabled` configuration write. Unsupported CLI operations, policy restrictions and incomplete inventories produce an explicit error. Command-source Claude installs requiring command review and Codex installation interstitials remain in the CLI's consent flow. Raw diagnostics, manifests, configuration bodies and evaluation prompts are never returned to the UI or saved in conversation history.

**Temporary sources for this conversation** accepts at most eight of each source type: Claude plugin directories/zip files, public HTTPS zip URLs without embedded credentials or query parameters, or Codex additional skill roots. These use `--plugin-dir`, `--plugin-url`, and `skills/extraRoots/set` respectively. Paths refer to the selected execution computer. Sources are held in host memory for the conversation and account, survive closing the dialog, and clear when that host app restarts. They are neither workspace settings nor portable fork data. A saved conversation is required. Inspection uses the same temporary sources; Claude zip/URL component locations remain CLI-owned, with commands reported when available.

Mutations acquire the selected conversation's native lock. They invalidate frontend inventories and the selected profile's parked-process reuse revision, including after an uncertain write failure. The next reply resumes the native session in a fresh process; an already-running reply is not interrupted. Other accounts keep their own settings. `skills/changed` notifications during Codex replies invalidate the source and composer catalogs without entering saved messages. Inventories refresh on opening; they remain separate even for conversations in the same project because temporary sources can differ.

Claude **Evaluate** requires explicit trust confirmation and a finite USD budget (0.01–100). It runs one case repetition at a time, disables report publishing and scaffold scripts, and grants no real MCP servers or gated tools. The CLI's budget is checked between runs and can be exceeded by the single run already in flight. The app returns only a completion/failure/budget outcome; Claude retains its local report in the selected working folder. Cancellation, dialog closure, renderer reload and app closure cancel owned evaluation work. A ten-minute bound releases an abandoned evaluation. A failed cancellation request remains visible; connectivity loss does not prove the host stopped. Evaluation does not start a chat reply or reuse its native process.

Verification: `tests/plugins.spec.ts` covers plugin controls, confirmation, draft preservation, skill refresh and narrow layouts. Rust's opt-in `plugins::tests::real_installed_cli_plugin_lifecycle` exercises both installed CLIs against disposable profiles and a local fixture marketplace, including real install/read/toggle/remove and Codex extra-root skill toggles, without paid prompts. `scripts/plugins-native-smoke.mjs` uses `scripts/native-plugins.tauri.json` (frontend 1447, CDP 9537) to verify native IPC, profile isolation, invalid requests, skill writes, temporary-root isolation and rendered UI. Use the guarded Windows launcher for its compiled binary. Paid evaluation, external URL downloads and physical remote/WSL execution are separate validation boundaries.

## Sources and evidence

- **Codex:** discovers global and project `AGENTS.override.md` / `AGENTS.md`, configured global fallback filenames, companion `CLAUDE` guidance, local skills, and scoped memory metadata. Skills reported by `skills/list` replace filesystem candidates and preserve disabled entries. Instructions and memories remain discovery evidence; custom configuration layers, trust, imports, and size limits can affect loading. MCP metadata comes from `config/read` and `mcpServerStatus/list`. See [Codex instruction discovery](https://learn.chatgpt.com/docs/agent-configuration/agents-md), [skill discovery](https://learn.chatgpt.com/docs/build-skills), and [app-server APIs](https://learn.chatgpt.com/docs/app-server).
- **Claude:** discovers user/project `CLAUDE.md`, `CLAUDE.local.md`, rules, skills, legacy commands, skills from enabled installed plugins, and the selected project's memory directory. A fresh `get_context_usage` query adds reported loaded instruction paths and imports. The query disables hooks and tool execution while allowing configured MCP discovery, and requests no model response; it does not reproduce hook-injected content. Managed configuration and conditional skill availability are not fully resolved by filesystem discovery. See [Claude memory and instructions](https://code.claude.com/docs/en/memory) and [skills](https://code.claude.com/docs/en/skills).
- **Gemini / Antigravity:** lists known global and project guidance and skill locations as candidates. Actual loading and memory availability are unknown. Chats enable the CLI's configured tools with full access and no approval prompts. See [Antigravity context paths](https://www.antigravity.google/docs/cli/gcli-migration/) and [CLI skills](https://www.antigravity.google/docs/cli/plugins/).

Discovery is bounded to 600 entries and 6,000 filesystem visits with cycle detection; reaching a limit is visible. An unavailable CLI or folder produces an error, and a failed provider metadata query retains discovered entries with an explicit caveat. The source computer performs relay inspections. No credential files or other projects' Claude transcripts/memory folders are inventoried.

## Native verification

`scripts/context-native-smoke.mjs` uses a separate `com.vinicius.agentstudio.context-qa` installation and WebView CDP port 9447. Build with `scripts/native-context.tauri.json` and an isolated Cargo target, then launch with a separate WebView user-data folder. The script verifies live metadata queries across Claude and Codex models, Antigravity discovery, profile isolation, invalid selections, and the actual rendered inspector. It requests no generated model replies. Evidence goes under `artifacts/context-native*`.

Context inspection follows the selected computer's CLI and profile. A Desktop connection can inspect a WSL folder through its translated Windows/UNC path; a WSL connection requires that distribution's Linux CLI. The cache includes both execution and folder environments. The earlier `scripts/context-wsl-native-smoke.mjs` fixture predates this policy; current computer selection and missing-CLI checks use `scripts/wsl-computers-native-smoke.mjs`.
