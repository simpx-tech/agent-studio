# Screens

A screen is a lasting page a chat builds for you in Agent Studio: a dashboard, a tracker, a report you revisit or a small tool, with its own interface, the commands it runs and the MCP tools it calls on the computer that keeps it, on Windows and in that computer's WSL distributions alike. Ask a Claude or Codex chat for one ("make a page of the pull requests I opened this week"), and it saves the screen with its `save_screen` tool. The reply shows a card that opens it, and the **Screens** tab of the sidebar lists every screen by computer, beside Active and History. `/screens` opens that tab.

Nothing asks for permission (requested 2026-10-30: "forget permissions, it can do anything"): a page runs its actions, commands and tools as soon as it asks. Screens saved while approvals existed keep their files; the approval in them is ignored and dropped by the next save.

## How a chat builds one

Claude and Codex chats of a saved conversation get five Agent Studio tools, Claude through the `agent_studio` SDK server (`mcp__agent_studio__save_screen`, `…list_screens`, `…read_screen`, `…list_mcp_tools`, `…call_mcp_tool`) and Codex as dynamic tools of the same names (`src-tauri/src/screens/tools.rs`):

- `save_screen` takes a `title`, an optional one-line `description`, the page's `html`, its `actions` and its `mcpTools`, of any size or number, and returns the screen's id. Passing that `id` again replaces the screen with the complete new version, and a page already open loads it. Only the conversation's own call reaches it: Claude's registered parent tool use, Codex's parent thread without a namespace; sub-agents' calls are refused.
- `list_screens` names the screens this computer keeps, their folders, actions and MCP tools with the account that calls those first, how many of their jobs run and whether this conversation can update each one.
- `read_screen` returns one screen whole, with the values its page saved and its jobs, so a later chat can change it.
- `list_mcp_tools` and `call_mcp_tool` reach the MCP servers of any place of this computer as a screen's page reaches them (below), so a chat on Windows sees and tries the servers signed in inside WSL, such as Linear, before a screen calls them. Codex reports each tool's description and input schema; Claude Code reports tool names, and a call's error names the arguments a tool expects.

The prompt mentions the tools only briefly; the `save_screen` description holds the page API below. A Codex thread keeps the dynamic tools it started with, so chats begun before a tool existed reach it only in Claude (whose tool list is read when its process starts) or in a new Codex chat.

A saved screen belongs to the computer whose CLI ran the reply, and its actions run in that conversation's working folder: the project folder, or the Standalone chat's own folder. Both are recorded on that computer when the screen is created, never taken from a request, and an update keeps them; a screen made in a WSL distribution is updated from a chat there. The account the conversation replied with is recorded the same way, as the one that calls the screen's MCP tools first where the screen runs and that answers its page's questions to a model; an update from another chat keeps it while that account stays connected there.

## The page

The page runs in the sandbox that shows artifacts and visualizations (`src/lib/artifact-preview.html`, served as `studio-artifact` on desktop and `/artifact-preview` by the relay): an opaque origin with `sandbox allow-scripts` and a CSP that blocks every network request, remote script, style, font and frame. Its document starts with the app's theme variables (`--foreground`, `--heading`, `--muted-foreground`, `--card`, `--border`, `--primary`, `--viz-series-1…6`, in the resolved light or dark theme), gentle defaults the page may override, and the bridge, then the page itself, a fragment or a whole document (`screenDocument` in `src/lib/screens.ts`). It fills the main area and scrolls by itself. A theme change reaches the open page as a `studio-theme` event on `window`, with the variables replaced, without loading the page again.

The page reaches Agent Studio only through the global `studio` object:

- `studio.run(name, params, {onOutput, signal})` runs one of its actions as a job and resolves to `{exitCode, stdout, stderr, timedOut, stopped, durationMs, job}`; `onOutput(text, stream)` receives its output as it arrives, and aborting `signal` stops it. It rejects only when the action cannot run at all, such as an unknown action or a folder that is gone.
- `studio.json(name, params, options)` runs an action and parses its stdout, rejecting with its stderr when it does not end with exit code 0.
- `studio.exec(script, {shell, where, params, timeout, onOutput, signal})` runs a script the page writes, as an action runs, and resolves like `run`. Without `shell` it runs in PowerShell on Windows and in bash elsewhere and in WSL.
- `studio.start(name, params)`, or `studio.start({script, shell, where, params, timeout})`, starts a job that is kept: it goes on while no page shows it and stays, with its output, until a page forgets it. It resolves to the job at once.
- `studio.jobs()` lists the screen's jobs, the newest first; `studio.follow(id, {onOutput})` replays a job's output from its start, follows it as it arrives and resolves like `run` once it ended; `studio.stop(id)` stops a running job with everything it started; `studio.forget(id)` removes one.
- `studio.mcp(server, tool, args, {where, account})` calls any MCP tool of the servers an account has where it is called and resolves to `{content, structuredContent, text, account}`: the tool's content blocks as its server returned them, its structured result when it has one, its text blocks joined and the account that answered. It rejects with the tool's own error, or when no account there has the server connected.
- `studio.mcpJson(server, tool, args, options)` calls a tool and returns its structured result, or else its text parsed as JSON; `studio.mcpServers({where, account})` lists the servers an account has there.
- `studio.ask(prompt, {model, system, json})` asks a model as the screen's account, in the restricted background runtime titles use (no tools, no conversation, the provider's small model unless the page names one), and resolves to its answer, parsed as JSON with `json: true`.
- `studio.load(key)` and `studio.save(key, value)` keep JSON values of any size for this screen on its computer; saving `null` removes a value. `studio.values` holds every value saved when the page opened, so a page restores its state before its first paint.
- `studio.copy(text)` puts text on the clipboard; `studio.open(url)` opens an http or https link in the browser.
- `studio.chat(text, {send})` opens a new conversation in the screen's folder with the text as its draft, and sends it with `send: true`. It works while the screen is shown, never from a screen another view covers.
- `studio.theme` is `dark` or `light`, and `studio.screen` holds its id and title.

The window that shows the page checks every message (`screenCall`): it must come from that frame, carry the frame's token and be a known call with valid values of any size. A frame may wait for any number of answers at once. A reloaded or closed frame is never answered.

## A page keeps its context

A screen keeps what it showed when you leave it (requested 2026-10-30, after a build screen lost its build output when another screen was opened):

- Every screen a window opens stays open in that window, mounted out of sight while a chat, another screen, Connections or Settings shows (`keptScreens` in `+page.svelte`), so its page keeps its state, its pending calls and the output it is following. Reload, deleting the screen or a change of workspace ends it; a new revision a chat saves loads in its place.
- Every action or command a page runs is a job on the computer that keeps the screen (`src-tauri/src/screens/jobs.rs`): its output is written as it arrives to app data `screens/jobs/<screen>/<job>.log`, with its record beside it, and it goes on whether or not a page follows it. A job `studio.run` or `studio.exec` started goes once a page received its end; one whose page closed first stays until a page follows it to its end or forgets it. A job `studio.start` started stays until forgotten. A page that opens again, in this window after a reload, after the app restarted or on another device, finds them with `studio.jobs()` and follows them.
- Quitting the app stops the jobs still running, which keep what they printed and read as stopped; a job the app could not see end reads as interrupted. Restart to update waits for running jobs as it waits for replies.
- The toolbar's Jobs button, a spinner while jobs run, opens the screen's jobs whatever its page shows: each with its state, time and output, followed while it runs, with Stop and Remove (`ScreenJobs.svelte`). The Screens tab marks a screen whose jobs run.

## Actions, commands and places

Each action declares `name`, `description`, `shell`, `script`, `params`, an optional `timeout` and an optional `where`:

- `shell` is `powershell` (Windows: PowerShell 7 when it is on PATH, otherwise Windows PowerShell 5.1) or `bash` (Git Bash on Windows, bash in WSL, Linux and macOS). The chat hears at once when the place an action runs in has no such shell.
- `params` maps each name to `{type: string | number | integer | boolean, description, enum, pattern, maxLength, minimum, maximum, optional}`; the computer refuses values that do not fit before anything runs. A value the action does not declare passes as it is, as JSON when it is not text. Each value reaches the script only as the environment variable `PARAM_<NAME>` (`since` is `PARAM_SINCE`), never as script text.
- `timeout` is a whole number of seconds, at least 1, with no upper bound; an action without one runs until it ends.
- `where` names another place of the same computer to run in (`src-tauri/src/screens/places.rs`): `windows`, the Windows computer itself; `wsl`, the screen's own distribution or else the first one this computer manages; or a WSL distribution by its name. The command starts in the screen's folder as that place reaches it (`C:\work` is `/mnt/c/work` in WSL, a WSL folder is `\\wsl.localhost\<distribution>\…` on Windows), or in that distribution's home folder when it cannot. Without `where` it runs where the screen does.

The computer runs a command (`src-tauri/src/screens/run.rs`) in its folder with stdin closed, without the variables of an agent session, and with `NO_COLOR=1`:

- PowerShell receives a constant command (`-NoProfile -NonInteractive -ExecutionPolicy Bypass -Command`) that sets UTF-8 output, adds the user's current PATH from the registry, reads the script from a private file named by an environment variable and deletes it, and runs it as a function named after the action (`command` for a page's own), so its errors name it and their lines. It ends with the script's `exit` or the exit code of the last program it ran. (`-EncodedCommand` would make Windows PowerShell write its errors as CLIXML.)
- bash starts as a login shell, as agents run commands, returns to the folder after the profile and runs the script from its file.
- In WSL, `wsl.exe` runs the fixed `screen-run.sh`, which reads the folder (empty for the home folder), the script, the time limit (0 for none) and each value as lines of base64 on stdin, never on a command line, exports the values, and runs the script with `setsid` under a job marker `wsl-cancel.sh` can stop; when the command has a time limit, a watchdog there ends it at that limit even if Windows lost the run.

Output is read as it arrives and kept whole. A command past its time limit, or stopped, ends with everything it started, and keeps what it printed. Commands run side by side, as many at once as a computer's screens ask for.

## How MCP calls run

The computer calls a tool (`src-tauri/src/screens/mcp.rs`) through the CLI of an account in the place the call names, or where the screen runs, started under that account's profile in the screen's folder as that place reaches it, with the MCP servers a chat of that account loads there: the profile's own, the definitions it shares from another account or the computer's CLI context (`--mcp-config` for Claude, `-c` overrides for Codex), and shared plugin servers. No model takes part, and Agent Studio reads no MCP credential or configuration body: the CLI connects the servers, keeps their sign-ins and makes the call.

The account comes from the place (`candidates` in `places.rs`): one the page or the tool's declaration names, by the name Connections gives it; where the screen runs, the screen's account, then that place's CLI login; elsewhere, that place's CLI login first, whose terminal holds the sign-ins its servers have, then the same account's separate profile there; then every other Claude or Codex account there, the screen's agent first. A call goes on to the next account while one has no such server connected, must sign in to it or does not start, and the account that answered is remembered for that screen, place and server, so one screen never calls as the account another screen found; a tool's own error is its answer. When none can call it, the error names each account and why.

- Claude Code runs in stream-json mode with no tools, hooks or session file, and answers its `mcp_call` control request for `mcp__<server>__<tool>` (the server named as Claude Code names it, so `claude.ai Linear` and `claude_ai_Linear` reach the same connector) and its `mcp_status` for listings, which wait while a server still connects. The request carries `result_not_for_model`, so a large result comes whole instead of being shortened for a model. Agent Studio refuses a form a server asks for.
- Codex runs its app-server with an ephemeral thread (`approvalPolicy: never`, which declines a server's forms) and answers `mcpServer/tool/call` and `mcpServerStatus/list` on that thread. A server named as an agent saw it (`dash_name` for `dash-name`) is found by its configured name once, and a tool's `isError` result rejects with the tool's text. A separate WSL profile signs in with its Windows login first, as its chats do.

Each screen keeps one CLI for each account and place it calls through (the chats' `call_mcp_tool` share theirs), side by side as many at once as it asks, and ends it five minutes after its last call ends, when a chat saves the screen again, when you delete it, when a call finds its server not connected, signed out or not started (so the next call starts a CLI that reads them again), and when the app quits. A call itself waits as long as its tool takes.

## Where screens live

A screen lives on the computer that runs its commands, under app data `screens/` (`<id>.json`, `<id>.data.json` for saved values and `jobs/<id>/` for its jobs), written atomically. Like tool results, it is never part of the workspace, exports, relay sync or prompts. A reply keeps only the card of each screen it saved (`screens` on the message: id, revision, title, environment), which syncs, exports and merges with the conversation like its other metadata.

Windows reach screens through transport (`listScreens`, `readScreen`, `runScreenAction`, `startScreenJob`, `screenJobs`, `screenJobOutput`, `stopScreenJob`, `forgetScreenJob`, `callScreenTool`, `screenMcpServers`, `askScreenModel`, `deleteScreen`, `loadScreenData`, `saveScreenData` in `src/lib/transport.ts`), routed by environment to the computer that keeps them: the desktop's own through `manage_screen`, others' and the Viewer's through the relay's `screens` job, whose request the relay validates strictly (`screenRequestSchema`) and whose large results leave once read. A page follows a job by asking for its output from where it stopped, each request waiting up to 25 seconds for more, on this computer and through the relay alike. Starting a job, calling a tool or asking a model runs once however many copies of its call the window sends. The Screens tab asks each reachable computer for its list when it opens and a computer's list again when a reply there saves a screen; an offline computer's screens stay listed as last read, and its screen opens again once it connects. Deleting a screen asks first and removes its page, values and jobs from its computer; chats keep their cards. Windows of earlier releases still send approvals, which the computer answers with the screen.

Remote screens need a relay that knows the `screens` job's requests; jobs, places and the other requests added on 2026-10-30 reach another computer once the VPS runs the release that brings them.

A PowerShell action's five lines reached their reader in ten answers as it printed them, with exit code 3, and a stop ended a two-minute job in 135 ms. A screen's page stayed loaded while Settings showed and loaded again on Reload, following its job's five lines each time.
