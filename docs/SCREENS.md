# Screens

A screen is a lasting page a chat builds for you in Agent Studio: a dashboard, a tracker, a report you revisit or a small tool, with its own interface, the commands it may run on the computer that keeps it and the MCP tools it may call there. Ask a Claude or Codex chat for one ("make a page of the pull requests I opened this week"), and it saves the screen with its `save_screen` tool. The reply shows a card that opens it, and the **Screens** tab of the sidebar lists every screen by computer, beside Active and History. `/screens` opens that tab.

## How a chat builds one

Claude and Codex chats of a saved conversation get three Agent Studio tools, Claude through the `agent_studio` SDK server (`mcp__agent_studio__save_screen`, `…list_screens`, `…read_screen`) and Codex as dynamic tools of the same names (`src-tauri/src/screens/tools.rs`):

- `save_screen` takes a `title`, an optional one-line `description`, the page's `html`, its `actions` and its `mcpTools`, of any size or number, and returns the screen's id. Passing that `id` again replaces the screen with the complete new version. Only the conversation's own call reaches it: Claude's registered parent tool use, Codex's parent thread without a namespace; sub-agents' calls are refused.
- `list_screens` names the screens this computer keeps, their folders, actions and MCP tools with the account that calls those, whether you allowed them and whether this conversation can update each one.
- `read_screen` returns one screen whole, with the values its page saved, so a later chat can change it.

The prompt mentions the tools only briefly; the `save_screen` description holds the page API below. A Codex thread keeps the dynamic tools it started with, so chats begun before this feature reach screens only in Claude (whose tool list is read when its process starts) or in a new Codex chat.

A saved screen belongs to the computer whose CLI ran the reply, and its actions run in that conversation's working folder: the project folder, or the Standalone chat's own folder. Both are recorded on that computer when the screen is created, never taken from a request, and an update keeps them. A screen of a WSL distribution runs its actions in that distribution and can be updated only from a chat there. The account the conversation replied with is recorded the same way, as the one that calls the screen's MCP tools (below); an update from another chat keeps it while that account stays connected where the screen runs, and a screen saved before MCP tools takes the account of the next chat that saves it.

## The page

The page runs in the sandbox that shows artifacts and visualizations (`src/lib/artifact-preview.html`, served as `studio-artifact` on desktop and `/artifact-preview` by the relay): an opaque origin with `sandbox allow-scripts` and a CSP that blocks every network request, remote script, style, font and frame. Its document starts with the app's theme variables (`--foreground`, `--heading`, `--muted-foreground`, `--card`, `--border`, `--primary`, `--viz-series-1…6`, in the resolved light or dark theme), gentle defaults the page may override, and the bridge, then the page itself, a fragment or a whole document (`screenDocument` in `src/lib/screens.ts`). It fills the main area and scrolls by itself.

The page reaches Agent Studio only through the global `studio` object:

- `studio.run(name, params)` runs one of its actions and resolves to `{exitCode, stdout, stderr, truncated, timedOut, durationMs}`. It rejects when the action cannot run, such as before you allowed the screen's actions.
- `studio.json(name, params)` runs an action and parses its stdout, rejecting with its stderr when the exit code is not 0 or it stopped at its time limit.
- `studio.mcp(server, tool, args)` calls one of the MCP tools the screen declares and resolves to `{content, structuredContent, text}`: the tool's content blocks as its server returned them, its structured result when it has one, and its text blocks joined. It rejects with the tool's own error, or when the tool cannot be called, such as before you allowed it or while its server needs sign-in.
- `studio.mcpJson(server, tool, args)` calls a tool and returns its structured result, or else its text parsed as JSON.
- `studio.load(key)` and `studio.save(key, value)` keep JSON values of any size for this screen on its computer; saving `null` removes a value.
- `studio.chat(text)` opens a new conversation in the screen's folder with the text as its draft, which you send yourself. It works only while the screen's frame has focus, right after you clicked or typed in it, so a page cannot open chats by itself.
- `studio.theme` is `dark` or `light`, and `studio.screen` holds its id and title.

The window that shows the page checks every message (`screenCall`): it must come from that frame, carry the frame's token and be a known call with valid values of any size (an action name, a plain object of parameters, a server's and a tool's name on one line, a plain object of arguments, a key without control characters, a JSON value, a chat's text). A frame may wait for any number of answers at once. A reloaded or closed frame is never answered.

## Actions, MCP tools and their approval

Each action declares `name`, `description`, `shell`, `script`, `params` and an optional `timeout`:

- `shell` is `powershell` (Windows: PowerShell 7 when it is on PATH, otherwise Windows PowerShell 5.1) or `bash` (Git Bash on Windows, bash in WSL, Linux and macOS). The chat hears at once when its computer has no such shell.
- `params` maps each name to `{type: string | number | integer | boolean, description, enum, pattern, maxLength, minimum, maximum, optional}`. The computer refuses values that do not fit before anything runs. Each value reaches the script only as the environment variable `PARAM_<NAME>` (`since` is `PARAM_SINCE`), never as script text.
- `timeout` is a whole number of seconds, at least 1, with no upper bound; an action without one runs until it ends.

Each MCP tool (requested 2026-10-18) declares `server`, `tool` and an optional `description`, named as the chat's own tool list names them: `mcp__linear__list_issues` is `{"server": "linear", "tool": "list_issues"}`. Names are one line as written, without control or hidden characters; `agent_studio`, Agent Studio's own server, works only inside a chat.

Nothing runs until you allow exactly the actions and MCP tools a screen declares now. The screen shows a request until then, and **Review actions** lists each action's shell, any time limit, parameters and complete script, with the computer and folder they run in, and each MCP tool with its server and the account that calls it. Allowing records a SHA-256 digest of the actions and where they run on that computer, and of the MCP tools with their account (`screens/<id>.json`); a screen without MCP tools keeps the digest of the releases before them, so approvals given then still hold. The request names the digest you reviewed, so anything that changed meanwhile is never allowed unseen. A chat that changes the actions or tools, anything about where they run or the account that calls the tools clears the approval; changing only the page keeps it. Revoke from the same dialog. Scripts and every text you review refuse hidden characters (controls, zero-width and bidirectional formatting), as Run in console does.

The computer runs an action (`src-tauri/src/screens/run.rs`) in the screen's folder with stdin closed, without the variables of an agent session, and with `NO_COLOR=1`:

- PowerShell receives a constant command (`-NoProfile -NonInteractive -ExecutionPolicy Bypass -Command`) that sets UTF-8 output, adds the user's current PATH from the registry, reads the script from a private file named by an environment variable and deletes it, and runs it as a function named after the action, so its errors name the action and their lines. It ends with the script's `exit` or the exit code of the last program it ran. (`-EncodedCommand` would make Windows PowerShell write its errors as CLIXML.)
- bash starts as a login shell, as agents run commands, returns to the folder after the profile and runs the script from its file.
- In WSL, `wsl.exe` runs the fixed `screen-run.sh`, which reads the folder, the script, the time limit (0 for none) and each value as lines of base64 on stdin, never on a command line, exports the values, and runs the script with `setsid` under a job marker `wsl-cancel.sh` can stop; when the action has a time limit, a watchdog there ends it at that limit even if Windows lost the run.

Each output stream comes whole (`truncated` is always false). An action past its time limit is stopped with everything it started, and its outcome keeps what it printed. Actions run side by side, as many at once as a computer's screens ask for.

## How MCP calls run

The computer calls an allowed tool (`src-tauri/src/screens/mcp.rs`) through the CLI of the screen's account, started under that account's profile in the screen's folder with the MCP servers a chat of that account loads there: the profile's own, the definitions it shares from another account or this computer's CLI context (`--mcp-config` for Claude, `-c` overrides for Codex), and shared plugin servers. No model takes part, and Agent Studio reads no MCP credential or configuration body: the CLI connects the servers, keeps their sign-ins and makes the call.

- Claude Code runs in stream-json mode with no tools, hooks or session file, and answers its `mcp_call` control request for `mcp__<server>__<tool>` (the server named as Claude Code names it, so `claude.ai Linear` and `claude_ai_Linear` reach the same connector). The request carries `result_not_for_model`, so a large result comes whole instead of being shortened for a model. Claude Code waits for a server still connecting, Agent Studio refuses a form a server asks for, and Claude Code closes a stdio connection whose message is larger than it accepts (20 MB did, 1 MB did not, on 2.1.302).
- Codex runs its app-server with an ephemeral thread (`approvalPolicy: never`, which declines a server's forms) and answers `mcpServer/tool/call` on that thread. A server the page names as an agent saw it (`dash_name` for `dash-name`) is found by its configured name once, and a tool's `isError` result rejects with the tool's text. A separate WSL profile signs in with its Windows login first, as its chats do.

Each screen keeps one CLI while its page calls tools, side by side as many at once as it asks, and ends it five minutes after the last call ends, when a chat saves the screen again, when you revoke or delete it, when a call finds its server not connected, signed out or not started (so the next call starts a CLI that reads them again), and when the app quits. A call itself waits as long as its tool takes. A tool's content blocks reach the page as its server sent them, text, images as base64 data and resources alike, with its structured result.

## Where screens live

A screen lives on the computer that runs its actions, under app data `screens/` (`<id>.json`, and `<id>.data.json` for saved values), written atomically. Like tool results, it is never part of the workspace, exports, relay sync or prompts. A reply keeps only the card of each screen it saved (`screens` on the message: id, revision, title, environment), which syncs, exports and merges with the conversation like its other metadata.

Windows reach screens through transport (`listScreens`, `readScreen`, `runScreenAction`, `callScreenTool`, `allowScreen`, `revokeScreen`, `deleteScreen`, `loadScreenData`, `saveScreenData` in `src/lib/transport.ts`), routed by environment to the computer that keeps them: the desktop's own through `manage_screen`, others' and the Viewer's through the relay's `screens` job, whose request the relay validates strictly (`screenRequestSchema`) and whose large results leave once read. A run or a tool call another device asks for waits as long as it takes, and runs once however many copies of its call the window sends. The Screens tab asks each reachable computer for its list when it opens and a computer's list again when a reply there saves a screen; an offline computer's screens stay listed as last read, and its screen opens again once it connects. Deleting a screen asks first and removes its page, actions and saved values from its computer; chats keep their cards.

Remote screens need a relay that knows the `screens` job, which arrives with the release that brings this feature to the VPS. Likewise, another device's MCP calls need a relay that knows the job's `mcp` request; until the VPS runs the release that brings it, they work only in the desktop window of the computer that keeps the screen.

## Verification

On 2026-10-02 the installed CLIs built a screen through the production loops: `installed_claude_saves_a_screen_whose_action_runs_once_allowed` (Claude Code 2.1.287, Sonnet, 6 s) and `installed_codex_saves_a_screen_whose_action_runs_once_allowed` (Codex CLI 0.160.0, its default model, 22 s) each asked for a screen with one PowerShell action. Each model called `save_screen` with a valid definition (Codex's app-server accepted the dynamic tools on a new thread), the action was refused until allowed, then ran in real PowerShell and printed the expected JSON, and an out-of-range value was refused. Both opt-in tests use subscription capacity; run them with `cargo test --manifest-path src-tauri/Cargo.toml --lib saves_a_screen_whose_action -- --ignored --nocapture --test-threads=1`, with the inherited `CLAUDE*` session variables removed except `CLAUDE_CONFIG_DIR`. The native app's window, a remote computer's screen through the released relay and macOS or Linux hosts were not exercised.

On 2026-10-18 `installed_claude_answers_a_screens_mcp_calls` (Claude Code 2.1.302) and `installed_codex_answers_a_screens_mcp_calls` (Codex CLI 0.163.0) called every tool of a local stdio MCP server through the same sessions screens use: a text result, a 1 MB result whole, structured content, an image, a tool's own error and an unknown server, with the server running in the screen's folder; Codex reached `probe-server` named as `probe_server`. They need Node and no model, and run with `cargo test --manifest-path src-tauri/Cargo.toml --lib answers_a_screens_mcp_calls -- --ignored --test-threads=1`, again without the inherited `CLAUDE*` session variables. The same day the user's three approved screens read as allowed under the new digest, and `scripts/screens-mcp-native-smoke.mjs` drove an isolated debug build (`scripts/native-screens-mcp.tauri.json`, CDP 19891) without any login: for an isolated Claude and an isolated Codex account sharing nothing, MCP management added the probe to the profile, and a screen of that account had its tools refused until allowed. They then answered through `manage_screen` (text, 1 MB whole, structured content, a tool's own error, an unknown tool), and the screen's page called two tools through its window. The first call started the account's CLI (352 ms for Claude Code, 149 ms for Codex), later calls took about 4 ms on the same server process, and quitting left no CLI or server running. A claude.ai connector and an OAuth server's sign-in through a screen were not exercised.

Rust unit tests cover submission checks, parameter values, MCP tool declarations, the digest of screens with and without tools, the store's revisions, approvals and account, the request handler, parent-only tool calls for both providers, and real PowerShell and Git Bash runs on Windows (folder, quoting, UTF-8, exit codes, errors as text, time limits). `screens::mcp` tests drive both CLI protocols over in-memory pipes (answers in any order, refused CLI requests, a CLI that ends, Codex server names) and the per-screen CLIs with paused time (one shared CLI, another account, five idle minutes, an unreachable server, release and quitting). `cargo test --lib -- --ignored a_real_wsl_action` runs actions in the first WSL distribution, including a missing folder and a background child that ends at the limit. `src/lib/screens.test.ts` covers request and bridge validation, hosts from before MCP tools, the page document, and cards through events, storage and merges. `tests/screens.spec.ts` drives a reply that saves a screen, approval, runs, saved values, `studio.chat` and deletion in the desktop window, a screen whose MCP tools wait for approval and then answer, and a page that tries to open chats by itself or forge calls. `tests/screens-viewer.spec.ts` opens a computer's screen from the phone Viewer through a real relay, runs its action and calls its tool there, and the relay refuses malformed screen jobs.
