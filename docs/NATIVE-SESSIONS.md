# Native session continuity

Claude and Codex conversations now resume the installed CLI's own saved transcript. A new process still handles each submitted reply, but that process resumes the same session. The provider retains its tool results, intermediate messages, and compaction state according to its native persistence behavior. Agent Studio's bounded display history is no longer used to reconstruct every follow-up.

- Claude creates a UUID session with `--session-id` and uses that exact `--resume` ID thereafter. Initial app guidance and legacy context use non-query input; only the current submitted message has human provenance. Changed conversation instructions are supplied as new context. Background title generation retains `--no-session-persistence`.
- Codex creates a non-ephemeral app-server thread and subsequently calls `thread/resume` with `excludeTurns: true`. The original dynamic tool definitions remain with the thread; the new process handles their callbacks. Each reply applies the selected model and reasoning. Cancellation first requests `turn/interrupt` and allows up to five seconds for confirmation before terminating the owned process tree.
- Only current images and skill invocations are submitted on normal follow-ups. Earlier images remain in the native transcript. A retry sends an explicit continuation request instead of treating the original instruction as a new independent task. Unacknowledged delivery is identified as uncertain earlier context, with attachments retained for recovery.

The backend stores only a versioned binding, provider session ID, and history/instruction/scope fingerprints under the execution host's app-data `native-sessions` directory. It never accepts a native session ID or transcript path from the renderer or relay. The binding covers provider, account connection/profile, environment, app installation namespace, and folder. An OS file lock excludes concurrent runs of the same conversation across app processes. Atomic writes preserve the binding through normal restarts. Actual transcripts remain in the selected CLI profile; credentials are neither read nor copied.

Choosing CLI default on a resumed conversation resolves the current CLI configuration explicitly: Claude uses a bounded, non-query context report with tools/hooks disabled, and Codex uses its configuration/model catalog. This avoids retaining the previous explicit model from the transcript. Unavailable default metadata produces an actionable error instead of silently selecting a different model. [Claude documents its saved-model precedence](https://code.claude.com/docs/en/model-config); Codex fields are checked against the installed CLI's generated app-server schema.

Existing chats bootstrap once from their portable saved messages. Imported chats and conflict copies with a new conversation ID also bootstrap independently. Tool details omitted before this upgrade cannot be reconstructed. Native transcripts and bindings are not in workspace exports or relay sync; a Viewer resumes through the same execution host. Moving to another host or deleting a CLI transcript does not transfer that native history. Missing, corrupt, mismatched, or diverged existing bindings fail explicitly without silently replaying work. Start a new conversation to establish a new session. Deleting an app conversation does not delete the CLI's own transcript.

Switching an existing conversation to another account of the same agent is the one deliberate exception. Neither CLI keeps two logins in one profile, so the other account has its own profile directory and cannot resume the previous transcript. The next reply therefore starts a fresh native session under the selected profile, bootstrapped from the saved messages exactly like an older chat's first native reply, and reports that in progress. The previous account's transcript is never read, copied, or resumed, and its unrecorded tool details stay unavailable; a retry of the same request continues the interrupted attempt rather than treating it as new work. Version 2 bindings record the account and the location parts of the scope separately, so the host recognizes an account change at the same computer and folder by itself, while a changed computer, environment, installation, or folder still fails. Version 1 bindings cannot tell the two apart and switch only when the run request carries the renderer's explicit `accountSwitch` flag, which the app sends once an earlier reply used another connection. Bindings are rewritten as version 2 on the next successful bind, and Standalone working-folder bindings are re-keyed to the location so the chat keeps its folder. Switching back later starts over the same way; the earlier account's stale binding is never restored. The Native prompt tab reports a binding that belongs to the previously selected account until the first reply under the new one.

The portable request limits still apply: 200 messages and 400 KB of text, plus the existing image/visual limits. Native compaction can summarize older provider context as it does in the CLI. Stopping terminates owned processes; it does not preserve live shells or background workers. Claude workflow progress can remain in the transcript without making killed workflow processes resumable. Antigravity retains display-history replay, and terminal session commands remain unavailable in the composer.

This closes the verified cross-reply tool-context gap. It does not promise identical output to a desktop app: Agent Studio still supplies its own guidance and tools, and desktop-specific integrations, prompts, and runtime behavior can differ. Model generation also varies between runs.

Claude and Codex chat runs have no Agent Studio elapsed-time cutoff, including while waiting for a question answer or delegated work. Stop still cancels the owned run; Codex retains its five-second interruption grace period. Startup remains bounded to two minutes for Claude tool initialization and Codex turn initialization. Background title/usage queries, Antigravity's five-minute reply timeout, and relay heartbeat expiry are unchanged. Provider-side limits and individual tool timeouts still apply.

## Forking conversations

Use **Fork conversation** in the toolbar (under Conversation actions on phones) or the sidebar row's context menu. **Fork from here** below a finished assistant reply copies history through that reply. The new chat opens in Active with a `(fork)` title and an empty composer; no provider request starts until you send a message. An unsent draft in the chat you leave is restored when you return to it. Forking a sidebar row while a blank composer has an unsent draft creates the fork in Active without replacing that draft.

A whole-conversation fork keeps current next-reply settings, including the selected account. A fork from an earlier reply uses that reply's captured settings, or the conversation settings for older records without them. Computer, execution environment, and project folder stay the same. Messages, images, answered questions, accepted steering, reasoning, visualizations, plans, work history, usage, and recorded file changes remain available as copied history. Finished failed/stopped replies keep their original status. A running turn and its initiating user message are excluded; the first running reply cannot yet be forked. The source continues independently, including its queued messages.

Forks have new conversation and message IDs and use normal workspace persistence, export, and authenticated relay sync. The app checks the 20 MB workspace limit before inserting the copy, surfaces save failures, and never makes copied pending questions answerable. On the first send, Claude and Codex bootstrap a fresh native session from the fork's portable saved context. Native transcripts, unrecorded tool context, live processes, and credentials are not copied. Project forks operate on the same project files; Standalone forks get their own new per-chat working folder, without copying the source folder's files. Historical Files edited and usage readings describe the copied replies, not newly performed work.

## Persistent processes

Since 2026-09-19 a conversation's Claude or Codex process no longer ends with its reply. After a completed or cleanly interrupted reply the runner parks the process in a per-host pool (`src-tauri/src/pool.rs`) with its output readers idle, and the conversation's next reply reuses it: Claude receives the next human message on the same stream-json stdin, and Codex receives another `turn/start` on the loaded thread. Reuse requires the same provider, account connection and profile scope, computer and environment, folder, executable, model, reasoning, and native session ID; a switched account, a changed model or reasoning level, a moved folder, an unhealthy protocol state, or an exited process kills the parked process and launches a fresh one that resumes the native session exactly as before. Instruction changes and retries still travel in-band. The pool keeps at most four processes, releases a process after fifteen minutes idle, on conversation deletion, and on app close, and never parks background title or usage runtimes, Antigravity, or legacy chats without a conversation identity.

Stop now interrupts in-band first. Claude receives a `control_request` with subtype `interrupt` and answers with a `control_response` followed by an `error_during_execution` result for the interrupted turn; Codex receives `turn/interrupt` and reports the turn as `interrupted`. The runner waits up to five seconds for that turn end and then parks the process, so background shells and MCP servers survive a stop. If the CLI does not confirm within the grace period, or the interrupt could not be written, the owned process tree is killed as before, including WSL process groups, and the next reply resumes the transcript in a new process. Codex token counters and Claude cost reporting stay continuous while a process lives; a restart still resets Codex counters, so per-reply scoping is unchanged.

The composer accepts messages while a reply runs. Enter or the queue button holds up to eight messages per conversation in session memory, listed above the composer in order with a control that returns one to the draft. After the running reply completes, the next queued message is sent automatically with its images and skill invocation. A stopped or failed reply, or a reply that ends while the composer cannot send, returns queued text and images to the draft instead, oldest first ahead of any text already typed. Queued messages are never saved, exported, or relayed, and a Viewer observing a desktop-started reply queues locally the same way. The separate **Steer now** action sends plain text to the active Claude or Codex reply. Enter and Queue message still send a follow-up after completion. Images, skills, slash commands, and Gemini messages remain queue-only. Steering keeps the active account, model, reasoning, folder, and native session; edits to the toolbar still apply only to the next reply.

Steering is bound to the originating run and connection. Codex uses [turn/steer](https://developers.openai.com/pt-BR/docs/app-server) with the host-owned expectedTurnId and waits for the matching acknowledgment. Claude sends a UUID-tagged human message through stream-json and waits for its --replay-user-messages echo. Tool execution and model request boundaries determine when the provider incorporates the correction. Starting, ended, unsupported, or mismatched runs reject steering without converting it into a new reply. Each reply supports up to eight submissions, 30,000 characters each and 60,000 in total; duplicate identities cannot execute twice.

Accepted inputs appear as **You · Steered this reply** above that reply's answer and survive saves, exports, relay checkpoints, and stopped/failed replies. Fresh-session bootstrap includes them as earlier user context. Retrying a steered attempt retains the old reply and adds an explicit continuation request so its guidance remains visible. Unconfirmed or rejected submissions keep the composer text, and late confirmations cannot erase newer draft edits. If Claude finishes before confirming submitted input, the owned process is released instead of parking unseen follow-up work. Remote steering uses authenticated workspace jobs and the exact original connection; it never falls back to local execution or silently replays after reconnect.

## Validation

Fork checks (2026-09-19): `npm run verify` passed 215 unit tests, the frontend build/type check, and 148 browser scenarios. Fork coverage includes full/earlier history, independent continuation, saved drafts, running-turn exclusion, save failure recovery, mobile and keyboard controls, reload/export, and a real HTTP Viewer relay with separate private workspaces and an offline execution host. Rust format and clippy passed; the full Rust suite passed 151 tests with `-- --test-threads=1`, with four existing opt-in tests ignored. One parallel repeat hit the existing Claude interruption fixture's fixed 400 ms startup/cancellation race (`an acknowledged interrupt keeps the CLI`); the serial run retained every test and no production interruption behavior was changed.

`scripts/forks-native-smoke.mjs` drove the isolated `scripts/native-forks.tauri.json` Windows app on CDP 9588 through real Sonnet and GPT-5.6-Sol source/fork replies. Both forks recalled a random marker from saved history in distinct native sessions, preserved the source chat and binding bytes, and restored its unsent draft. The Codex Standalone case also verified context inspection before first send, a dedicated folder, and no source-file copy. The initial native run exposed the legacy folder fallback for copied history; the portable `forked` marker now selects a dedicated folder only for a new binding, preserving existing legacy and native bindings. Reports and inspected desktop/mobile/native screenshots are under `artifacts/forks/` and `artifacts/fork-*-browser.png`. Live fork continuation through WSL, Gemini, macOS/Linux desktop, a remote execution host, and physical phones was not exercised. Repeat with a separate Cargo target and WebView profile; never point this script at the normal app.

Standalone folder isolation (2026-09-13): `scripts/standalone-native-smoke.mjs first` uses the isolated `scripts/native-standalone.tauri.json` app on CDP 9541. Two real Windows Codex chats and one Claude chat create the same relative filename with different contents in separate per-chat folders. Context inspection returns each matching folder. A legacy Codex chat reads an existing file from the old shared runtime. After restarting only that QA app, the `second` phase rereads all four files and verifies unchanged native session IDs, account selections, and empty saved project paths. The test passed with GPT-5.6-Sol and Sonnet; screenshots and results are in `artifacts/standalone/`.

The opt-in `real_wsl_bridge_preserves_stdin_isolates_profiles_and_kills_descendants` Rust test also passed against installed WSL. It verifies distinct per-chat Linux folders, preserved files on a later visit, invalid-ID rejection, stdin, isolated profiles, cancellation, and early Stop using a controlled shell executable. This does not constitute a live WSL model test. No new Gemini, macOS/Linux desktop, or physical-phone provider run was performed for this change. Global CLI profiles and hooks remain configured as before.

Deadline regressions use Tokio's virtual clock: the response deadline stays pending through 24 simulated hours for Claude and Codex while bounded background deadlines still expire. A controlled native Windows child exercises the actual Codex protocol loop through two simulated hours, both completing afterward and cancelling with a pending question. The same test reproduces the old one-hour error before the fix; it does not represent an hours-long live model benchmark.
