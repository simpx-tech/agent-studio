# Native session continuity

## Claude Fast mode and fallback models

Chat instructions offers Fast mode (CLI default, On, or Off) and an optional ordered fallback-model list. `/fast` opens that control without sending anything. `/fast on`, `/fast off`, and `/fast default` change the next-reply preference directly; they are local shortcuts, work only while idle, and never reactivate a History chat. Selecting the shortcut preserves trailing draft text and attachments. Invalid command arguments remain in the composer.

The execution host adds an explicit `fastMode` boolean to the chat's process-local `--settings` JSON, preserving TODO tools and plan permission rules. CLI default omits the key. The selected profile's settings and provider eligibility still apply. Fast mode requests faster service at higher per-token pricing and uses usage credits on subscription plans; a saved preference is not proof of actual fast service. Claude can use standard speed when unavailable. No global/profile settings are written, and Agent Studio does not silently change the primary model.

Fallback models accept up to three distinct, bounded aliases or IDs, comma-separated. The host passes the validated list as one literal `--fallback-model` argument, allowing Claude to handle overload or unavailable models. Leaving it empty omits the flag and retains the CLI profile's fallback default. This does not mean fallback is disabled if the profile configures a chain. Model support and pricing are determined by the selected CLI/account.

Both settings are captured per reply and preserved through save, export, relay, retry, and forks. Changes invalidate the owning conversation's parked process, and the next process resumes the same native session. They never enter prompt history or restricted background title/usage requests. Other providers reject these request fields. Compaction retains the same launch preferences.

References: [Claude Fast mode](https://code.claude.com/docs/en/fast-mode) and [CLI fallback-model flag](https://code.claude.com/docs/en/cli-reference). Installed CLI checked: 2.1.277.

Verification on 2026-09-20: isolated Windows Tauri app, four real Opus replies with Off → On → Off → Off. Verified literal launch preferences, process replacement on changes, `--resume` on the same chat, unchanged-settings process reuse, saved reply settings, and actual provider completion. An earlier marker-recall probe also confirmed remembered context across replacements; a later repetition received a provider `reasoning_extraction` refusal, so the reusable smoke uses simple arithmetic. The checked Fast-mode request was served at standard speed; premium service eligibility and forced overload/unavailable-model fallback remain unverified. Browser checks cover desktop/mobile controls, draft/cancel behavior, History state, slash commands, validation, and reload; schema/native tests cover relay/fork preservation, launch identity, and background/provider rejection.

## Rewind and file Undo

**Rewind here**, shown below your message on hover or keyboard focus and always on touch screens, or **/rewind**, returns to immediately before that message. Confirmation shows how many messages will be set aside. The draft, account, location, next-reply settings, and files stay unchanged. **Undo rewind** restores the exact removed messages, including images and response metadata, until another message or a retry is submitted. The recoverable suffix is saved and exported with the conversation, so a restart does not lose it. A running reply or queued input must finish or be stopped first, and `/compact` waits until the next reply has started the new session.

Rewind advances the conversation's history revision and closes its parked process. The next Claude/Codex reply starts a new native session from only the retained portable messages; it cannot resume the discarded provider context. This deliberately does not preserve earlier native tool-only details or compaction state. The confirmation explains that limit, and the reply's Work history notes the new session. A rewound history is never carried to another account: after an account switch the next reply starts fresh under the selected account instead of forking the old transcript. After **Undo rewind**, the history again continues exactly what the bound native session received, so the next reply resumes that session. Old native transcripts remain in their CLI profile. A request carrying an older revision than the host's saved conversation or native binding is rejected until that window or device syncs; a newer request can arrive before the sync and proceeds. Concurrent deliberate edits are kept as conflict copies rather than spliced back into a rewound chat, while a one-sided archive change from another device carries over. Standalone working folders remain bound to the same conversation.

**Undo edits** below a completed, failed, or stopped response, or **/undo** for the latest eligible response, previews the recorded files on the execution computer and requires confirmation. It reverses successful file-tool results, including added, modified, renamed, and deleted UTF-8 text files when complete source was reported. Codex add/delete results contain full source in their `diff` field; updates contain unified hunks. Shell edits, external actions, private files, incomplete or oversized diffs, symlinks/reparse points, and edits outside the chat's working folder are not supported. Existing responses without a host checkpoint explicitly report that Undo is unavailable.

Private checkpoints contain bounded before/after text only on the execution host (`undo/<run-id>.json`), outside workspace exports and relay data. Limits are 32 files, 512 KB per file, and 8 MB per checkpoint. Preview and apply accept only conversation/run identities, using the saved host scope and trusted provider results. Every current file must match the recorded after-state before any restoration begins. An interrupted transaction is journaled and can finish only from its two recorded states; later user edits block recovery. Repeated Undo calls return the saved receipt without reverting newer work. Existing file permissions are retained; deleted-file permissions were not recorded. Checkpoints are retained with native app data.

Undo keeps the response and its original diff visible, labels its file edits undone, and removes that response's edits from the combined chat summary. Its receipt also advances the history revision; because the undone reply's saved context now says those file edits were undone, the next reply starts a new native session that receives it. Checking the files can be cancelled; restoring them cannot be interrupted. Remote Viewer requests route to the original execution computer, and the host saves the receipt even if the requesting Viewer disconnects. An offline or older host cannot perform file Undo.

Windows verification (2026-09-19): the isolated `scripts/native-rewind.tauri.json` app, launched through `npm run tauri dev` with a separate Cargo target and WebView profile on CDP 9593, passed real Claude and Codex Rewind, Undo rewind, draft preservation, and new-session exclusion of a discarded codeword. Claude file Undo rejected a later manual edit and then removed its created file. `scripts/undo-native-smoke.mjs` exercised a real Codex response adding, editing, and deleting three files; Undo refused a conflicting file before any write, restored all three after the conflict was removed, retained its receipt across app reload, and preserved a subsequent user edit on an idempotent retry. Reports and inspected screenshots are under `artifacts/rewind/`. The opt-in `scripts/rewind-native-smoke.mjs` creates fresh disposable chats for repeat checks. Browser tests cover desktop and phone-sized dialogs, cancel/confirmation, failure and retry, slash commands, persistence, and next-run history; Rust tests cover filesystem comparisons, interrupted recovery, path rejection, native session revision isolation, and provider source decoding. Unit and real HTTP relay tests cover conflict preservation and host routing. Live WSL, macOS/Linux, separate login profiles, paired Viewer, and physical-phone checks remain unverified.

## Saved native context

Claude and Codex conversations now resume the installed CLI's own saved transcript. A healthy parked process handles later replies; a replacement process resumes the same session. The provider retains its tool results, intermediate messages, and compaction state according to its native persistence behavior. Agent Studio's bounded display history is no longer used to reconstruct every follow-up.

- Claude creates a UUID session with `--session-id` and uses that exact `--resume` ID thereafter. Initial app guidance and legacy context use non-query input; only the current submitted message has human provenance. Changed conversation instructions are supplied as new context. Background title generation retains `--no-session-persistence`.
- Codex creates a non-ephemeral app-server thread and subsequently calls `thread/resume` with `excludeTurns: true`. The original dynamic tool definitions remain with the thread; the new process handles their callbacks. Each reply applies the selected model and reasoning. Cancellation first requests `turn/interrupt` and allows up to five seconds for confirmation before terminating the owned process tree.
- Only current images and skill invocations are submitted on normal follow-ups. Earlier images remain in the native transcript. A retry sends an explicit continuation request instead of treating the original instruction as a new independent task. Unacknowledged delivery is identified as uncertain earlier context, with attachments retained for recovery.

The backend stores only a versioned binding, provider session ID, and history/instruction/scope fingerprints under the execution host's app-data `native-sessions` directory. It never accepts a native session ID or transcript path from the renderer or relay. The binding covers provider, account connection/profile, environment, app installation namespace, and folder. An OS file lock excludes concurrent runs of the same conversation across app processes. Atomic writes preserve the binding through normal restarts. Actual transcripts remain in the selected CLI profile; credentials are neither read nor copied.

Choosing CLI default on a resumed conversation resolves the current CLI configuration explicitly: Claude uses a bounded, non-query context report with tools/hooks disabled, and Codex uses its configuration/model catalog. This avoids retaining the previous explicit model from the transcript. Unavailable default metadata produces an actionable error instead of silently selecting a different model. [Claude documents its saved-model precedence](https://code.claude.com/docs/en/model-config); Codex fields are checked against the installed CLI's generated app-server schema.

Existing chats bootstrap once from their portable saved messages. Imported chats and conflict copies with a new conversation ID also bootstrap independently. Tool details omitted before this upgrade cannot be reconstructed. Native transcripts and bindings are not in workspace exports or relay sync; a Viewer resumes through the same execution host. Moving to another host or deleting a CLI transcript does not transfer that native history. Missing, corrupt, mismatched, or diverged existing bindings fail explicitly without silently replaying work. Start a new conversation to establish a new session. Deleting an app conversation does not delete the CLI's own transcript.

Switching an existing conversation to another account of the same agent carries the latest native parent transcript into a new native session under the selected profile. The host closes only this conversation's parked process, resolves the previous profile from its local registry and binding, and validates immutable JSONL history (at most 64 MiB total and 128 ancestors). Claude uses native file resume with `--fork-session`; Codex imports the verified rollout and its paginated history ancestors into the destination's session store, then calls `thread/fork`. Ancestors include only their recorded byte prefixes, with complete-record boundaries and UUID identities validated before import. Codex imports remain in the destination because later native resumes and forks reference them; only the temporary launch snapshot is removed. Existing longer ancestor files are accepted only when their referenced prefixes match exactly. Existing source and destination transcripts are never overwritten. Tool results and compaction records in the parent transcript carry forward; live terminals, running workers, and subagent sidecar files do not. Credentials and unrelated profile files are never copied. Missing, incomplete, corrupt, or conflicting transcripts fail explicitly before a model reply; the app does not silently substitute visible-message history.

Version 2 bindings distinguish an account change at the same computer and folder from a moved conversation; changed hosts, environments, installations, or folders still fail. Version 1 bindings require the explicit `accountSwitch` flag and must resolve their original scope through the host registry. The destination binding changes only after the provider confirms its new native identity. Retrying continues the earlier attempt, and switching back forks the most recent transcript rather than restoring that account's stale history. Standalone chats keep their working folder. Before the first reply with the new account, the Native prompt tab still reports that the binding belongs to the previous account. This transfer is separate from the **Fork conversation** action, which retains its portable-history behavior below.

The portable request limits still apply: 200 messages and 400 KB of text, plus the existing image/visual limits. Native compaction can summarize older provider context as it does in the CLI. Stopping first tries the in-band interrupt described below; the fallback terminates owned processes and cannot preserve live shells or background workers. Claude workflow progress can remain in the transcript without making killed workflow processes resumable. Antigravity retains display-history replay, and terminal session commands other than `/compact` remain unavailable in the composer.

This closes the verified cross-reply tool-context gap. It does not promise identical output to a desktop app: Agent Studio still supplies its own guidance and tools, and desktop-specific integrations, prompts, and runtime behavior can differ. Model generation also varies between runs.

Claude and Codex chat runs have no Agent Studio elapsed-time cutoff, including while waiting for a question answer or delegated work. Stop still cancels the owned run; Codex retains its five-second interruption grace period. Startup remains bounded to two minutes for Claude tool initialization and Codex turn initialization. Background title/usage queries, Antigravity's five-minute reply timeout, and relay heartbeat expiry are unchanged. Provider-side limits and individual tool timeouts still apply.

## Forking conversations

Use **Fork conversation** in the toolbar (under Conversation actions on phones) or the sidebar row's context menu. **Fork from here** below a finished assistant reply copies history through that reply. The new chat opens in Active with a `(fork)` title and an empty composer; no provider request starts until you send a message. An unsent draft in the chat you leave is restored when you return to it. Forking a sidebar row while a blank composer has an unsent draft creates the fork in Active without replacing that draft.

A whole-conversation fork keeps current next-reply settings, including the selected account. A fork from an earlier reply uses that reply's captured settings, or the conversation settings for older records without them. Computer, execution environment, and project folder stay the same. Messages, images, answered questions, accepted steering, reasoning, visualizations, plans, work history, usage, and recorded file changes remain available as copied history. Finished failed/stopped replies keep their original status. A running turn and its initiating user message are excluded; the first running reply cannot yet be forked. The source continues independently, including its queued messages.

Forks have new conversation and message IDs and use normal workspace persistence, export, and authenticated relay sync. The app checks the 20 MB workspace limit before inserting the copy, surfaces save failures, and never makes copied pending questions answerable. On the first send, Claude and Codex bootstrap a fresh native session from the fork's portable saved context. Native transcripts, unrecorded tool context, live processes, and credentials are not copied. Project forks operate on the same project files; Standalone forks get their own new per-chat working folder, without copying the source folder's files. Historical Files edited and usage readings describe the copied replies, not newly performed work.

## Persistent processes

Since 2026-09-19 a conversation's Claude or Codex process no longer ends with its reply. After a completed or cleanly interrupted reply the runner parks the process in a per-host pool (`src-tauri/src/pool.rs`) with its output readers idle, and the conversation's next reply reuses it: Claude receives the next human message on the same stream-json stdin, and Codex receives another `turn/start` on the loaded thread. Reuse requires the same provider, account connection and profile scope, computer and environment, folder, executable, reasoning, and native session ID, plus the model for Codex; a switched account, a changed Codex model or reasoning level, a moved folder, an unhealthy protocol state, or an exited process kills the parked process and launches a fresh one that resumes the native session exactly as before. Instruction changes and retries still travel in-band. The pool keeps at most four processes, releases a process after fifteen minutes idle, on conversation deletion, and on app close, and never parks background title or usage runtimes, Antigravity, or legacy chats without a conversation identity.

Claude model and thinking-budget changes use the installed CLI's in-band controls before the next human message. The optional **Thinking token budget** in Chat instructions accepts Automatic (empty), Off (0), or 1,024–128,000 tokens. It is distinct from Reasoning effort; native model support and limits still apply. The budget is captured with reply settings and retained through saves, exports, relay sync, and forks. Each changed setting receives a unique control request ID and must acknowledge success before the next control or prompt is sent. Settings are applied only on the owning host between replies; editing the toolbar does not mutate a running reply. Effort, permission mode, auto-compaction window, structured output and temporary-plugin changes still require a new process. Background title/usage work never inherits a chat budget.

A rejected, malformed, timed-out (30 seconds), cancelled, or partially applied update never submits the next prompt and cannot leave an uncertain process parked. The next retry resumes the native session in a fresh process. Unrelated, stale, child, and foreign-session acknowledgments cannot release the prompt. Errors remain bounded generic text. Initial explicit budgets also use the control after SDK initialization; clearing one sends null to restore the spawn-time CLI default. No app budget is set through environment or launch flags, so Automatic does not retain an earlier app override.

Claude Code 2.1.277 acknowledges an omitted/null model or the string default without restoring the selected profile's configured model. On an explicit-to-default change, Agent Studio uses its existing bounded, tool-free default-model query in the same profile/folder, then sends that explicit model to the parked chat process. The query retains the validated Standalone folder binding on WSL, covered by command-construction tests. It never starts a model reply or replaces the chat process. See the [Claude SDK model-switching API](https://code.claude.com/docs/en/agent-sdk/python#methods).

Stop now interrupts in-band first. Claude receives a `control_request` with subtype `interrupt` and answers with a `control_response` followed by an `error_during_execution` result for the interrupted turn; Codex receives `turn/interrupt` and reports the turn as `interrupted`. The runner waits up to five seconds for that turn end and then parks the process, so background shells and MCP servers survive a stop. If the CLI does not confirm within the grace period, or the interrupt could not be written, the owned process tree is killed as before, including WSL process groups, and the next reply resumes the transcript in a new process. Codex token counters and Claude cost reporting stay continuous while a process lives; a restart still resets Codex counters, so per-reply scoping is unchanged.

The composer accepts messages while a reply runs. Enter or the queue button holds up to eight messages per conversation in session memory, listed above the composer in order with a control that returns one to the draft. After the running reply completes, the next queued message is sent automatically with its images and skill invocation. A stopped or failed reply, or a reply that ends while the composer cannot send, returns queued text and images to the draft instead, oldest first ahead of any text already typed. Queued messages are never saved, exported, or relayed, and a Viewer observing a desktop-started reply queues locally the same way. The separate **Steer now** action sends plain text to the active Claude or Codex reply. Enter and Queue message still send a follow-up after completion. Images, skills, slash commands, and Gemini messages remain queue-only. Steering keeps the active account, model, reasoning, folder, and native session; edits to the toolbar still apply only to the next reply.

Steering is bound to the originating run and connection. Codex uses [turn/steer](https://developers.openai.com/pt-BR/docs/app-server) with the host-owned expectedTurnId and waits for the matching acknowledgment. Claude sends a UUID-tagged human message through stream-json and waits for its --replay-user-messages echo. Tool execution and model request boundaries determine when the provider incorporates the correction. Starting, ended, unsupported, or mismatched runs reject steering without converting it into a new reply. Each reply supports up to eight submissions, 30,000 characters each and 60,000 in total; duplicate identities cannot execute twice.

Accepted inputs appear as **You · Steered this reply** above that reply's answer and survive saves, exports, relay checkpoints, and stopped/failed replies. Fresh-session bootstrap includes them as earlier user context. Retrying a steered attempt retains the old reply and adds an explicit continuation request so its guidance remains visible. Unconfirmed or rejected submissions keep the composer text, and late confirmations cannot erase newer draft edits. If Claude finishes before confirming submitted input, the owned process is released instead of parking unseen follow-up work. Remote steering uses authenticated workspace jobs and the exact original connection; it never falls back to local execution or silently replays after reconnect.

Restart recovery (2026-09-22): loading a saved workspace marks every reply that was still running as cancelled with the notice `This response was interrupted when the app closed.` Relay sync then reconciles that copy with the relay's last checkpoint. A viewer or another computer that restarted only observed the run stop, so a newer running checkpoint keeps winning there and its chat keeps following the live host. The execution host itself is different: after a crash or power loss nothing will ever finish its run, so `pollRelay` gives `mergeShared` a dead-run check that recognises replies whose connection executes on this installation, including its managed WSL distributions, and which are neither the current local run nor a claimed relay job. Their interruption then outranks the stale running checkpoint, the newest checkpoint content is kept, and the cancelled state is published so other devices stop showing Responding. A completed, failed, or stopped checkpoint still wins over the interruption. Before this rule, the first restart after an outage could merge the relay's later checkpoint back over the local interruption and leave the reply Responding with a growing elapsed time, while Stop had no live run to cancel.

## Waiting for background work

Claude Code runs slow commands with `run_in_background`, ends its turn, and the CLI re-invokes the model when each task exits. The end of a turn is therefore not always the end of the requested work. Counting running tasks cannot distinguish a test run from a dev server or app left running for the user, and Claude Code's own session state also ignores background shells. Background agents and workflows still hold a reply implicitly. For shell work, Claude chats get the `await_background_tasks` tool (`mcp__agent_studio__await_background_tasks`) from the in-process `agent_studio` SDK server. It is always loaded, so tool search never hides its description, and marked read-only. The model calls it right before ending a turn with the IDs of the finite background tasks whose results it still needs; the description tells it never to include servers, watchers or apps started for the user.

The runner accepts only a registered parent call, matched by input like `visualize`, naming tasks that this reply's parent launched and whose launching call returned while they kept running. Child tasks, running foreground commands, finished, unknown and malformed IDs are refused with a bounded explanation; a call takes at most eight IDs and a reply tracks at most 32. A result stays intermediate while a declared task runs, and afterwards until the CLI has delivered its completed or failed outcome to the model: as a replayed `<task-notification>` user message inside a turn, or as the turn the CLI starts after the result. The reply shows **Waiting for background work to finish** in its activity and keeps **Steer now** available. It ends at the result of that follow-up turn, so completion alerts, pending badges, mobile pushes and queued sends follow the actual end. If no turn starts within 15 seconds of an undelivered outcome, the reply ends anyway; stopped tasks deliver nothing. Token and reasoning counts sum every turn of the reply, the context reading keeps its latest value, and the cost is the change in the process's running total (see [USAGE.md](USAGE.md)). A follow-up turn's `system/init` rebinds the native session without unconfirming the reply's delivered message; before 2026-09-22 it did, so the next message resent the previous one as an interrupted delivery with refreshed instructions.

Stop during a wait sends the in-band interrupt plus a `stop_task` control request for each declared or delegated task the reply is waiting for. An idle CLI answers only with acknowledgements, so the reply ends as stopped once all of them arrive, and the process is parked with any server the user is trying still running. A rejected stop releases the process instead of parking it. A running turn still ends with its interrupted result, and an unconfirmed Stop keeps the five-second kill fallback.

Limits: tasks started by an earlier reply cannot be awaited, because each reply tracks only its own task lifecycle. A background task the model did not declare can still finish after the reply ended and re-invoke the model inside the parked process, where its output is not shown; the tool closes that gap only when the model declares its waits. Codex and Antigravity replies are unchanged.

Background-wait checks (2026-09-22, Claude Code 2.1.278): a stream-json probe with the app's SDK tool showed Sonnet 5, given only the tool description, starting a stand-in dev server and a 25-second test command in the background, declaring only the tests, and ending its turn; the CLI started the follow-up turn when the tests exited, and the server kept running. Further probes confirmed that an idle interrupt returns only an acknowledgement, that `stop_task` stops a task without a follow-up turn, and that a task finishing mid-turn is replayed as a `<task-notification>` user message. The opt-in `installed_claude_*` tests in `src-tauri/src/claude_native_tests.rs` drive the production launch flags and runner with the installed CLI and Sonnet: one reply waited 29 seconds for a declared 20-second test command, reported its output and left the server running; Stop during another reply's wait ended it as stopped with a parkable process. Controlled PowerShell children cover the ordinary wait, a completion before the result with a follow-up turn, a replayed completion without one, the fallback when no follow-up turn arrives (two seconds under test), token totals, and Stop stopping only declared work. These runs depend on the model's tool choice and do not cover WSL, macOS/Linux, or a Viewer-started reply.

## Claude chat instructions

**Settings → Claude chat instructions** holds one workspace-wide text that Agent Studio appends to the system prompt of every interactive Claude chat, in any folder. It starts with a default that asks Claude to run tests, builds and type checks in the foreground (Bash allows up to ten minutes) and to keep `run_in_background` for processes meant to keep running, such as dev servers, watchers or an app for the user to try. A Claude turn that waits in the foreground cannot end early, so the reply's completion alert stays accurate even when the model would not declare a background wait. Users can edit, clear or restore the text.

The optional workspace field `claudeInstructions` stores only a changed value, up to 4,000 characters: absent follows the current default, and an empty string turns the instructions off. It syncs with the paired workspace and exports; concurrent edits keep the device that changed it, a stale Settings save is refused once with an explanation, and a relay that predates the field drops it. Each Claude run request carries the effective non-empty text as a top-level `claudeInstructions` field, validated on the executing host and passed to the selected CLI as one literal `--append-system-prompt` argument. It never enters conversation history, per-conversation instructions, reply settings, or prompt replay. It joins the parked-process identity, so a change applies from each chat's next reply in a fresh process that resumes the same native session. Codex, Antigravity, and restricted background title or usage requests never receive it, and the Claude desktop app and terminal are unaffected.

## Compaction

Open any usage bar and choose **Compact context**, or submit **/compact** in an idle Claude or Codex chat. The button keeps the existing composer text and attachments. A slash request cannot include attachments or be queued while another operation is running. Claude accepts optional focus instructions after `/compact`; Codex accepts the command on its own. Send a normal message first for a new, imported, or newly selected account's conversation, so a matching native session exists. Compaction never starts a replacement session under another account.

The operation uses the same authenticated transport, selected computer/profile, native binding lock, cancellation, checkpoints, and parked-process pool as chat replies. Claude receives a human stream-json `/compact` message. Codex receives [`thread/compact/start`](https://developers.openai.com/pt-BR/docs/app-server) on the already loaded or resumed thread; its empty acknowledgment is not completion. Claude `system/status` with `compacting` and Codex `contextCompaction` items supply progress. A Claude `system/compact_boundary`, completed Codex item, or legacy `thread/compacted` confirms the boundary. The operation still waits for the parent result/turn completion and reports an explicit error if no boundary was confirmed. Claude zero-turn results are ignored only when an actual non-query context injection is pending.

Automatic boundaries also appear in reply history. Markers retain only bounded status, trigger, revisions and provider-reported before/after token counts, with current and legacy Codex events deduplicated. Codex does not identify automatic triggers, so unrequested boundaries are labelled simply **Context compacted**. Summaries, preserved message IDs, and native session IDs are never included. Saved chats, workspace exports, and relay checkpoints retain the markers; prompt replay excludes this metadata. Stops or failures without a boundary show **Compaction was not confirmed**. A completed boundary invalidates old request-context readings and growth trends until the provider reports a subsequent reading; before/after compaction counts do not masquerade as a measured model request.

Claude's usage panel also offers an automatic-compaction window: **Automatic**, presets, or a custom integer from 100,000 through 1,000,000 tokens. The selected value is saved per conversation and supplied via the installed CLI's `--autocompact` flag on chat launches only. Changing it replaces the parked process on the next operation while resuming the same native session. Automatic uses the CLI default. Background title and usage runtimes keep their existing restrictions. This setting is a compaction window, not the model's maximum context capacity; CLI/model limits still apply.

The installed protocol probe is `node scripts/compaction-cli-probe.mjs`; native UI proof uses `scripts/native-compaction.tauri.json` with its own Cargo target, WebView profile, and CDP port 9597, followed by `node scripts/compaction-native-smoke.mjs`. Automated coverage includes parent isolation, legacy alias deduplication, empty acknowledgments/results, unconfirmed completion, binding ownership, sizing bounds, stale checkpoints, saved history, draft retention, and responsive controls.

Compaction checks (2026-09-19): direct protocol and isolated Windows native UI runs passed with the existing Claude and Codex logins, Sonnet and GPT-5.6-Sol at low effort. Both compacted the current session, retained the composer draft, recalled a test fact afterward, and retained one completed marker after reloading the app. Claude accepted the 100,000-token window and reported 28,445 tokens before manual compaction and 1,951 after; Codex did not report before/after counts. Results and inspected screenshots are in `artifacts/compaction/`. Browser checks cover desktop and 390px layouts, sizing bounds, slash focus instructions, progress, stopped/unconfirmed state, and saved history. Automatic boundary handling has protocol-fixture coverage; a live automatic threshold was not reached. Live compaction through WSL, macOS/Linux, separate login profiles, paired Viewer, and physical phones was not exercised.
