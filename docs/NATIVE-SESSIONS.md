# Native session continuity

## Fast mode and Claude fallback models

**Fast**, beside the composer's Build/Plan picker, turns Fast mode on or off for a Claude or Codex chat whose selected model offers it, as its model catalog says: Claude Code's `initialize` answer marks models with `supportsFastMode` (the CLI default and Opus 5.5 with Claude Code 2.1.301), matched to each alias by value or by the model it resolves to, and Codex's `model/list` lists a Fast service tier (`priority`, whose description, such as "2x speed, increased usage", the toggle's hover shows; older CLIs list `fast` among `additionalSpeedTiers`). A chat keeps its choice while another model is selected, and the toggle returns with a model that offers it. The toggle sets an explicit on or off; `/fast` turns it on or off, and `/fast on`, `/fast off` and `/fast default` (the CLI default, which omits the setting) set it. Both are local: they never send a message or reactivate a History chat, choosing `/fast` from the list keeps the rest of the draft, a model without Fast mode refuses `/fast on`, and invalid arguments stay in the composer. Like Model and Reasoning, Fast mode can change while a reply runs and applies to the next message, which the Next message hint names; the reply that changes it says Switched to Fast mode or Switched to Standard speed. New chats start without it.

For Claude, the execution host adds an explicit `fastMode` boolean to the chat's process-local `--settings` JSON, preserving TODO tools and plan permission rules; the CLI default omits the key. Claude Code serves Fast mode in SDK sessions such as these only with that per-session opt-in (`fast_mode_disabled_reason: "sdk_opt_in_required"` otherwise), so the CLI default means standard speed here. The catalog's alias query opts in the same way, so Claude says whether the account can use Fast mode: a lasting reason (`free`, `preference`, `extra_usage_disabled`) goes with each model that has Fast mode as `fastModeBlocked`, the toggle's hover gives Claude's words for it (Fast mode requires usage credits, Fast mode requires a paid subscription, Fast mode has been disabled by your organization), and the toggle turns the warning colour while on. A network failure or a check still under way never blocks. The choice stays the user's, and the CLI decides at each reply. Fast mode is billed at higher per-token prices and uses usage credits on subscription plans; Claude can serve standard speed while it is unavailable or cooling down after its rate limit. A change replaces the conversation's parked process, and the next one resumes the same native session. No global or profile settings are written, and Agent Studio does not silently change the primary model.

For Codex, the host sends `serviceTierForTurn` with each `turn/start`: `fast`, which Codex takes for its `priority` tier, or `default` for standard speed. It never sets the thread's `serviceTier`, so a turn without the setting runs at the `service_tier` the CLI profile configures, and a change keeps the parked process. Codex omits a tier the model does not offer.

Fallback models stay Claude's, in Chat instructions. They accept distinct aliases or IDs, comma-separated, as many as the CLI takes; the CLI reports its own limit. The host passes the validated list as one literal `--fallback-model` argument, allowing Claude to handle overload or unavailable models. Leaving it empty omits the flag and retains the CLI profile's fallback default. This does not mean fallback is disabled if the profile configures a chain. Model support and pricing are determined by the selected CLI/account.

Both settings are captured per reply and preserved through save, export, relay, retry, and forks. They never enter prompt history or restricted background title/usage requests. Gemini rejects Fast mode, and every other provider rejects fallback models. Compaction retains the same launch preferences. A saved preference is not proof of fast service.

References: [Claude Fast mode](https://code.claude.com/docs/en/fast-mode) and [CLI fallback-model flag](https://code.claude.com/docs/en/cli-reference). Installed CLIs checked: Claude Code 2.1.301 and Codex 0.163.0.

Verification on 2026-09-20: isolated Windows Tauri app, four real Opus replies with Off → On → Off → Off. Verified literal launch preferences, process replacement on changes, `--resume` on the same chat, unchanged-settings process reuse, saved reply settings, and actual provider completion. An earlier marker-recall probe also confirmed remembered context across replacements; a later repetition received a provider `reasoning_extraction` refusal, so the reusable smoke uses simple arithmetic. The checked Fast-mode request was served at standard speed; premium service eligibility and forced overload/unavailable-model fallback remain unverified.

Verification on 2026-10-16: the opt-in `installed_claude_names_each_alias_for_its_model` read Fast mode for the CLI default and Opus 5.5, none for Sonnet 5.5, Fable 5.1 and Haiku 5.5, and `extra_usage_disabled` for that profile's account; Codex 0.163.0 listed a `priority` Fast tier for every model, answered `thread/start` with `fast` as `priority`, and the opt-in `installed_codex_answers_with_fast_mode_on_and_off` completed real turns with `serviceTierForTurn` `fast` and `default` through the production loop. `scripts/fast-fallback-native-smoke.mjs` drives the toggle in an isolated app. Browser checks cover the toggle for both agents, models without Fast mode, the blocked state, changes while a reply runs, slash commands, History state, validation and reload; schema/native tests cover relay/fork preservation, launch identity, and background/provider rejection.

## Rewind and file Undo

**Rewind here**, shown below your message on hover or keyboard focus and always on touch screens, returns at once to immediately before that message: clicking it already chose the message, and **Undo rewind** takes the rewind back. **/rewind** asks which message and shows how many messages will be set aside. Either way the message goes back into the message box, ahead of any draft, to edit or press Enter to send again. Its text returns, and so do its images, read back into memory from this computer's image store or the relay (`readChatImage`, the `read_chat_image` command on the desktop); an image that cannot be read is left out with a notice. Its Codex mentions stay chosen only while the conversation uses the account whose reply answered it, and must otherwise be chosen again. A message an earlier rewind returned and left unchanged gives way to the new one, so rewinding further back leaves only that message and the draft. The account, location, next-reply settings, and files stay unchanged. **Undo rewind** restores the exact removed messages, including images and response metadata, until another message or a retry is submitted. In the window that rewound, it also takes the returned message back out of the message box while it is as the rewind left it, restoring the draft; an edited message stays. The notice above the message box reads **Conversation rewound; files unchanged.** The recoverable suffix is saved and exported with the conversation, so a restart does not lose it. A running reply or queued input must finish or be stopped first, and `/compact` waits until the next reply has started the new session.

Rewind advances the conversation's history revision and closes its parked process. The next Claude/Codex reply starts a new native session from only the retained portable messages; it cannot resume the discarded provider context. This deliberately does not preserve earlier native tool-only details or compaction state. The rewound notice explains that limit, and the reply's Work history notes the new session. A rewound history is never carried to another account: after an account switch the next reply starts fresh under the selected account instead of forking the old transcript. After **Undo rewind**, the history again continues exactly what the bound native session received, so the next reply resumes that session. Old native transcripts remain in their CLI profile. A request carrying an older revision than the host's saved conversation or native binding is rejected until that window or device syncs; a newer request can arrive before the sync and proceeds. Concurrent deliberate edits are kept as conflict copies rather than spliced back into a rewound chat, while a one-sided archive change from another device carries over. Standalone working folders remain bound to the same conversation.

**Undo edits** below a completed, failed, or stopped response, or **/undo** for the latest eligible response, previews the recorded files on the execution computer and requires confirmation. It reverses successful file-tool results, including added, modified, renamed, and deleted UTF-8 text files when complete source was reported. Codex add/delete results contain full source in their `diff` field; updates contain unified hunks. Shell edits, external actions, private files, incomplete diffs, symlinks/reparse points, and edits outside the chat's working folder are not supported. Existing responses without a host checkpoint explicitly report that Undo is unavailable.

Private checkpoints contain the before/after text, whatever the size or number of files, only on the execution host (`undo/<run-id>.json`), outside workspace exports and relay data. Preview and apply accept only conversation/run identities, using the saved host scope and trusted provider results. Every current file must match the recorded after-state before any restoration begins. An interrupted transaction is journaled and can finish only from its two recorded states; later user edits block recovery. Repeated Undo calls return the saved receipt without reverting newer work. Existing file permissions are retained; deleted-file permissions were not recorded. Checkpoints are retained with native app data.

Undo keeps the response and its original diff visible, labels its file edits undone, and removes that response's edits from the combined chat summary. Its receipt also advances the history revision; because the undone reply's saved context now says those file edits were undone, the next reply starts a new native session that receives it. Checking the files can be cancelled; restoring them cannot be interrupted. Remote Viewer requests route to the original execution computer, and the host saves the receipt even if the requesting Viewer disconnects. An offline or older host cannot perform file Undo.

Windows verification (2026-09-19): the isolated `scripts/native-rewind.tauri.json` app, launched through `npm run tauri dev` with a separate Cargo target and WebView profile on CDP 9593, passed real Claude and Codex Rewind, Undo rewind, draft preservation, and new-session exclusion of a discarded codeword. Claude file Undo rejected a later manual edit and then removed its created file. `scripts/undo-native-smoke.mjs` exercised a real Codex response adding, editing, and deleting three files; Undo refused a conflicting file before any write, restored all three after the conflict was removed, retained its receipt across app reload, and preserved a subsequent user edit on an idempotent retry. Reports and inspected screenshots are under `artifacts/rewind/`. The opt-in `scripts/rewind-native-smoke.mjs` creates fresh disposable chats for repeat checks. Browser tests cover desktop and phone-sized dialogs, cancel/confirmation, failure and retry, slash commands, persistence, and next-run history; Rust tests cover filesystem comparisons, interrupted recovery, path rejection, native session revision isolation, and provider source decoding. Unit and real HTTP relay tests cover conflict preservation and host routing. Live WSL, macOS/Linux, separate login profiles, paired Viewer, and physical-phone checks remain unverified.

The rewind smoke also confirms that **Undo rewind** resumes the original native session. See docs/VERIFICATION.md.

## Saved native context

Claude and Codex conversations now resume the installed CLI's own saved transcript. A healthy parked process handles later replies; a replacement process resumes the same session. The provider retains its tool results, intermediate messages, and compaction state according to its native persistence behavior. Agent Studio's display history is no longer used to reconstruct every follow-up.

- Claude creates a UUID session with `--session-id` and uses that exact `--resume` ID thereafter. Initial app guidance and legacy context use non-query input; only the current submitted message has human provenance. Changed conversation instructions are supplied as new context. Background title generation retains `--no-session-persistence`.
- Codex creates a non-ephemeral app-server thread and subsequently calls `thread/resume` with `excludeTurns: true`. The original dynamic tool definitions remain with the thread; the new process handles their callbacks. Each reply applies the selected model and reasoning. Cancellation first requests `turn/interrupt` and allows up to five seconds for confirmation before terminating the owned process tree.
- Only current images and skill invocations are submitted on normal follow-ups. Earlier images remain in the native transcript. The history fingerprint names each image by the reference the chat keeps, never its bytes, so a binding saved while images were still inline continues once they move into the image store. A retry sends an explicit continuation request instead of treating the original instruction as a new independent task. Unacknowledged delivery is identified as uncertain earlier context, with attachments retained for recovery.

The backend stores only a versioned binding, provider session ID, and history/instruction/scope fingerprints under the execution host's app-data `native-sessions` directory. It never accepts a native session ID or transcript path from the renderer or relay. The binding covers provider, account connection/profile, environment, app installation namespace, and folder. An OS file lock excludes concurrent runs of the same conversation across app processes. Atomic writes preserve the binding through normal restarts. Actual transcripts remain in the selected CLI profile; credentials are neither read nor copied.

Choosing CLI default on a resumed conversation resolves the current CLI configuration explicitly: Claude uses a non-query context report with tools/hooks disabled, and Codex uses its configuration/model catalog. This avoids retaining the previous explicit model from the transcript. Unavailable default metadata produces an actionable error instead of silently selecting a different model. [Claude documents its saved-model precedence](https://code.claude.com/docs/en/model-config); Codex fields are checked against the installed CLI's generated app-server schema.

Existing chats bootstrap once from their portable saved messages. Imported chats and conflict copies with a new conversation ID also bootstrap independently. Tool details omitted before this upgrade cannot be reconstructed. Native transcripts and bindings are not in workspace exports or relay sync; a Viewer resumes through the same execution host. Moving to another host or deleting a CLI transcript does not transfer that native history. Missing, corrupt, mismatched, or diverged existing bindings fail explicitly without silently replaying work. Start a new conversation to establish a new session. Deleting an app conversation does not delete the CLI's own transcript.

Switching an existing conversation to another account of the same agent carries the latest native parent transcript into a new native session under the selected profile. The host closes only this conversation's parked process, resolves the previous profile from its local registry and binding, and validates immutable JSONL history (streamed whole, whatever its size or number of ancestors; a cyclic lineage is refused). Claude uses native file resume with `--fork-session`, except between two accounts linked to the same Claude directory ([shared context](SHARED-CONTEXT.md#linked-claude-profiles)): they read the same transcripts, so the selected account resumes the session in place and nothing is copied; Codex imports the verified rollout and its paginated history ancestors into the destination's session store, then calls `thread/fork`. Ancestors include only their recorded byte prefixes, with complete-record boundaries and UUID identities validated before import. Codex imports remain in the destination because later native resumes and forks reference them; only the temporary launch snapshot is removed. Existing longer ancestor files are accepted only when their referenced prefixes match exactly. Existing source and destination transcripts are never overwritten. Tool results and compaction records in the parent transcript carry forward; live terminals, running workers, and subagent sidecar files do not. Credentials and unrelated profile files are never copied. Missing, incomplete, corrupt, or conflicting transcripts fail explicitly before a model reply; the app does not silently substitute visible-message history.

Version 2 bindings distinguish an account change at the same computer and folder from a moved conversation; changed hosts, environments, installations, or folders still fail. Version 1 bindings require the explicit `accountSwitch` flag and must resolve their original scope through the host registry. The destination binding changes only after the provider confirms its new native identity. Retrying continues the earlier attempt, and switching back forks the most recent transcript rather than restoring that account's stale history. Standalone chats keep their working folder. Before the first reply with the new account, the Native prompt tab still reports that the binding belongs to the previous account. This transfer is separate from the **Fork conversation** action, which retains its portable-history behavior below.

The account can also be chosen while a reply runs (requested 2026-10-15). That reply keeps its account and process to its end: steering, answers to its questions and Stop still reach it, and the next-message hint names the new account beside any model and reasoning change. A message sent meanwhile is queued as usual and goes with the conversation's settings once the reply ends, so the host prepares the transfer from the transcript that reply completed. A queued message for another account never takes over a Claude reply that only waits for background work, because the new account needs a process of its own: it waits for that reply to end. As with any switch, the new account's first reply closes the parked process, ending background work it kept running.

Portable requests have no message, text, image or visual limit. Native compaction can summarize older provider context as it does in the CLI. Stopping first tries the in-band interrupt described below; the fallback terminates owned processes and cannot preserve live shells or background workers. Claude workflow progress can remain in the transcript without making killed workflow processes resumable. Antigravity retains display-history replay, and terminal session commands other than `/compact` remain unavailable in the composer.

This closes the verified cross-reply tool-context gap. It does not promise identical output to a desktop app: Agent Studio still supplies its own guidance and tools, and desktop-specific integrations, prompts, and runtime behavior can differ. Model generation also varies between runs.

Claude and Codex chat runs have no Agent Studio elapsed-time cutoff, including at startup (Claude tool initialization, Codex turn initialization) and while waiting for a question answer or delegated work. Antigravity replies and background title and usage queries have none either. Stop still cancels the owned run; Codex retains its five-second interruption grace period. Relay heartbeat expiry is unchanged. Provider-side limits and individual tool timeouts still apply.

## Forking conversations

Use **Fork conversation** in the toolbar (under Conversation actions on phones) or the sidebar row's context menu. **Fork from here** below a finished assistant reply copies history through that reply. The new chat opens in Active with a `(fork)` title and an empty composer; no provider request starts until you send a message. An unsent draft in the chat you leave is restored when you return to it. Forking a sidebar row while a blank composer has an unsent draft creates the fork in Active without replacing that draft.

A whole-conversation fork keeps current next-reply settings, including the selected account. A fork from an earlier reply uses that reply's captured settings, or the conversation settings for older records without them. Computer, execution environment, and project folder stay the same. Messages, images, answered questions, accepted steering, reasoning, visualizations, plans, work history, usage, and recorded file changes remain available as copied history. Finished failed/stopped replies keep their original status. A running turn and its initiating user message are excluded; the first running reply cannot yet be forked. The source continues independently, including its queued messages.

Forks have new conversation and message IDs and use normal workspace persistence, export, and authenticated relay sync. The app surfaces save failures and never makes copied pending questions answerable. On the first send, Claude and Codex bootstrap a fresh native session from the fork's portable saved context. Native transcripts, unrecorded tool context, live processes, and credentials are not copied. Project forks operate on the same project files; Standalone forks get their own new per-chat working folder, without copying the source folder's files. Historical Files edited and usage readings describe the copied replies, not newly performed work.

## Importing chats

**Settings → Workspace data → Import chats**, or **/import**, lists the chats that Claude Code and Codex saved on this computer and its managed WSL distributions, for every account. Each separate profile keeps its own sessions, and the terminal and the desktop apps share their environment's default CLI directory (`~/.claude`, `~/.codex`), so every one of those directories is a source. The Claude desktop app shows each of its accounts a different list of Code sessions while their transcripts all live in `~/.claude`: it files the list under `claude-code-sessions/<account>/<organization>/` in its own app data. The importer reads that index and matches each organization with the `orgId` that each Claude connection's `claude auth status` reports, so a desktop chat appears under, and continues with, the account that made it. Other chats continue with the profile that holds them, or else with the CLI login of the computer that runs them. The list filters by account and searches titles, first prompts and folders. Chats Agent Studio started (bound to a conversation, or recognized by its guidance or originator) stay hidden unless asked for, and a chat already imported offers **Open** instead.

Listing reads metadata. A Claude transcript is read whole up to 1 MB and otherwise 512 KB at each end, deserializing only the fields the list shows; Codex threads come from the profile's own `codex app-server` through `thread/list`, which scans rollouts so threads its state database missed are listed too. The host hands out an opaque key per chat, so no window ever names a native session ID or path. A session the desktop app moved into a second project folder is listed once, from its newest file.

An imported chat runs where its folder is, as the Claude app runs a chat: a folder inside a WSL distribution runs inside that distribution, with its own Linux CLI, git and toolchain at native speed, and a folder on this computer runs with this computer's CLI. A chat a Windows desktop app ran in a WSL folder therefore opens on that distribution's computer, in its folder, and continues with the account that made it through that account's login in the distribution; when that account is not connected there yet, the list says so (Connections adds it in one step, and it signs in there once), and the chat continues with the distribution's own login until the Agent picker switches it. That covers the Claude app's WSL sessions and the Codex app's threads in WSL folders, whether Codex recorded them by their `\\wsl.localhost` path or, from its WSL agent, by their Linux path. The distribution is the one the Claude app's index records (`wslConfig.distro`), or else the managed distribution that has the folder, and a folder on a drive WSL mounts (`/mnt/c/…`) is this computer's own (`C:\…`). The Claude app keeps such a chat twice: the Claude Code it runs inside the distribution writes the original to the distribution's own `~/.claude`, and the app copies it here under `projects/ssh-…`, where the copy can lag behind. The distribution's directory is a source when an account is connected there or the app's index names the distribution, and it is found without the distribution's CLI, so its chats are listed where Claude Code is not installed. Each chat appears once, from the copy used last or, of copies as recent, the longer one, and importing either copy marks both as imported. Chats a distribution's own CLI made, as its terminal makes them, continue on that distribution as well.

Importing reads one chat whole into a new History conversation. A Claude transcript is read along its active branch, from its latest record back to its start and through compaction boundaries to the history they summarized; every human prompt starts a reply, while tool results, task notifications, Claude Code's own notices and Agent Studio's context stay with the reply they belong to. Codex turns come from `thread/turns/list`, and a message sent while a turn ran becomes that reply's steering, as it does live, among the turn's items where it arrived, so the imported reply divides around it there. The records replay through the decoders of a live reply, so an imported reply keeps its Work history, reasoning, tool calls with their results (kept in the tool-output store like a live run's), files edited, plans, compaction markers and token usage. Prompt images move into the image store. Each reply records the model that ran it and its duration, and the conversation's next reply uses that model line's picker alias (`opus` for `claude-opus-5-5`).

The host records where the chat came from in `imports/<conversation>.json`: provider, environment, profile or default directory, session ID and, for Claude, the transcript's path inside its profile. None of it enters the workspace. The conversation's first reply forks that session into the selected account's profile, as an account switch does: Claude resumes a copy with `--fork-session` under a new session ID, and Codex copies the rollout and its ancestors when the profile differs, then calls `thread/fork`. The original stays as it was in its app. The copy streams whole, whatever its size, as an account switch's does. That reply also gives the model Agent Studio's guidance once. A Codex thread keeps the dynamic tools it started with, so visualize, send_files, compare_files and studio_ask_user are unavailable in an imported Codex chat. A rewind before the first reply starts a new session from the retained messages, and a session that is no longer on this computer continues from the imported messages with a notice. A chat whose folder is not on this computer can still be imported to read; continuing it needs that folder and an account of its agent on the computer that runs it.

Only the desktop app imports: the Viewer has no access to CLI stores, and the stores of other computers are not listed. Imported chats are ordinary conversations otherwise; they sync, export and fork like any other, while their native records stay on this computer.

## Persistent processes

Since 2026-09-19 a conversation's Claude or Codex process no longer ends with its reply. After a completed or cleanly interrupted reply the runner parks the process in a per-host pool (`src-tauri/src/pool.rs`) with its output readers idle, and the conversation's next reply reuses it: Claude receives the next human message on the same stream-json stdin, and Codex receives another `turn/start` on the loaded thread. Reuse requires the same provider, account connection and profile scope, computer and environment, folder, executable, reasoning, and native session ID, plus the model for Codex. For a native install the executable includes the size and modification time of the CLI file it runs (npm's script, or the binary itself), because an alias can mean a different model after a CLI update: Claude Code 2.1.278 resolves `opus` to Opus 5 and 2.1.281 to Opus 5.5. A managed WSL install's Linux file is not checked. A switched account, an updated CLI, a changed Codex model or reasoning level, a moved folder, an unhealthy protocol state, or an exited process ends the parked process and launches a fresh one that resumes the native session exactly as before. A healthy process ends as a terminal ends it (`Process::finish`): its input closes and it exits by itself, after any login renewal its profile's lock shows under way, and its tree is killed once it is gone or after ten seconds; an unhealthy one is killed at once. Claude Code renews an expired login in the background, and the server spends the old refresh token as soon as the request arrives, so a process killed before saving the new one signed its account out at the next renewal (2026-10-11). Instruction changes and retries still travel in-band. Since 2026-09-28 closing a chat is the user's decision: nothing expires or evicts a parked process, however long its chat waits or however many chats keep one, so background work such as a Monitor runs as long as it needs. Moving a chat to History or deleting it releases the process on the computer that runs it. The Viewer or another desktop asks that computer with a `release` relay job, and a chat deleted on another device is also released when the deletion reaches its computer by sync. History moves arriving by sync release nothing, because each desktop's startup moves its saved chats to History and publishes that too. A rewind, a file Undo and quitting the app (a window closed to the tray keeps them) end the process as well, and the pool never parks background title or usage runtimes, Antigravity, or legacy chats without a conversation identity.

Claude model and thinking-budget changes use the installed CLI's in-band controls before the next human message. The optional **Thinking token budget** in Chat instructions accepts Automatic (empty), Off (0), or any number of tokens. It is distinct from Reasoning effort; native model support and limits still apply. The budget is captured with reply settings and retained through saves, exports, relay sync, and forks. Each changed setting receives a unique control request ID and must acknowledge success before the next control or prompt is sent. Settings are applied only on the owning host between replies; editing the toolbar does not mutate a running reply. Effort, permission mode, auto-compaction window, structured output and temporary-plugin changes still require a new process. Background title/usage work never inherits a chat budget.

A rejected, malformed, cancelled, or partially applied update never submits the next prompt and cannot leave an uncertain process parked; an unanswered update waits for the CLI however long it takes, and Stop ends that wait. The next retry resumes the native session in a fresh process. Unrelated, stale, child, and foreign-session acknowledgments cannot release the prompt. Errors remain generic text. Initial explicit budgets also use the control after SDK initialization; clearing one sends null to restore the spawn-time CLI default. No app budget is set through environment or launch flags, so Automatic does not retain an earlier app override.

Claude Code 2.1.277 acknowledges an omitted/null model or the string default without restoring the selected profile's configured model. On an explicit-to-default change, Agent Studio uses its existing tool-free default-model query in the same profile/folder, then sends that explicit model to the parked chat process. The query retains the validated Standalone folder binding on WSL, covered by command-construction tests. It never starts a model reply or replaces the chat process. See the [Claude SDK model-switching API](https://code.claude.com/docs/en/agent-sdk/python#methods).

Stop now interrupts in-band first. Claude receives a `control_request` with subtype `interrupt` and answers with a `control_response` followed by an `error_during_execution` result for the interrupted turn; Codex receives `turn/interrupt` and reports the turn as `interrupted`. The runner waits up to five seconds for that turn end and then parks the process, so background shells and MCP servers survive a stop. If the CLI does not confirm within the grace period, or the interrupt could not be written, the owned process tree is killed as before, and the next reply resumes the transcript in a new process. In WSL that includes everything the launch started (`wsl-kill.sh`): its descendants and every process carrying the launch's `AGENT_STUDIO_JOB`, so commands Claude Code runs in sessions of their own end too, as `taskkill /T` ends them on Windows. Codex token counters and Claude cost reporting stay continuous while a process lives; a restart still resets Codex counters, so per-reply scoping is unchanged.

The composer accepts messages while a reply runs. Enter or the queue button holds any number of messages per conversation in session memory, listed above the composer in order with a control that returns one to the draft. After the running reply completes, the next queued message is sent automatically with its images and skill invocation. While a Claude reply only waits for background work, the next queued message goes at once instead and takes that wait over (see [Sending while a reply waits](#sending-while-a-reply-waits)). A stopped or failed reply, or a reply that ends while the composer cannot send, returns queued text and images to the draft instead, oldest first ahead of any text already typed. Queued messages are never saved, exported, or relayed, and a Viewer observing a desktop-started reply queues locally the same way. Each conversation keeps its own queue while other conversations send and reply. Its queued messages wait for its own reply, and they go out when that reply completes even while another conversation is open, without changing your remembered model choices. When a conversation that is not open stops or fails, or its next message cannot be sent (queued mentions from another account, images that cannot be saved), the queue waits until you open that conversation, where its messages return to the draft. The separate **Steer now** action sends plain text to the active Claude or Codex reply. Enter and Queue message still send a follow-up after completion. Images, skills, slash commands, and Gemini messages remain queue-only. Steering keeps the active account, model, reasoning, folder, and native session; edits to the toolbar still apply only to the next reply.

Steering is bound to the originating run and connection. Codex uses [turn/steer](https://developers.openai.com/pt-BR/docs/app-server) with the host-owned expectedTurnId and waits for the matching acknowledgment. Claude sends a UUID-tagged human message through stream-json and waits for its --replay-user-messages echo. Tool execution and model request boundaries determine when the provider incorporates the correction. Starting, ended, unsupported, or mismatched runs reject steering without converting it into a new reply. A reply takes any number of submissions of any length; duplicate identities cannot execute twice.

An accepted input shows as a message of your own, where the reply took it (requested 2026-10-13): your bubble at the right edge of the conversation, marked **Steer** above it, with the reply's work up to then above and the reply going on below under its own heading. The reply is still one reply. Each part of it keeps its own live activity while it runs and its own **Work history** afterwards, the later parts are headed with the time of their steer, and the answer, the footer and the reply's actions follow the last part. A steer the reply took before it had done anything stands above the reply, and steers taken one after the other stand together. Only an input the provider acknowledged becomes a message; until then the text stays in the composer.

The window that first hears a steer records its place beside the receipt, in the reply's optional `steeringPlaces`: `after`, the number of calls, comments, notes and reasoning blocks the reply had recorded until then, and `at`, the time the reply's computer confirmed it, which the `steering` event carries beside the receipt. Codex confirms a steer at once, so it can stand below a command that is still running; Claude Code confirms it when it takes it in, as the running call returns. A receipt itself never changes shape: releases before 2026-10-13 validate it strictly and would refuse a chat whose receipt held anything more, while they drop the list of places and keep every receipt. Copies of a reply keep a steer's place when they merge, the larger count when two differ, since a device that follows a reply through the relay can have missed entries the job no longer carried. Steers keep the order they were sent in whatever each copy counted, and one saved without a place, as replies steered on earlier releases are, follows the reply's work, with only the answer after it. A reply that ended without an answer shows its last comment in its place only when no steer followed that comment, so a comment written before a steer never reads as the answer to it.

Accepted inputs survive saves, exports, relay checkpoints, and stopped/failed replies. Fresh-session bootstrap includes them as earlier user context. Retrying a steered attempt retains the old reply and adds an explicit continuation request so its guidance remains visible. Unconfirmed or rejected submissions keep the composer text, and late confirmations cannot erase newer draft edits. If Claude finishes before confirming submitted input, the owned process is released instead of parking unseen follow-up work. Remote steering uses authenticated workspace jobs and the exact original connection; it never falls back to local execution or silently replays after reconnect.

Restart recovery (2026-09-22): loading a saved workspace marks every reply that was still running as cancelled with the notice `This response was interrupted when the app closed.` Relay sync then reconciles that copy with the relay's last checkpoint. A viewer or another computer that restarted only observed the run stop, so a newer running checkpoint keeps winning there and its chat keeps following the live host. The execution host itself is different: after a crash or power loss nothing will ever finish its run, so `pollRelay` gives `mergeShared` a dead-run check that recognises replies whose connection executes on this installation, including its managed WSL distributions, and which are neither the current local run nor a claimed relay job. Their interruption then outranks the stale running checkpoint, the newest checkpoint content is kept, and the cancelled state is published so other devices stop showing Responding. A completed, failed, or stopped checkpoint still wins over the interruption. Before this rule, the first restart after an outage could merge the relay's later checkpoint back over the local interruption and leave the reply Responding with a growing elapsed time, while Stop had no live run to cancel.

Window reloads (2026-10-19): a reload of the window is no restart. On 2026-10-19 the window reloaded (WebView2 recorded a browser reload at 09:28:52 while the app process ran on since 09:09; its browser keys and right-click Reload were live), and every page load then cancelled each running reply natively, read them as interrupted and moved every chat to History, so three running replies stopped. Now a page load only detaches each reply from the document that started it (`Runs::reloaded`), and the reply runs on, keeping what it reports (`src-tauri/src/reply_feed.rs`): each event in the place its first report took and at its latest report, so a reply keeps one copy of its answer, of each call and of each comment however often they changed, while drafts of questions and skills changes are not kept. The reloaded window lists those replies (`live_runs`) before it reads the workspace, so `loadWorkspace` leaves them running, and follows each one its chats hold as running with `follow_run` (`startReply`'s `resume`), which replays the kept events onto the saved reply, whose merges by identity and revision make that safe, forwards the rest and answers with the reply's end; questions, forms, steering and Stop reach the run as before. A reply another device asked for goes on publishing its relay request once the relay answers (`resumeJob`, with the request in the heartbeat meanwhile), ends here like one of the window's own when the relay no longer holds the request, and does so after 30 seconds without a relay. A run no chat holds as running, whose chat went or recorded its end, is stopped and let go, and a request the old document left waiting to begin is refused (`open_feed`), so no reply runs unfollowed. A reply's events stay five minutes after its end reached its window, for a reload before that window saved it or the repair of a page that went silent as it arrived (docs/DIAGNOSTICS.md), and until a window takes its end otherwise. `app_session` tells every page after the first of the process that it `reloaded`, so a reload leaves chats where they were. WebView2's browser keys (F5, Ctrl+R and their variants, the Refresh, Back and Forward keys, Alt+Left/Right) reach the page without reloading or navigating it, and its right-click menu has no Back, Forward or Reload (`src-tauri/src/page_guard.rs`). Queued messages, which live in the window's memory, still go with a reload.

Abandoned replies (2026-10-15): a reply can also be saved as running while its computer, running, holds no run for it. A conflict copy an earlier release made kept its reply running while the run went on in the original chat, and a reply's end can fail to reach the window. Nothing would ever end such a reply: Stop cancelled nothing, steering answered "This reply has ended. Your steering was not sent." and a message queued after it waited for good. Every ten seconds, while connected to the relay, the window of the computer that runs a reply's account looks for replies saved as running that are neither its own runs (`runs`, the window's runs still in flight) nor relay jobs it executes (`abandonedReplies` in `src/lib/transport.ts`). Another device publishes a chat before it sends this computer the request for its reply, which can then wait on the relay for a poll, so a reply counts as abandoned only when checks at least 20 seconds apart each find the relay holding no request for it that is still queued or running. Stop on such a reply asks once and ends it at once. The reply ends as cancelled with "This response is no longer running.", is saved and published, and a queued message returns to the composer. Neither this ending nor a conflict copy's alerts anyone, on the desktop or through the relay's pushes (`endedWithoutRun`).

## Waiting for background work

Claude Code runs slow commands with `run_in_background`, ends its turn, and the CLI re-invokes the model when each task exits. The end of a turn is therefore not always the end of the requested work. Counting running tasks cannot distinguish a test run from a dev server or app left running for the user, and Claude Code's own session state also ignores background shells. Background agents and workflows still hold a reply implicitly. For shell work, Claude chats get the `await_background_tasks` tool (`mcp__agent_studio__await_background_tasks`) from the in-process `agent_studio` SDK server. It is always loaded, so tool search never hides its description, and marked read-only. The model calls it right before ending a turn with the IDs of the finite background tasks whose results it still needs; the description tells it never to include servers, watchers or apps started for the user.

The runner accepts only a registered parent call, matched by input like `visualize`, naming tasks that this reply's parent launched and whose launching call returned while they kept running. Child tasks, running foreground commands, finished, unknown and malformed IDs are refused with an explanation; a call takes any number of IDs, and a reply tracks every task it declares. A result stays intermediate while a declared task runs, and afterwards until the CLI has delivered its completed or failed outcome to the model: as a replayed `<task-notification>` user message inside a turn, or as the turn the CLI starts after the result. The reply shows **Waiting for background work to finish** in its activity and keeps **Steer now** available; the **Background work** toggle beside the reply's elapsed time counts each task still running and lists it with its elapsed time when opened (see [CAPABILITIES.md](CAPABILITIES.md)). It ends at the result of that follow-up turn, so completion alerts, pending badges, mobile pushes and queued sends follow the actual end. If no turn starts within 15 seconds of an undelivered outcome, the reply ends anyway; stopped tasks deliver nothing. Token and reasoning counts sum every turn of the reply, the context reading keeps its latest value, and the cost is the change in the process's running total (see [USAGE.md](USAGE.md)). A follow-up turn's `system/init` rebinds the native session without unconfirming the reply's delivered message; before 2026-09-22 it did, so the next message resent the previous one as an interrupted delivery with refreshed instructions.

Each turn of such a reply ends with its own text. The reply's work records that text as a comment, like everything Claude writes, and from the turn's end it is also the reply's answer, shown under the work while the reply waits. When another turn begins, because the CLI re-invokes the model for a finished task or because you steered the reply while it waited, the answer starts again (requested 2026-10-13): with the first parent line of the turn the decoder sends an empty `text` event (`Decoder::turn_started`, which the runner asks for ahead of the steer's receipt), so the earlier text shows where it was written, as a comment among the reply's work, and what the new turn writes and does follows it. A steer taken while the reply waited therefore stands below that text and above the turn it started. The turn that ends the reply leaves its text as the answer, and a reply stopped or failed before that ends with the last comment it wrote, as any reply without an answer does. Before this, the earlier text kept the answer's place until the new turn ended: everything that turn wrote was added above it, and a reply stopped or cut off in that turn kept the old text as its answer. An empty `text` event only empties an answer and never makes one, so a copy of a reply whose answer was emptied is a later state than one that still holds it, which is how two copies level in everything else merge (`laterReply`). Visuals and files that the earlier text placed stay after the reply's prose, like any that no answer places.

### Sending while a reply waits

A reply that only waits leaves the CLI idle between turns, so a message does not have to wait for that work, however long it runs. The reply's heading then reads **Waiting for background work** instead of Responding, the composer's send button sends rather than queues, and a message sent, or one already queued, goes at once. The host numbers each idle stretch and reports it with a `backgroundwait` event, which the reply keeps as the optional `backgroundWait` field while the stretch lasts and drops when a turn starts or the reply ends. A window that receives the reply's events goes by them first, since a synced copy of the field can lag behind them, and a relay that predates the field drops it until it is updated. The window sends the next reply with `takeOver` naming the waiting reply's run and stretch. The host admits it beside the waiting reply, and the waiting reply accepts at its idle point only while that stretch is current, no steering awaits its echo, and the new reply's launch identity matches its process: otherwise it keeps waiting as before. Accepting ends the waiting reply as completed with the text it had, which the new reply's history already carries, and hands over the process with the delegated and declared work it still waits for, releasing its native session lock. The process is never parked in between, so no output is dropped. The new reply resumes the same native session, answers at once, and waits for the inherited work as for its own: a result ends it only after the CLI has replayed its message (a turn the work started first does not) and every inherited task has delivered its outcome, and Stop sends `stop_task` for the inherited work as well. Its reading of the account before the reply is skipped, since the waiting reply's reading as it ends marks the same moment.

The message joins the conversation, together with the new reply, only when the host confirms with a `takeover` event; a computer that runs the reply for another device adds the same two messages from the request's `takeOver.messages`. Until then it stays in the queue, marked **Sending now**. A refusal (a turn started meanwhile, the reply already ended, launch settings that need a new process, which would stop the work, or a host without this support) leaves it queued for the reply's next idle stretch or its end, and the window does not ask again in the same stretch. Changed settings are explained when they are the reason, and the window already holds back a message whose account, reasoning, plan mode, Fast mode, fallback models, structured output or auto-compaction differ from the waiting reply's.

The waiting reply keeps its sub-agents and workflows. Its tool and workflow records move to the process's background watch, the replies after it route the lines about that work there instead of recording them as their own, and the window applies what the watch reports to that saved reply: outcomes at once, progress with the next sync and at most every few seconds to disk. The results of their later calls are kept with that reply's other results. Other devices receive these updates with the synced conversation. File edits the work makes from then on are recorded, shown and undone with the reply that took over; an edit already under way at the hand-over is not recorded. The new reply names the reply it took over in the optional `tookOver` field (that reply's message id, set on the placeholder, so `takeOver.messages` carries it to the executing host, and kept through sync when an older relay drops it), and while it runs, its footer's **Sub-agents** toggle lists the sub-agents still running of that reply and of every reply taken over before it (`carriedSubagents` in `src/lib/subagents.ts`), each opening the conversation that its own reply keeps; until then the waiting reply had ended and nothing listed them (requested 2026-10-16). Meanwhile those sub-agents read **In background** in their reply's Work history and their conversations read live, as if their reply still ran; once the reply that waits for them ends, nothing is carried, whatever the saved records say. When the process ends, sub-agents and workflows of a handed-over reply that still ran read Stopped. Once none of them runs, the watch lets that reply go, so a sub-agent that a later reply resumes afterwards is recorded with that later reply.

Stop during a wait sends the in-band interrupt plus a `stop_task` control request for each declared or delegated task the reply is waiting for. An idle CLI answers only with acknowledgements, so the reply ends as stopped once all of them arrive, and the process is parked with any server the user is trying still running. A rejected stop releases the process instead of parking it. A running turn still ends with its interrupted result, and an unconfirmed Stop keeps the five-second kill fallback.

Limits: tasks started by an earlier reply cannot be awaited, because each reply tracks only its own task lifecycle and, after a take-over, the one it continues. A background task the model did not declare can still finish after the reply ended and re-invoke the model inside the parked process, where its output is not shown; the tool closes that gap only when the model declares its waits. The task's outcome is still recorded: the parked process's task notifications update the call in that saved reply and remove it from **Background work** (see [CAPABILITIES.md](CAPABILITIES.md)). Codex and Antigravity replies are unchanged.

Background-wait checks (2026-09-22, Claude Code 2.1.278): a stream-json probe with the app's SDK tool showed Sonnet 5, given only the tool description, starting a stand-in dev server and a 25-second test command in the background, declaring only the tests, and ending its turn; the CLI started the follow-up turn when the tests exited, and the server kept running. These runs depend on the model's tool choice and do not cover WSL, macOS/Linux, or a Viewer-started reply.

The opt-in `installed_claude_message_takes_over_a_reply_waiting_for_a_background_agent` test drove the production runner with Sonnet: the first reply started one background agent and ended its turn; a take-over request with that stretch received the process, the new reply answered a question 1.3 seconds later while the agent ran, and it ended 17 seconds later at the turn that followed the agent's report, while 16 updates of the agent reached the earlier reply. The runner took that result for the reply's end and released the CLI as it began the message. The CLI replays each message it takes, `/compact` and local commands included, before that message's result, so any Claude reply with tools now ends only at a result after its message's replay, and the empty turn of a notice before it is skipped like a context acknowledgement; a compaction still ends at its own result. ## Transcripts Claude Code cleans up

Claude Code deletes transcripts and other session files older than `cleanupPeriodDays`, 30 days by default, once a day, from whichever session on a Claude directory starts first, and headless sessions such as Agent Studio's run that sweep too. A chat resumes its native session from that transcript, so a chat left alone for a month used to fail with Claude Code's "No conversation found" (requested 2026-10-07, `src-tauri/src/retention.rs`).

- Every Claude process Agent Studio starts (chats, titles, usage and model readings, context inspection, MCP management and default-model queries) passes `cleanupPeriodDays: 3650` in its own `--settings`, Claude Code's own example for long retention. Agent Studio's processes therefore never delete transcripts, in the account's own profile or in a directory it shares.
- The Claude app and the terminal sweep the computer's own Claude directory (`~/.claude`, or `CLAUDE_CONFIG_DIR`) with their own settings, and Agent Studio's chats keep their transcripts there when they use the CLI login or a separate profile linked to it (docs/SHARED-CONTEXT.md). Before such a CLI starts, once per directory in each run of the app, Agent Studio adds `"cleanupPeriodDays": 3650` to that directory's `settings.json` when the file sets none: right after the opening brace, the rest of the file as it was, and a new file when there is none. A period you set yourself is kept, and a file that is a link, read-only or not a JSON object is left alone; set any period, including 30, to choose another. Inside a WSL distribution the launch script does the same (`share_retain` in `wsl-share.sh`). The Claude app's own desktop sessions were already exempt from the sweep.
- A transcript can still go: deleted by hand, by a period you chose, or before this change. Before a fresh process resumes a Claude session, the executing host looks for `projects/<folder>/<session>.jsonl` in the profile, by the folder the CLI runs in and then through every project folder. When the projects folder reads whole without it, the reply starts a new native session from the saved messages instead, as after a rewind, and says so: "Claude Code no longer has this chat's earlier session on this computer". Earlier tool details and compacted context are not carried over. An account switch whose source transcript is gone continues the same way rather than failing. A projects folder that cannot be read leaves the CLI to resume as before. `/compact` on a chat whose transcript is gone asks for a message first, since there is nothing to compact.

## Claude chat instructions

**Settings → Claude chat instructions** holds one workspace-wide text that Agent Studio appends to the system prompt of every interactive Claude chat, in any folder. It starts with a default that asks Claude to run tests, builds and type checks in the foreground (Bash allows up to ten minutes) and to keep `run_in_background` for processes meant to keep running, such as dev servers, watchers or an app for the user to try. A Claude turn that waits in the foreground cannot end early, so the reply's completion alert stays accurate even when the model would not declare a background wait. Users can edit, clear or restore the text.

The optional workspace field `claudeInstructions` stores only a changed value, of any length: absent follows the current default, and an empty string turns the instructions off. It syncs with the paired workspace and exports; concurrent edits keep the device that changed it, a stale Settings save is refused once with an explanation, and a relay that predates the field drops it. Each Claude run request carries the effective non-empty text as a top-level `claudeInstructions` field, validated on the executing host and passed to the selected CLI as one literal `--append-system-prompt` argument. It never enters conversation history, per-conversation instructions, reply settings, or prompt replay. It joins the parked-process identity, so a change applies from each chat's next reply in a fresh process that resumes the same native session. Codex, Antigravity, and restricted background title or usage requests never receive it, and the Claude desktop app and terminal are unaffected.

## Compaction

Open any usage bar and choose **Compact context**, or submit **/compact** in an idle Claude or Codex chat. The button keeps the existing composer text and attachments. A slash request cannot include attachments or be queued while another operation is running. Claude accepts optional focus instructions after `/compact`; Codex accepts the command on its own. Send a normal message first for a new, imported, or newly selected account's conversation, so a matching native session exists. Compaction never starts a replacement session under another account.

The operation uses the same authenticated transport, selected computer/profile, native binding lock, cancellation, checkpoints, and parked-process pool as chat replies. Claude receives a human stream-json `/compact` message. Codex receives [`thread/compact/start`](https://developers.openai.com/pt-BR/docs/app-server) on the already loaded or resumed thread; its empty acknowledgment is not completion. Claude `system/status` with `compacting` and Codex `contextCompaction` items supply progress. A Claude `system/compact_boundary`, completed Codex item, or legacy `thread/compacted` confirms the boundary. The operation still waits for the parent result/turn completion and reports an explicit error if no boundary was confirmed. Claude zero-turn results are ignored only when an actual non-query context injection is pending.

Automatic boundaries also appear in reply history, as entries of the reply's work (requested 2026-10-12): a marker shows in live activity and in **Work history** where the compaction began among the reply's calls, comments and reasoning, such as **Context compacted automatically · 967,265 tokens before → 8,081 after** between two groups of calls, instead of on a line above the answer. The window that first hears a marker records its place (`after`, the number of entries the reply had recorded until then), and copies of a reply keep it when they merge: the larger count when two differ, since a device that follows a reply through the relay can have missed entries the job no longer carried. A marker saved before places were recorded follows the reply's work, at the end of its history. A `/compact` reply is its compaction, so its marker stays the reply's content. Markers retain only status, trigger, revisions, that place and provider-reported before/after token counts, with current and legacy Codex events deduplicated. Codex does not identify automatic triggers, so unrequested boundaries are labelled simply **Context compacted**. Summaries, preserved message IDs, and native session IDs are never included. Saved chats, workspace exports, and relay checkpoints retain the markers; prompt replay excludes this metadata. Stops or failures without a boundary show **Compaction was not confirmed**. A completed boundary invalidates old request-context readings and growth trends until the provider reports a subsequent reading; before/after compaction counts do not masquerade as a measured model request.

Claude's usage panel also offers an automatic-compaction window: **Automatic**, presets, or any custom positive number of tokens. The selected value is saved per conversation and supplied via the installed CLI's `--autocompact` flag on chat launches only. Changing it replaces the parked process on the next operation while resuming the same native session. Automatic uses the CLI default. Background title and usage runtimes keep their existing restrictions. This setting is a compaction window, not the model's maximum context capacity; CLI/model limits still apply.

The installed protocol probe is `node scripts/compaction-cli-probe.mjs`; native UI proof uses `scripts/native-compaction.tauri.json` with its own Cargo target, WebView profile, and CDP port 9597, followed by `node scripts/compaction-native-smoke.mjs`. Automated coverage includes parent isolation, legacy alias deduplication, empty acknowledgments/results, unconfirmed completion, binding ownership, sizing validation, stale checkpoints, saved history, draft retention, and responsive controls.

Compaction checks (2026-09-19): direct protocol and isolated Windows native UI runs passed with the existing Claude and Codex logins, Sonnet and GPT-5.6-Sol at low effort. Both compacted the current session, retained the composer draft, recalled a test fact afterward, and retained one completed marker after reloading the app. Claude accepted the 100,000-token window and reported 28,445 tokens before manual compaction and 1,951 after; Codex did not report before/after counts. Results and inspected screenshots are in `artifacts/compaction/`. Browser checks cover desktop and 390px layouts, sizing validation, slash focus instructions, progress, stopped/unconfirmed state, and saved history. Automatic boundary handling has protocol-fixture coverage; a live automatic threshold was not reached. Live compaction through WSL, macOS/Linux, separate login profiles, paired Viewer, and physical phones was not exercised.
