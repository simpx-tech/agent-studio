# Workflows, visualizations, artifacts, plans, and tools

## Optional project folder

Choose a computer to select its agent, account, model, and reasoning and start chatting. A project folder is optional: computer-scoped new chats start as **Standalone**, and the Folder picker always offers **Standalone** to clear a draft's project folder. Clearing the folder preserves the draft, attachments, and model settings. Choosing a recent folder or browsing still adds project context; existing conversations keep their fixed computer, folder, and account.

New Standalone chats get a persistent working folder of their own on the selected execution computer. Native hosts use app-data `standalone/<conversation UUID>`; managed WSL uses `~/.local/share/<app identifier>/standalone/<conversation UUID>` in the selected distribution. Replies, retries, and app restarts reuse the same folder. Context and skill inspection use that chat's folder and keep separate caches for Standalone chats. Tool access and the selected CLI profile's global instructions, hooks, skills, and integrations remain enabled.

Existing chats retain their previous shared runtime to preserve file references and native session continuity. Host-local versioned bindings record the choice; imported saved history without a binding also retains the legacy runtime. New chats do not copy files or instructions from it. Chat deletion retains generated files and native transcripts. Working folders are not sandboxes: chat agents retain their configured full filesystem access.

The saved conversation retains its computer and environment even though no project path is sent to the provider. Desktop, managed WSL, and paired Viewer use the same selection and routing rules; unavailable or signed-out connections still cannot send, and another computer is never used as a fallback. Working-folder contents and bindings stay on the execution host, outside workspace exports and relay sync. Background title generation continues to use its separate restricted runtime.

## File and app mentions

Type `@` anywhere at a word boundary in a Claude or Codex draft to search files in the selected working folder. Type `$` in Codex to choose an accessible, enabled app. Arrow keys navigate; Enter, Tab or touch inserts the choice into the draft, and Escape dismisses. Selection never sends a message. Paths with spaces are quoted, and surrounding draft text is preserved. A new Standalone chat needs its first message to create its working folder before file search is available.

Codex uses the installed CLI's `fuzzyFileSearch` and paginated `app/list`. Its chat process enables stable `mentions_v2`; selected files and apps become structured `mention` inputs alongside the visible text. Claude receives literal `@path` text, with name-only discovery on its selected host and no Codex dependency. Claude search omits hidden and generated directories, skips symbolic links, and is bounded to 20,000 entries, 20 directory levels and three seconds. File pickers return at most 50 matches; the app catalog is bounded to 200 entries. Partial results are labelled. No file contents, app URLs, tool definitions or credentials enter discovery results.

Queries use the normal selected-connection transport, including managed WSL and Viewer jobs. They validate the folder/connection on the owning host, run separately from parked chat processes, and never start a model turn or install, enable, authenticate or invoke apps. Native queries have a two-process limit, a 20-second file timeout and a 60-second app timeout. App discovery suppresses `app/list/updated` because its unpaginated directory includes large icon payloads; bounded paginated responses supply the picker. The scan stops at 1,000 catalog entries or 200 accessible enabled apps, labelling partial catalogs. App metadata is cached only inside the composer for up to one minute; account, folder and inventory changes invalidate it. Late results cannot replace another selection.

Up to 16 selected Codex references are saved with their user message and retained through exports, relay, queue restoration and retries. Only the current submission becomes native mention input; earlier references remain historical text. Deleting or renaming a token drops its selected identity. Account/folder changes require selecting retained mention text again, and selected native mentions use Queue message during a running reply. Settings navigation preserves their draft identity. Plain typed `@path` text remains available without autocomplete.

`tests/mentions.spec.ts` covers draft insertion, native identity, Claude text, stale discovery, failure handling, Settings navigation, queue restoration and mobile layout. Rust tests cover bounded discovery and current-turn input mapping. The opt-in real-provider smoke is `node scripts/mentions-native-smoke.mjs`, using `scripts/native-mentions.tauri.json` with its own absolute Cargo target and CDP port 19661. Build from Codex with `npm run tauri dev -- --config scripts/native-mentions.tauri.json --no-watch -- -- --check-startup`, then use the guarded Windows launcher. The startup probe exits without leaving a modal rejection window that could be mistaken for a running app. The smoke uses disposable files and existing CLI sign-ins, consumes model usage for file-read checks, and only inspects app availability; `--apps-only` retries the catalog without another model reply.

Live Windows verification on 2026-09-20 confirmed Codex 0.153.4 and Claude file search, quoted-path insertion and real file reads through the native composer. Codex structured reference metadata was saved, and Claude kept literal text. Native Windows `app/list` returned service HTTP 403; the same installed CLI returned accessible apps when invoked from the Codex task environment. The picker reports the denial without exposing the upstream HTML, changing credentials, or bypassing network policy. Native app-catalog success remains unverified in that environment; app selection and structured input are covered by controlled browser and Rust tests. Results and screenshots are under `artifacts/mentions-native/`.

## Reasoning display

Claude thinking text and Codex reasoning summaries appear where they happened: in the live activity while a reply runs, and in **Work history** after a completed, stopped, or failed reply, between the progress comments and tool groups around them. Each block is muted prose beside a brain mark, readable without opening another disclosure and distinct from progress comments and the final answer. Markdown and code highlighting use the same sanitized renderer as answers, and links open through the same safe-source check as progress comments. A reply whose only activity is reasoning still gets a Work history. Replies without reported reasoning show none, including older history.

The decoder accepts parent Claude `thinking` blocks and `thinking_delta` events, Codex app-server `reasoning` items and `item/reasoning/summaryTextDelta` / `textDelta`, and legacy Codex exec reasoning snapshots. Codex turns request automatic summaries. Indexed parts preserve paragraph boundaries, and complete snapshots replace streamed content by identity without duplication. Claude Code prints each content block of a message as its own `assistant` line, so a block's array index in a snapshot is not its position in the message: once a message's thinking has streamed (chats pass `--include-partial-messages`), its snapshot lines add no reasoning, and snapshots without a stream are numbered by position across the message's lines. Empty thinking blocks, such as the signature-only block that opens Fable messages, reserve none of the bounded items. Replies saved before this was fixed hold each streamed Claude thinking block twice under the same message (`message:1` from the stream, `message:0` from the snapshot); the timeline shows identical text once per message. When Codex supplies both a summary and content, the summary is displayed. Signatures, encrypted or redacted payloads, child messages, and reasoning from another Codex turn are excluded.

Reasoning is saved as separate revisioned blocks, retained through workspace exports, relay events and same-run checkpoints. Capture is bounded to 64 items per reply and 16,000 Unicode characters per item; truncated text is marked incomplete. It never becomes final-answer text, prompt replay, title context, or an executable artifact.

Provider availability matters: live Windows checks on 2026-09-19 with Claude Code 2.1.277, Sonnet 5 and Sonnet 4.6 returned no thinking text despite reported thinking tokens. No disclosure is fabricated from tokens or signatures. This matches the [upstream headless thinking-display report](https://github.com/anthropics/claude-code/issues/82896). Claude's decoder and process/event path are covered by controlled thinking streams; live Codex GPT-6-Astra supplied a summary that streamed, rendered, and survived save/reload. The opt-in native check is `scripts/reasoning-native-smoke.mjs`, with results in `artifacts/reasoning-native/results.json`. Update the relay and Viewer alongside the native app to accept the new block type and expanded event envelope.

## MCP elicitation

Claude and Codex MCP servers can request input during a reply. The chat shows the server name and a form, or a URL flow with **Open page** and a separate **Continue** confirmation. **Decline** and **Cancel** return their distinct protocol actions. Defaults may populate fields, but nothing is submitted or opened automatically. Opening a URL or accepting its request does not confirm that authentication or another external action succeeded; the MCP server owns that confirmation. Form values are sent to the requesting server, so secrets belong in the server's external URL flow.

Supported forms use MCP's flat object schema: strings, finite numbers, integers, booleans, single-choice enums (including `oneOf` titles and legacy `enumNames`), and arrays of enum choices (including `anyOf` titles). Required/optional fields, defaults, length/numeric/item bounds, email/URI/date/date-time formats and bounded Rust-compatible patterns are validated on the native host. Unsupported validation keywords, nested objects, invalid patterns, secret formats and oversized schemas fail explicitly instead of silently dropping constraints. Limits are 16 requests per reply, 16 fields per form, 32 choices per field, 4,000 characters per text value and 24 KB per response. URL navigation accepts HTTPS and loopback HTTP only, without embedded username/password credentials.

The adapters handle Claude's snake_case `elicitation` control payload and Codex's `mcpServer/elicitation/request` form/URL union. Codex's stable `tool_call_mcp_elicitation` flag is enabled by the installed CLI; the extended OpenAI form capability is not advertised. Codex requests must match the bound parent thread and, when reported, the active turn. Claude rejects explicit child attribution and foreign session IDs; its current control schema does not include a tool-use ID for stronger child correlation. Responses go through structured stdin on the originating process, with native write acknowledgement. Cancellation, provider withdrawal, completion, process loss and stale connection/run identities close the live input channel. The normal composer draft and full-access execution are preserved. Codex requires the granular approval policy with only mcp_elicitations enabled: its never policy silently declines elicitation before emitting a request. Ordinary sandbox/rule/skill/permission approvals remain disabled. The host preserves full-access behavior for Codex-marked empty MCP tool-call approvals, but never automatically fills a nonempty form or accepts an explicit user-input, sensitive-action or strict-review request.

The native app and paired Viewer save only revisioned receipts containing request/run identity, server name, mode and outcome. Request messages, form definitions, URLs and responses remain transient and are excluded from workspace storage, exports, prompt replay and checkpoints. The Viewer fetches a pending request from its exact host/connection via authenticated relay jobs, including for desktop-started chats. Relay job bodies remain in the existing bounded in-memory job queue; they are not written to workspace files. Closed or restored history never recreates a provider input channel. Update the native app, relay and Viewer together.

`tests/elicitations.spec.ts` covers desktop and narrow-screen UI, failures/retries, explicit URL opening, cancellation, draft preservation and a real paired Viewer/relay roundtrip. Rust tests exercise both production stream runners with child-process protocol fixtures for form/URL accept/decline/cancel, plus validation, privacy and stale/withdrawn request rejection. An opt-in installed-CLI check is available with `cargo test --manifest-path src-tauri/Cargo.toml --lib elicitation_installed_clis -- --ignored --nocapture`; it uses a disposable MCP server and synthetic input, uses existing CLI authentication, and consumes model capacity.

Live Windows verification on 2026-09-19 with Claude Code 2.1.277 accepted a real MCP form and continued the reply, including through the native WebView and Tauri transport. Codex 0.153.4 accepted form input, declined URL input, and continued its real MCP call through the production runner. That CLI rejects URL mode before delivering a control request (`Client does not support URL-mode elicitation requests`); the Claude URL adapter is verified with a controlled native protocol stream until the CLI supports forwarding it. See the [upstream URL elicitation report](https://github.com/anthropics/claude-code/issues/88075). The repeatable native UI smoke is `node scripts/elicitation-native-smoke.mjs`, using `scripts/native-elicitation.tauri.json`, a separate Cargo target, Vite port 1461 and CDP port 19671; launch through `npm run start:windows -- -Executable <isolated binary>` after the `npm run tauri dev` build. Results and the reviewed form screenshot are under `artifacts/elicitation-native/`.

## Agent questions

Codex and Claude can ask questions during a running reply. A **Your input is needed** form appears in the conversation. Choose an option, select several when allowed, or type your own answer. **Send answers** returns all answers to the same running agent. No option is preselected or submitted automatically. **Skip questions** explicitly tells the agent you declined to answer. The normal message draft stays intact, and a delivery error leaves the form available to retry.

Multiple questions appear one at a time, with a **Question 1 of N** counter. Use the numbered buttons to jump directly to any question, or **Back** and **Next** to browse, even before answering. Checkmarks identify answered questions; you can revisit and edit them before submitting. Choices and text stay intact between steps. Each question uses radio buttons for one answer or checkboxes for multiple answers, according to the agent's question definition. Only **Send answers** on the final step requires and submits the complete set; **Skip questions** on any step skips the whole set. Single-question forms keep their direct submission action.

The form works in the native app and the paired Agent Studio Viewer, including for questions in a chat started on the desktop. Viewer answers go through the private relay to the connection that owns the original run; they do not start another reply. Submitted or skipped forms disappear without a **Your answers** card. Answer data remains in saved history and JSON exports and supplies earlier conversation context on later turns. Stopping a run, losing its process, or reaching its deadline makes outstanding questions unavailable. Reopening saved history cannot revive an old provider process.

Question history is retained by reply/run identity and request revision even when an older relay or client omits it from a sync response. An omitted field cannot dismiss a waiting local form or erase a submitted answer; newer answer/cancellation revisions still win, and conversation deletion remains effective. Keep the relay and Viewer updated so they can store and display questions themselves.

A full native page reload interrupts the old document's owned reply, including a provider waiting silently for an answer. The next reply waits for that process to finish stopping before starting. Ordinary navigation between chat, Connections, and Settings keeps the reply running. Interrupted history does not restore the old answer channel or automatically replay the request.

The adapter supports Codex's `item/tool/requestUserInput` (including nonblocking requests) and Claude's `AskUserQuestion` permission callback. Both providers also receive `studio_ask_user`: a Codex dynamic tool and a Claude in-process SDK MCP tool, available in ordinary full-access chat modes. Claude question callbacks do not introduce approvals for unrelated tools. Integration follows the [Codex app-server request protocol](https://learn.chatgpt.com/docs/app-server) and [Claude Agent SDK user-input protocol](https://code.claude.com/docs/en/agent-sdk/user-input). Antigravity's currently installed print interface does not expose a supported interactive question/answer channel, so its questions remain ordinary conversation text.

Question and answer data are escaped text, not HTML or application commands. Only parent calls are accepted. Limits are four questions per call, twelve choices per question, sixteen calls and 256 KB of question/answer history per reply. Secret-input requests are rejected; this form is not a credential-entry interface. The native registry validates the original run, account connection, request identity, and complete answer before writing structured data to the provider's owned stdin. Duplicate submissions cannot send another response. Claude and Codex runs, including pending questions, have no Agent Studio elapsed-time cutoff. Cancellation, startup failure checks, and ongoing relay heartbeats remain active; abandoned remote hosts still expire promptly. Update the relay and clients together to preserve the optional `questions` field and enable answer jobs.

Verification: `src/lib/questions.test.ts`, the Rust `providers::questions` tests, `tests/questions.spec.ts`, and `scripts/questions-native-smoke.mjs`. Native QA requires the isolated `scripts/native-questions.tauri.json` app, a separate Cargo target/WebView2 profile, and debugging port 9497. The native script checks the exact app identifier before touching its disposable workspace, then tests real provider calls and UI answers without accessing CLI credentials.

## Input templates

Choose **Templates** beside the composer, then **New template**. Give the template a name and write your reusable prompt. Add custom inputs with **Add input field** or type placeholders such as `Review {{change}} with a focus on {{areas to check}}`. Field names can contain letters, numbers, spaces, underscores, and hyphens. Repeating a field name reuses its value; prompts without fields are supported too.

Choose a saved template, fill each input, and review the message preview. **Insert into message** appends the filled text after the existing draft, with a blank line between them, and returns focus to the composer. It does not send, start an agent, restore a History conversation, or alter attachments and chat settings. Edit the draft as usual and press Send when ready. Cancel or Escape leaves the draft unchanged. All values are plain text and can span multiple lines; values containing placeholders or HTML remain literal text.

The library supports search, editing, and confirmed deletion. Definitions are stored in the optional `inputTemplates` field of workspace version 3, included in JSON exports, and synchronized through the existing private workspace relay. Filled values remain temporary until insertion and are not saved as template defaults. Signing out or changing workspaces clears the dialog and its values. Concurrent template edits retain a named conflict copy; an editor whose saved template has already changed on another device must reopen it before saving. Limits are 100 templates, 80 characters per name, 30,000 characters per template and combined message, and 20 different fields with names up to 60 characters. The workspace's existing 20 MB storage limit still applies. Update the relay and paired apps together to retain the new optional field.

Verification lives in `input-templates.test.ts`, `tests/input-templates.spec.ts`, and `scripts/input-templates-native-smoke.mjs`. The native script requires the isolated `scripts/native-input-templates.tauri.json` app identity and WebView2 debugging port 9481 (`TEMPLATE_QA_PORT` can override the port). Use a separate Cargo target and WebView2 data folder. Wait for the Templates button to become enabled after reload: the chat shell renders before the workspace load completes, and its presence alone previously allowed the test to open an empty library. The button now stays disabled during loading. Native QA exercises actual save/reload and draft insertion; it deliberately makes no provider request.

The shared input focus ring extends 6px beyond a control (2px outline plus 4px offset). Keep at least that much space inside the template body's scroll boundary; its former 4px side padding clipped both sides of focused inputs. The body now uses 8px padding and scroll padding. Check focused search, editor, and fill inputs on desktop and narrow layouts, including controls scrolled into view.

## Interactive visualizations

Ask Codex or Claude to visualize a process, chart, comparison, or simulation. Both can call **visualize** to put an interactive HTML/SVG fragment between the paragraphs it explains. Visuals share the reply's typography, colors, and transparent background, with no enclosing card or repeated title bar. Their height follows their content, including interactions and narrow layouts. Restart, expand, and side-panel controls appear on hover or keyboard focus and stay visible on touch layouts. The larger viewer offers source inspection and downloads. Controls inside a visual stay local; follow-up questions go through the composer.

After accepting a visual, the tool tells the agent to place `<!-- visualize:ID -->` on its own line between blank lines in the explanation. Only a standalone top-level marker for an accepted visual positions it; quoted/code examples cannot create previews, and repeated markers do not duplicate a frame. Older replies without markers retain their visuals below the prose. Markers and exact source survive history/export/relay without changing the workspace schema. Authors should use natural-height fragments, the supplied CSS color variables, and no outer background, dashboard shell, or repeated prose heading.

Agent Studio supplies this tool through Codex app-server dynamic tools and Claude Code's SDK MCP stream (`mcp__agent_studio__visualize`). It uses the installed CLI and selected account, computer, and folder. This is an Agent Studio integration, not an embedded Codex or Claude chat application. Codex's installed visualization skill can guide content creation, but must submit its fragment through the tool rather than emitting a local-file reference. Agent Studio does not read files named in responses. The tool is not enabled for Gemini, titles, or other restricted background queries.

The tool takes `id`, `title`, and `html`. Reusing an ID updates that visual in the current reply. Only validated parent submissions are displayed; Claude submissions also require successful matching tool results. Visual source and revisions survive history, exports, and relay checkpoints. Completed visual source is provided as earlier context for follow-up edits, without replaying tool calls. Limits are 512,000 UTF-8 bytes per source, 12 visuals and 2,000,000 bytes per reply, and 8,000,000 bytes of visual source in request history. The existing 20 MB workspace limit still applies.

Visuals use the artifact sandbox with inline CSS/JavaScript, SVG, and data images. External scripts, styles, network calls, nested frames, local file access, application commands, and host follow-up APIs are unavailable. Include required data and code directly. The bundled chat font loads as data; it needs no network access. The renderer reports only its height to the owning frame, checked by window identity and a per-render token and clamped to 24–1,600 pixels; larger content scrolls inside the preview. It cannot issue application commands. Source inspection and downloads retain the original submitted source. Reloading restores the saved visual, resetting any temporary interactions such as a slider position.

Integration references: [Codex dynamic tool calls](https://learn.chatgpt.com/docs/app-server), [Claude Code custom tools](https://code.claude.com/docs/en/agent-sdk/custom-tools). Claude Code's SDK requires bidirectional stdin for custom tools; Agent Studio retains it until a result arrives with no delegated agent/workflow tasks pending, then waits for the owned process to exit. Persistent background shell tasks do not hold that input open.

## Slash commands and skills

Start a message with `/` to search commands and skills for the selected agent. Use the arrow keys and Enter or Tab to complete a choice, or click/tap it. Escape closes suggestions. Completing a native command or skill inserts its name and a space without sending, so you can add arguments before submitting. You can also type the full `/name arguments` directly. Namespaced Claude commands, including plugin skills and saved native workflows, keep their CLI spelling.

App shortcuts are `/help`, `/new`, `/model`, `/reasoning`, `/instructions`, `/context`, `/usage`, `/rewind`, `/undo`, and `/connections`. They open existing app controls without creating a provider reply; remaining text stays in the draft. `/new` starts a conversation on the selected computer and folder. `/rewind` and `/undo` open the Rewind and Undo edits confirmations described in docs/NATIVE-SESSIONS.md. Instructions remain editable between replies. Model and reasoning changes use their existing next-message behavior.

Claude suggestions use the command metadata returned by the selected CLI profile's initialization. Codex suggestions include only enabled, CLI-reported skills; selecting a duplicate name retains the exact source path. The app translates `/skill-name` into Codex's `$skill-name` spelling plus a structured `skill` input on stdin. The visible user message retains its slash spelling, with bounded name/path metadata preserved through saved history, export, relay delivery, and retry. Earlier skill references are not injected again on subsequent replies. Selecting a skill does not claim it ran. See the official [Codex skill input contract](https://learn.chatgpt.com/docs/app-server#start-a-turn-invoke-a-skill) and [Claude command discovery and dispatch](https://code.claude.com/docs/en/agent-sdk/slash-commands).

Discovery shares the Model context cache and owning-host transport. It does not load file bodies into the composer or expose CLI initialization/account payloads. Switching agents, models, folders, or computers cannot reuse another selection's results. Failed refreshes preserve cached suggestions but block invocation until a fresh discovery succeeds. Offline or signed-out agents expose only app shortcuts. The installable PWA uses its selected computer's catalog and execution. Update the relay and execution computers together: older desktop hosts without command-catalog support show an update notice instead of silently discarding native skill references.

Terminal/session operations such as `/resume`, `/workflows`, and `/loop` remain unavailable in the composer. Agent Studio resumes its own Claude/Codex sessions automatically through their native protocols, without exposing terminal session controls or importing arbitrary CLI sessions. Use `/new` for a fresh app conversation. `/compact` is available for idle Claude and Codex chats, along with Compact context in usage details and Claude auto-compaction sizing. Unknown commands keep the draft and explain the problem. Absolute paths, fenced/inline code, and slash text inside ordinary prose remain ordinary messages. Gemini offers app shortcuts only. See [native session continuity](NATIVE-SESSIONS.md).

## Claude workflows

Ask for a workflow directly in chat, or enter a saved `/workflow-name` command and its input in the composer. The selected Claude Code CLI uses its native `Workflow` tool and controls orchestration, branching, parallel agents, and intermediate results. There is no separate workflow toolbar button or launcher. See [Claude Code Dynamic Workflows](https://code.claude.com/docs/en/workflows).

Native saved scripts load from the selected project's `.claude/workflows/`, the selected CLI profile's personal workflow directory, and configured plugins. Include “save it for reuse,” a name, and a project or personal location in your request to have Claude save its script. Invoke that native command in later chats. These files belong to the execution computer and are not copied into workspace exports or relayed to another computer. Existing profile/organization workflow settings still apply. The app does not create a second workflow library or run JavaScript itself.

The panel tracks native run IDs, status, phases, agent labels/models, reported token/time counts, and bounded result previews. The native launch acknowledgement is not completion: Agent Studio waits for the background task and subsequent CLI results. Only current human input gets `origin: {kind: "human"}`; earlier context is sent separately with `shouldQuery: false` so history cannot opt a new prompt into the `ultracode` keyword. Native `task_progress.workflow_progress` frames provide phase and agent metadata in Claude Code 2.1.267; older versions may report less detail. The SDK documents [Workflow inputs/outputs and background task notifications](https://code.claude.com/docs/en/agent-sdk/typescript).

Running requires the exact selected connection to be ready. The selected host owns the CLI process, account/profile, working folder, and captured parent model settings. Workflow scripts may choose their own agent models under Claude's native policy. **Stop response** cancels the owned process tree, including its workflow. Claude and Codex replies have no Agent Studio elapsed-time cutoff, including while waiting for answers. Startup checks remain bounded, and relay heartbeats still expire after 45 seconds without contact. There is no automatic replay after interruption. Retry resumes the same native transcript with an explicit continuation request to inspect existing results before repeating side effects. This preserves context; it cannot guarantee that every external operation is idempotent or revive killed background tasks.

The terminal `/workflows` menu, interactive pause/resume/restart controls, and resuming a previous native run across app replies are not exposed. Use the installed Claude CLI for those operations. Agent Studio renders at most 16 native runs per reply, 64 phases and 128 agents per run; omitted phase/agent details get a limit notice. Native progress persists through saved history, exports, and relay revisions. Legacy app-owned step definitions and their results remain readable/exportable, but the custom editor and sequencer have been removed; old execution requests are rejected.

## Plan and progress

A reply's provider plan, native workflow runs and background work appear as compact toggles in its footer row: after the live elapsed time while the reply runs, and after its timing and **Files edited** once it ends. The row wraps on narrow screens and keeps the space above the composer free. While the reply runs, the **Plan** toggle shows completed steps and names the step in progress when there is room; a workflow toggle shows its run status, and **Background work** counts what still runs. Click a toggle to open its steps, phases and agents, or running items in a panel below the row; one panel is open at a time, it renders on first opening, and an open panel stays open when the reply ends. Completed Work history sits directly below the model title, above the final answer. Retry is the last action below token/time. Workflow progress and the agent's current plan are labelled separately. A completed reply never automatically completes pending plan steps; stopped, failed, or unconfirmed work stays visibly unfinished. Plans remain out of the conversation text replay.

Codex plans come from [`turn/plan/updated`](https://learn.chatgpt.com/docs/app-server#turn-events). Claude supports both `TodoWrite` and the newer `TaskCreate`, `TaskUpdate`, `TaskGet`, and `TaskList` tools, applying updates only after successful tool results and associating task IDs from creation results. Child-agent plans cannot overwrite the parent's panel. Snapshots are bounded to 64 items and merged by revision through checkpoints and relay delivery.

Agent Studio also supplies Codex with `studio_update_plan` using the app-server's [dynamic tool API](https://learn.chatgpt.com/docs/app-server#dynamic-tool-calls-experimental). Codex 0.153.4 did not expose its built-in `update_plan` in live checks with GPT-5.5 and GPT-5.6 Sol. The app tool accepts a bounded plan snapshot from the parent thread and updates the same panel; it executes no work or filesystem operations. Invalid arguments and child calls are rejected, repeated identical snapshots retain their revision, and tool activity records the invocation without arbitrary arguments. Models still choose when to report a plan; a plain-text checklist is not treated as a tool event.

Current Claude models disable todo tools by default. Agent Studio passes the process-local `--settings` override `{"env":{"CLAUDE_CODE_ENABLE_TODO_TOOLS":"1"}}` for tool-enabled chats, as documented in the [Claude Code release notes](https://platform.claude.com/docs/en/release-notes/claude-code). It does not edit profile settings, and background title/usage requests retain their restrictions. The override also travels as a fixed CLI argument through the WSL bridge. The decoder follows the [Claude task tracking protocol](https://code.claude.com/docs/en/agent-sdk/todo-tracking).

## Code snippets

Fenced code blocks in replies and progress text use syntax colors for their declared language, including common aliases such as `js`, `ts`, `py`, `sh`, and `ps1`. Common languages such as JavaScript/TypeScript, Python, Rust, C/C++, C#, Go, Java, SQL, JSON, YAML, HTML/XML, CSS, and PowerShell are bundled locally, so highlighting works offline. Colors update while a reply streams and reappear in saved history. Inline code, unlabelled fences, unknown languages, and blocks longer than 65,536 UTF-16 code units keep plain code formatting. Highlighted output is sanitized before display; HTML snippets remain inert code until explicitly opened as artifacts.

## Artifacts and HTML previews

The **Source** tab uses the same syntax colors as chat for HTML and SVG, including embedded CSS and JavaScript, in both modal and side-panel views. It displays the original source as inert text and keeps downloads unchanged. Very large sources retain plain code formatting.

Complete `html` and `svg` fenced code blocks in an assistant reply get an **Open HTML** or **Open SVG** artifact card. Put an optional short title after the language on the opening fence. Open the card for the existing modal viewer, or use its side-panel button to preview beside the chat. The viewer header switches between modal and panel without restarting the live preview. Preview/Source, restart, and download are available in both. The panel leaves the composer usable on wide windows and becomes a right-side drawer on narrow screens; closing it preserves the draft. Drag its left divider to resize, or focus the divider and use arrow keys (Shift for larger steps), Home/End for its limits, and Enter or double-click to reset. Width is remembered locally and clamped to leave space for chat when the window or conversation sidebar changes. Changing conversations or leaving chat closes the viewer. Desktop downloads are written to Downloads with unique filenames, without overwriting existing files; browser clients use their browser's download flow. Up to 12 artifacts of 512 KB each can be previewed per reply. Incomplete or oversized blocks remain available as code. Source is retained in the original reply, so saved history, exports, and relay updates preserve the artifact without reading local file paths. Parent-authored progress fences are also retained when a later native workflow completion summary follows the artifact; identical source is deduplicated. Tool output, arguments, and child results are never used as artifact source.

HTML previews support inline CSS and JavaScript, SVG, and embedded data images. They use a separate constant renderer: the `studio-artifact` custom protocol in native apps and `/artifact-preview` in browser clients. Both enforce their own response CSP and `sandbox allow-scripts`, without same-origin privileges, application IPC, storage access, external resources, nested frames, forms, popups, or top-level navigation. The main chat continues to render only sanitized Markdown. The app sends source into the renderer once; it does not accept messages or commands from artifact code. The public route serves only the empty bootstrap and is never used to store source or credentials. See the [iframe sandbox reference](https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Elements/iframe#sandbox).

This is a self-contained artifact viewer. Raw JSX/React requiring a build step, CDN dependencies, local file URLs, and arbitrary websites are not rendered. Compile such output to standalone HTML with inline dependencies first. There is no in-app web browser or artifact source editor.

Windows WebView2 injects Tauri JavaScript helper objects into subframes even when Wry requests main-frame-only initialization. Their presence does not grant the sandbox access: the renderer CSP blocks the IPC fetch transport, the iframe remains an opaque origin, and Wry's native message listener belongs to the main frame. Native QA checks actual read-only app/plugin invocations in the preview as well as blocked parent DOM, storage, and network access; checking only whether a helper object exists would be misleading. No artifact-authored message is handled by the application.

## Image attachments

With Codex or Claude selected, click the paperclip below the message input, paste a screenshot, or drop image files anywhere in the chat area, including over the conversation. A highlighted drop area appears while dragging. Dropping adds the previews to your current draft and focuses the message input without sending. Click a thumbnail to inspect the image at a larger size; Escape or Close returns to the chat. Use its remove button to discard an attachment before sending. You can send images with or without a text message.

PNG, JPEG, and WebP files are supported, with up to four images per message and 2 MiB per image. Original image bytes are preserved; the app does not resize or recompress them. A conversation can contain 8 MiB of image data. Images remain visible after reopening the conversation, are included on retries and later turns, and travel with workspace exports and relay sync. Update both computers to an image-capable app version. The existing 20 MB workspace limit still applies; an attachment that would exceed it stays in the draft with an explanation.

Codex receives structured `image` inputs with data URLs through its app-server stdin; Claude receives base64 image content blocks using `--input-format stream-json`. Each image is labelled with its original message position. No attachment paths are passed to the CLI, and image bytes are excluded from the text prompt, background titles, token estimates, and activity cards. See the [Codex app-server reference](https://learn.chatgpt.com/docs/app-server) and [Claude streaming image input](https://code.claude.com/docs/en/agent-sdk/streaming-vs-single-mode). Gemini's current [Antigravity stream input](https://www.antigravity.google/docs/cli/headless/) accepts text blocks only, so its paperclip is disabled with an explanation.

Tauri's native file-drop interception is disabled to let the WebView deliver file drops to the chat. Drops outside chat cannot open the file in place of the app. Ordinary text drops keep their normal behavior. File contents stay inside the selected conversation and are delivered to its selected CLI/account through the existing transport. Provider-reported vision usage contributes to the usual context meter; the app does not estimate vision tokens from base64 length.

## Tools and activity

Tool cards show elapsed time, and a running collapsed group shows its longest running tool (parallel durations are not added). The execution host advances observed time once per second even while a tool is quiet; this is elapsed time, never a completion percentage or a claim that output is arriving. Claude `tool_progress` can advance the clock with `elapsed_time_seconds`; Codex completion `durationMs` is retained when available. Older activity without timing stays unknown. Unfinished operations retain their last recorded time with the existing stopped/unconfirmed outcome after the reply ends.

Claude heartbeats and Codex `item/mcpToolCall/progress`, `item/commandExecution/outputDelta`, legacy `item/fileChange/outputDelta`, and `item/commandExecution/terminalInteraction` add fixed **Progress reported**, **Output received**, or **Terminal interaction** indicators. Expanded calls show when the last signal was recorded. No message, output delta, terminal input, process ID, or arbitrary progress text is stored or displayed; a call's output is shown once it finishes, as described under [Commands, inputs and results](#commands-inputs-and-results). Signals must match an existing running operation and its parent/child attribution; Codex also requires the exact thread, turn, and item kind. Late signals cannot revive finished calls. Repeated same-second signals are coalesced and the existing 200-operation cap applies. Optional `elapsedMs` and `progress` fields survive workspace export, saved history, checkpoints, and relay reconciliation, outside prompt replay.

The interactive `command/exec/*` API is distinct from model-owned command execution: its processes and notifications are connection-scoped, without a chat/turn identity. Agent Studio does not create those sessions or offer terminal input/resize/stop controls. Unowned `command/exec/outputDelta` is ignored rather than assigned to the active chat. This feature is progress indicators only. Protocol references: [Codex app-server](https://learn.chatgpt.com/docs/app-server) and [Claude SDK tool progress types](https://app.unpkg.com/@anthropic-ai/claude-agent-sdk@0.3.220/files/sdk.d.ts).

Windows native verification on 2026-09-20 used `scripts/native-tool-progress.tauri.json` and `scripts/tool-progress-native-smoke.mjs` with real Claude and Codex logins in an isolated app. Both ran a twelve-second command, showed live elapsed time, and saved completion duration without its output; Codex also supplied output-progress signals. Claude's PowerShell task lifecycle now updates its command card instead of being mistaken for a sub-agent with a raw result. Controlled native-loop fixtures cover Claude heartbeats, quiet timers and stale/unowned Codex signals; decoder fixtures also cover MCP progress, legacy file-change output, terminal interactions, child attribution and late completion. Desktop/mobile browser tests cover expansion, drafts, stopped state and restored history. Live MCP progress and legacy file-change output were not induced against external servers; WSL and other operating systems were not exercised for this feature.

All chat providers run their tools with full access and without permission prompts. Claude and Codex chats can load the selected CLI profile's skills, search the web, and delegate work to sub-agents. Ask for these actions in the composer. Codex chat explicitly enables live web search and multi-agent tools. Claude loads its default built-in tools and configured project/profile resources. Gemini/Antigravity uses its default agent, configured resources, and `--dangerously-skip-permissions` in `accept-edits` mode; available tools depend on that CLI. Gemini's native skill catalog and MCP connection status are not inspected by Agent Studio.

Open **Model context → Skills** to inspect available resources. **Use in next message** inserts a skill request into the current draft and returns focus to the composer. Disabled skills cannot be selected. This action does not send a message or claim that a skill has loaded.

While a reply runs, reasoning, progress messages and tool activity appear inline in order. The chat follows new updates while you are at the bottom. Scrolling up holds your reading position, even just above the end; scroll back to the bottom to resume following. Expanding or collapsing Work history, tool groups, file lists, or reply details keeps what you see in place. Collapsing near the end leaves temporary blank space below the conversation instead of pulling it down; scrolling up removes that space, and it never lets you scroll further down than where you were. Expanding content past the end stops following it. The full conversation and expanded activity remain scrollable above the composer. The message input starts at three lines and grows with a longer draft until the composer box reaches half the window (four lines on phones), then scrolls; browsers without CSS `field-sizing` keep the fixed three lines. While you follow the end, a taller composer, a smaller window or an opened phone keyboard keeps the end in view; a reading position above the end stays where it is. When it finishes, a collapsed **Work history** item appears directly below the model title, above the final answer. Its header shows the label without activity counts or category filters. Expand it to review all reasoning, progress comments and tool calls in their recorded order. Replies with only reasoning or progress comments also have Work history; replies without recorded activity omit it. The disclosure starts collapsed again when reopening a saved conversation. Expanded history ends with a divider before the final answer. The startup notes "Starting the provider CLI" and "Connected to Claude" are hidden from live and saved activity.

Both live activity and expanded Work history group consecutive tool calls into quiet, collapsed rows that count what happened, such as **Read 12 files**, **Ran 2 web searches**, or **Edited 3 files, ran 4 commands, and used 2 tools**. Every kind of action in the group appears with its count, in the order it first ran. A file counts once however often it was read or edited, going by the paths the provider reported (up to 12 for each Codex file change); a call without a reported path counts as its own file. Sub-agents count once each, even when resumed, and commands, file and web searches, web pages, agent messages, skills, images, hooks and other tools count every call. Reasoning and progress comments stay visible between groups in their recorded order. Expand a group to see its individual calls, then expand a call for details. Incoming calls and revisions keep an opened group open; completion and reopening saved chats start collapsed. Group labels use reported action metadata, with **Used N tools** for unrecognized tools. A running group reads like **Reading 3 files and running 1 command**. When a call failed, stopped, or has an unconfirmed outcome, the label switches to nouns that do not claim success, such as **Edits to 1 file and 2 commands**. After the activity limit, the group says that later calls are not shown instead of counting them. Running groups have a spinner, and failed, stopped, or unconfirmed outcomes remain visible on the collapsed row, including sub-agent work. A long label wraps beside its icon and chevron, and a running group's progress text wraps before its label on narrow screens.

**Background work.** Claude can move work to the background: a command started with `run_in_background` (or moved there when a turn is interrupted or steered), a Monitor watch, or a sub-agent launched asynchronously. Its call returns to the model while the work continues, so history never shows it running. Groups count these launches as **started N background tasks** or **started N background sub-agents**, without a spinner or clock, and the call reads **In background** while the reply runs. A **Background work** toggle in the footer row of the reply that started the work counts what is still running; open it to list each item, labelled by the reported description (the call in Work history shows its command), with the execution host's elapsed time for commands and monitors. It stays after the reply ends: the executing computer keeps following each Claude task that the chat's CLI process still runs, including ones started by earlier replies, by observing the parked process's task notifications, the way live account usage is read. An entry leaves the card when the CLI reports its outcome, which then updates that call in the saved reply with the final duration, a Completed, Failed or Stopped mark, and a note that it ran in the background. Releasing the process (after 15 idle minutes, a changed launch setting, deleting the chat, or closing the app) ends the work it still ran, recorded as Stopped when the app is still open to save it. Until an outcome arrives, work still running when a completed reply ended, such as a dev server left for you, reads **Left running** and is not flagged as a problem; after a stop or failure it stays unconfirmed. The list is transient state on the executing computer: a window that loads later asks the host for it, and the Viewer shows background work only while its reply runs, with later outcomes arriving through sync. Only the CLI's explicit signals count: `backgroundTaskId` in a Bash or PowerShell result, `taskId` in a Monitor result, and `isAsync` in an Agent result. Codex reports no equivalent signal, so its commands keep their usual running state. The optional `background` flag on calls and sub-agents survives saved history, exports, and relay checkpoints. On 2026-09-24, with Claude Code 2.1.278 and Sonnet through the production runner, the opt-in `installed_claude_reply_waits_for_declared_tests_but_not_servers` test confirmed that a server launch stays running with the flag after the reply and that the declared tests finish complete with it, and `installed_claude_background_work_outlives_its_reply` confirmed that a job left running is reported complete by the parked process and that releasing the process stops the server. Monitor and background sub-agent results were checked against recorded CLI transcripts and decoder fixtures, not induced live; browser tests cover the card, history labels, stops and phone layouts.

Individual calls show running, completed, failed, stopped, or unconfirmed outcomes. Each operation has a stable identity; repeated searches with the same query remain separate inside their group. Headers identify the target when supplied. Call details include:

- Skill cards show an actual Claude Skill invocation or an observed direct read of a `SKILL.md` file. File reads do not establish that all instructions were followed. The context inspector remains an availability inventory rather than a reply's read history.
- Search cards show the query and provider-supplied HTTP(S) source links when available. Missing sources are stated explicitly; the UI does not manufacture links or turn a missing result into a successful search.
- Sub-agent cards show each child's name, reported state, task and result when supplied, plus attributed child tool activity. Child text and token usage do not overwrite the parent reply. Nested delegation retains the reported parent relationship.
- Each child's collapsed **Messages** disclosure retains its reported text during the run and in saved Work history. Claude chat launches enable `--forward-subagent-text`; completed text blocks are keyed by SDK UUID because multiple blocks can share an API message ID. Codex `subAgentActivity` establishes ownership and lifecycle independently of legacy collaboration calls, and child message deltas reconcile against completed items. Duplicate lifecycle events cannot revive a finished child; known child turns reject mismatched updates. Thinking, signatures and raw tool output remain excluded.
- Claude **Message agent** cards show the recipient, reported short summary and supported message type. **List agents** cards show bounded names/statuses/counts when the CLI supplies a structured `agents` result. Text-only directory output is not copied. A directory listing never establishes child ownership: listed peers may belong to other sessions. Message bodies are not displayed, and tool success does not assert that a peer acted on the message.
- Read cards show the file path and available line ranges/counts, then the lines read with their line numbers. Glob and Grep cards identify the pattern, folder, filters, and reported matching file paths/counts, then the matches. Tool search shows its query and returned tool names. Commands show their description, the command itself, structured file actions, working folders, and their output with its exit code. Edit and Write cards show that call's own recorded diff. Older calls whose metadata was not recorded show an explicit explanation; their missing details cannot be reconstructed.

### Commands, inputs and results

Every call row has an icon for what it does. Commands are classified from their text, past folder changes, variable assignments and wrappers such as `sudo` or `timeout`: the Git logo for `git`, a pull request for `gh`, a flask for test runs (`npm test`, `vitest`, `cargo test`, `pytest`), a hammer for builds and type checks, a wand for linters and formatters, a package for installs, and separate icons for dev servers, scripts, containers, downloads, remote shells, listings, reads, searches, deletions, copies, processes, waits and other agent CLIs, with a terminal for anything else. Tools use file, code, image, edit, new-file, folder-search, text-search, web, link, skill, agent, connected-tool (a plug; a window or camera for browser automation and screenshots), plan, question, workflow and hook icons. A group shows the icon its first kind of action shares, such as the Git logo for a run of git commands, or that kind's general icon when its calls differ. Group labels are unchanged; images read by Claude and Codex count as **viewed N images**.

A command row reads as its description when Claude reports one, with the command below it, or as the command itself. Codex runs each command through the shell's own command line, like `"…\powershell.exe" -Command '<script>'`; the row and the details show the script and name the shell. A configured CLI hook can prepend lines, such as a `node …\hooks\…` call; the row names the first line after them, and the details show them quietly above the command. Records show up to 8,000 characters of a command and 4,000 of pretty JSON arguments for connected (MCP), dynamic and unrecognized tools; a longer command or input is kept whole with the result and shown whole when the call is opened. Skill arguments and web page prompts become bounded facts; Agent Studio's own tools and Write/Edit bodies are never recorded as inputs.

Opening a call shows its command, input and result as one transcript: the shell and its prompt with the highlighted command, then **Output** or **File content** with the line count, **Exit code N** (green for 0, red otherwise), and **Copy** actions. File reads show line numbers from the reported first line and highlight by file extension up to 64 KB; **Standard error** appears separately, in red only when the call failed. Images returned by a tool (Claude image reads and screenshot tools, Codex image views, connected tools) load one by one as thumbnails that open full size, with their dimensions and size; tiny images are enlarged with crisp pixels. A long result starts in a scrolling box with **Show all**. Each stream arrives whole up to 512 KB; a larger one shows its beginning and end with a marker and **Show full output**, which loads up to 8 MB of each stream. Text is always shown as text, never HTML.

Results stay on the computer that ran the reply, complete and without size, count or age limits. They cannot live in the synced workspace: it is one JSON document, capped at 20 MB, that is saved whole after every change and uploaded or downloaded whole when it syncs, and a heavy local history produced about 35,000 shell calls averaging 2.2 KB and 4,500 image reads averaging 180 KB in 20 days. The provider decoder hands each finished call's result, exactly as the provider sent it, to its run's recorder, which writes one folder per call under `tool-output/<run id>/` in the app data folder: `stdout.txt` and `stderr.txt`, `image-<n>.<ext>` for each image whose own bytes identify PNG, JPEG, GIF or WebP, and `meta.json`, written last, with the exit code, first line, image list and any command or input the record had to shorten. ANSI escape sequences and carriage-return progress redraws are cleaned when text is shown, not when it is kept. A Codex image view names a file, which is copied once when the call completes (a regular file of a supported type; a WSL path through the distribution's own path translation). The activity record keeps only the result's size: lines, bytes, images, whether it has errors, the exit code and whether the provider shortened it.

A window reads a result when its call is opened: through a native command on the computer that ran it, or as a transient relay job to that computer from other devices and the Viewer, naming only the run's UUID, the call's activity ID and, for an image, its index. A full view stays within one 20 MB relay request. Results are never synced, exported, checkpointed into relay state, or replayed into prompts, and no request can name a file path. While a result is being written, a request waits for it. Each window caches a bounded set of results and images. Results are kept as long as a saved chat references their run: when the app starts and after each run, only runs that the saved workspace no longer references are removed (after an hour, so a reply still being saved keeps its results). Deleted conversations therefore lose their results at the next pruning; forks keep their run identities and share them on the same computer. Other devices can read results only while that computer is online. Calls recorded before this version have no command or result to show, and a missing result says that it was not kept, with **Retry** for temporary failures such as an offline computer.

Completed activity remains in saved chats and workspace exports. Interrupted replies show stopped or unconfirmed outcomes for operations that never supplied a terminal event. Intermediate progress messages remain inside the expandable history and stay out of the next prompt's conversation replay. Plain activity blocks from older chats remain readable. Markdown response exports use the final answer.

## Implementation and limits

Codex chat uses the installed CLI's **app-server** stdio protocol with a persistent thread for each app conversation. Follow-ups use `thread/resume` with the exact host-owned ID and `excludeTurns: true`; the CLI retains its native transcript without returning raw earlier tool output to the renderer. Legacy callers without a conversation ID remain ephemeral. The validated process working directory and selected CLI profile are unchanged; JSON requests and prompts travel on stdin. Restricted title generation still uses `exec`, and usage/context inventory queries remain separate. The app-server stream also exposes measured last-request context input and the resolved model. Only the parent thread's usage contributes to the reply's meter.

The installed Codex 0.153.4 `exec --json` stream omitted modern `subAgentActivity` events in a live probe. Its app-server stream supplied those events and the child messages directly. Ephemeral threads reject `thread/read` with `includeTurns`, so the adapter consumes live child notifications and never reads another session's files. Protocol shapes were checked against the installed CLI's generated TypeScript schema and the [Codex exec event definitions](https://github.com/openai/codex/blob/main/codex-rs/exec/src/exec_events.rs).

Configured CLI hooks may prepend a command before a PowerShell skill-file read. In that case Codex can report an unknown command action. The fallback recognizes direct read statements after the hook, tracks quoting so echoed examples do not count as reads, and supports the observed `-Raw`/`-LiteralPath` form. A command can also read an ordinary file before a skill; the skill search continues past the ordinary read and retains that other target in the details. These cases have regression fixtures; hook scripts and skill bodies are never inspected by the activity decoder.

Claude tool inputs can arrive in fragments. Finishing the input block only updates metadata; a corresponding tool result or task notification establishes the outcome. Complete child messages carry their parent tool identity, as described in [Claude's streaming documentation](https://code.claude.com/docs/en/agent-sdk/streaming-output) and [sub-agent documentation](https://code.claude.com/docs/en/agent-sdk/subagents). Selected metadata fields, commands, bounded arguments of connected and unrecognized tools, search source links, and child results are forwarded; results reach only the executing computer's store. Account payloads and configuration bodies are excluded.

The decoder retains up to 200 operations, 64 sub-agents, 64 progress messages, and 12 sources and metadata facts per operation, with a command of 8,000 characters and an input of 4,000 each. Reaching the operation/agent limit produces a visible notice, and updates to existing records continue. Text and inputs are bounded. Source links reject non-web schemes and embedded credentials. Result text is rendered as text, not provider HTML.

Optional child messages retain up to 16 entries, 4,000 UTF-16 units each and 16,000 total per child, with a visible truncation notice. Existing entries continue accepting completion at the limit. Partial Codex messages left at stop/failure are labelled incomplete. All child detail remains outside parent text, token usage, reasoning, plan and prompt replay. Older saved activity without messages remains readable.

Activity records are an additive optional field inside workspace v3 activity blocks. The execution host checkpoints them, relay delivery retains the newest revision per operation, and same-run reconciliation merges progress independently of answer text. Both app installations and the relay should run the updated version to preserve this metadata and support the expanded event envelope.

Claude progress resets at each streamed message start and reconciles against the corresponding assistant message identity; its final result is separate. Its reported child-agent identity also keeps resumed child sessions from inflating the sub-agent count, while preserving each invocation's task and tools. Codex agent-message items retain their identities, with `final_answer` phase used for the final response and the completed turn providing a fallback for older phase-less events. A final message already present in the progress stream is shown once. This avoids concatenating commentary into the final answer or losing it when the provider replaces its accumulated text.

## Files edited summaries

Each finished assistant response has **Files edited** beside elapsed and cumulative AI time in a compact footer row, followed by the reply's plan, workflow and background work toggles when it has them. All of them start collapsed. Clicking a label opens its panel and closes any other; clicking the open label collapses it. File scope and list expansion survive panel switches. Each scope initially shows five files, with Show all files and Show fewer files controls for longer lists. The routine response-scope, combined-chat, and coverage notes are omitted. **This response** shows its recorded file edits; **All chat changes** shows the combined result of recorded edits across the entire conversation, including later responses. Each file expands into a line-numbered code diff with additions and deletions. Repeated edits are composed rather than counted again, and fully reverted changes disappear from the combined view. The UI does not modify files. Individual diffs start collapsed inside subtle bordered file rows. Added marks a newly created file in the selected scope and omits per-file line-change counts and hunk coordinate headers. Summary line-change totals cover existing files only; Edited marks a change to an existing file. A file created earlier and edited later remains Added in All chat changes. Paths are relative to the selected project, or a shared recorded directory when multiple absolute paths establish one; full paths remain available on hover, and unrelated roots stay explicit.

Codex native file-change completions and successful Claude Edit, MultiEdit, and Write results supply the source. This is a record of reported edits, not a scan of the working directory: shell commands, external edits, unsupported tools/providers, and older replies can lack diffs. A discontinuity, unavailable source, or recording limit is shown explicitly rather than reconstructed from a guess. Older replies retain confirmed filenames from saved edit activity while marking their missing diffs unavailable. Common credential files omit their diff bodies. File text is displayed as inert text and is never executed or read from an arbitrary path.

Optional `message.fileChanges` snapshots are revisioned and bounded to 100 edit operations, 32 files per operation, and 1 MB of serialized data (the native recorder reserves headroom at 900 KB). A hunk has validated original/updated line ranges and signed lines; incomplete hunks are never silently truncated into valid-looking source. The combined viewer bounds each file's line span to 100,000 lines and shows up to 200 files. Snapshots survive local history, workspace exports, remote delivery, and same-run checkpoints; they are excluded from model prompt replay, title generation, and tool activity. Older clients that omit this field cannot erase a matching locally retained run's snapshot.

## Unsent drafts

Text typed in the composer but not sent stays with its conversation. Switching chats, opening Connections or Settings, forking, following a notification, reloading, and closing Agent Studio keep it, and reopening the chat restores it, including a chat that moved to History at startup. New conversations keep a draft per location: each project folder and each computer's Standalone location has its own, so the sidebar **+** for a folder or Standalone reopens what you left there. Changing a new chat's folder or computer carries its text along; when the destination already has a draft, that text stays first, followed by a blank line and the carried text. `/new` moves its remaining text into the new conversation the same way. Sending, steering, or queuing the text removes the draft (queued messages stay session-only), as does clearing the composer. Deleting a conversation deletes its draft, including a deletion synced from another device.

Drafts belong to the device and are never part of the workspace, exports, or relay sync. The desktop app saves their text and selected mention identity in `drafts.json` in its app data through asynchronous native commands, at most every 300 ms while you type and immediately when the window loses focus, is hidden, or closes from the title bar or for an update. Attached images stay with a draft while the app is open but are not saved. The Viewer keeps drafts in browser storage scoped to its authenticated workspace; signing out, session expiry, or a workspace change removes them with the other cached data, and tabs of the same workspace merge their saved drafts per conversation, keeping the newest. Up to 100 drafts and 2 MB are saved, most recently edited first; a draft longer than 300,000 characters stays only in the open window. Restored mentions stay selected only while the chat, account, and folder still match; otherwise they must be chosen again, as after any other account or folder change. An unreadable drafts file is reported and replaced by the next save.

Verification: `src/lib/drafts.test.ts`, `src/lib/browser-workspace.test.ts`, `tests/drafts.spec.ts`, the Viewer case in `tests/private-workspaces.spec.ts`, and Rust `drafts::tests`. `scripts/drafts-native-smoke.mjs` drives an isolated build (`npx tauri build --debug --no-bundle --config scripts/native-drafts.tauri.json`, WebView2 debugging port 19682) launched through `npm run start:windows -- -Executable`: it closes the window from the title bar right after typing, relaunches, and checks both drafts and `drafts.json`. It seeds its chat directly and never sends a provider request.

## Message queue

While a reply is running, the composer keeps accepting input. Enter or the queue button holds the message for that conversation and lists it above the composer, in order, with a control that returns it to the draft. Up to eight messages can wait. When the reply completes, the first queued message is sent automatically with its images and any selected skill; each later one follows its own completed reply. If the reply is stopped or fails, or the composer cannot send when the reply ends, the queued messages return to the draft, oldest first and ahead of any text already typed, with images kept up to the four-per-message limit. Queued messages live only in the open session: they are never saved, exported, or relayed, and they do not steer the running turn. See docs/NATIVE-SESSIONS.md for the persistent process behind this.
