# Workflows, visualizations, artifacts, plans, and tools

## Optional project folder

Choose a computer to select its agent, account, model, and reasoning and start chatting. A project folder is optional: computer-scoped new chats start as **Standalone**, and the Folder picker always offers **Standalone** to clear a draft's project folder. Clearing the folder preserves the draft, attachments, and model settings. Choosing a recent folder or browsing still adds project context; existing conversations keep their fixed computer, folder, and account.

New Standalone chats get a persistent working folder of their own on the selected execution computer. Native hosts use app-data `standalone/<conversation UUID>`; managed WSL uses `~/.local/share/<app identifier>/standalone/<conversation UUID>` in the selected distribution. Replies, retries, and app restarts reuse the same folder. Context and skill inspection use that chat's folder and keep separate caches for Standalone chats. Tool access and the selected CLI profile's global instructions, hooks, skills, and integrations remain enabled.

Existing chats retain their previous shared runtime to preserve file references and native session continuity. Host-local versioned bindings record the choice; imported saved history without a binding also retains the legacy runtime. New chats do not copy files or instructions from it. Chat deletion retains generated files and native transcripts. Working folders are not sandboxes: chat agents retain their configured full filesystem access.

The saved conversation retains its computer and environment even though no project path is sent to the provider. Desktop, managed WSL, and paired Viewer use the same selection and routing rules; unavailable or signed-out connections still cannot send, and another computer is never used as a fallback. Working-folder contents and bindings stay on the execution host, outside workspace exports and relay sync. Background title generation continues to use its separate restricted runtime.

## Folder icons

Each project folder gets an icon of its own in the sidebar's Active and History folder groups, on the toolbar's Folder control and beside each folder in that control's list. The first conversation started in a folder without one, once its title request finishes, asks the same small model that names chats (**Claude Haiku**, **GPT-5.6 Luna / Low** or **Gemini 3.8 Flash / Low**, on the conversation's account) to choose from a catalog of 338 [Lucide](https://lucide.dev) icons in ten categories: software and tools, AI and data, web and security, devices, games, creative work, learning and health, business, home and travel, and nature. The model sees the folder's name after up to two of its parent folders (`Unreal Projects/Bluevox`) and up to 1,000 characters of the first message, never the folder's contents, and runs restricted in the title runtime like a title. Only a name from the catalog is kept.

The choice is saved with the workspace (`folderIcons`), so every computer and the Viewer show it, and later chats in the folder never ask again. If the choice fails, the folder keeps the plain folder mark and the next chat there after a reload tries again. Standalone chats keep their chat-bubble mark. A device on an older release keeps the icons it holds while syncing with an older relay that drops them, and shows the folder mark for icon names its catalog does not have yet.

## Account colors

Each account has a color of its own, so accounts with similar names can be told apart without reading them. Where a computer has several accounts of an agent, the Agent picker lists each as the agent's glyph on the account's color, the Agent control shows the selected account's mark in place of its bot icon, and a new chat's welcome shows the mark large and names the account. Connections puts the color before each account's name, and a chat that changes account says so in the color of the account it changes to: in the **Next message** hint, then in the **Switched to** notice above the reply. An agent with one account on a computer keeps its own mark. Reply headings and the sidebar are not marked.

An account takes a color by itself the first time the app sees it: the first of ten (blue, orange, green, pink, violet, yellow, teal, red, brown, gray) that no other account has. A workspace with more accounts than colors repeats them where it shows least: an account takes a color that no account on its computers has, its own agent's accounts first, so the accounts one Agent list shows together still differ. **Connections → Manage account → Color** changes it. Colors are names from that palette, each with a value for the dark and the light theme; the app keeps no custom colors.

The colors are saved with the workspace (`accountColors`), so every computer and the Viewer show the same ones, and an account keeps its color when others are added or removed. Two computers that each met their own accounts before they were paired started with the same colors: the one that syncs second gives its accounts better ones where there are any, once. A color you chose is never replaced by one an account took by itself, and of two choices the later wins. A device on an older release keeps the colors it holds while syncing with an older relay that drops them.

The toolbar gives the Agent control room for a long account name (up to 280px, 220px in windows up to 1100px wide), and a name that still does not fit is cut short with the account's color beside it.

## File and app mentions

Type `@` anywhere at a word boundary in a Claude or Codex draft to search files in the selected working folder. Type `$` in Codex to choose an accessible, enabled app. Arrow keys navigate; Enter, Tab or touch inserts the choice into the draft, and Escape dismisses. Selection never sends a message. Paths with spaces are quoted, and surrounding draft text is preserved. A new Standalone chat needs its first message to create its working folder before file search is available.

Codex uses the installed CLI's `fuzzyFileSearch` and paginated `app/list`. Its chat process enables stable `mentions_v2`; selected files and apps become structured `mention` inputs alongside the visible text. Claude receives literal `@path` text, with name-only discovery on its selected host and no Codex dependency. Claude search omits hidden and generated directories and skips symbolic links. File pickers list every match the search returns, and the app catalog every accessible enabled app; results left partial, such as by a folder that cannot be read, are labelled. No file contents, app URLs, tool definitions or credentials enter discovery results.

Queries use the normal selected-connection transport, including managed WSL and Viewer jobs. They validate the folder/connection on the owning host, run separately from parked chat processes, and never start a model turn or install, enable, authenticate or invoke apps. App discovery suppresses `app/list/updated` because its unpaginated directory includes large icon payloads; paginated responses supply the picker, through the whole catalog. App metadata is cached only inside the composer for up to one minute; account, folder and inventory changes invalidate it. Late results cannot replace another selection.

Selected Codex references, however many, are saved with their user message and retained through exports, relay, queue restoration and retries. Only the current submission becomes native mention input; earlier references remain historical text. Deleting or renaming a token drops its selected identity. Account/folder changes require selecting retained mention text again, and selected native mentions use Queue message during a running reply. Settings navigation preserves their draft identity. Plain typed `@path` text remains available without autocomplete.

`tests/mentions.spec.ts` covers draft insertion, native identity, Claude text, stale discovery, failure handling, Settings navigation, queue restoration and mobile layout. Rust tests cover discovery and current-turn input mapping. The opt-in real-provider smoke is `node scripts/mentions-native-smoke.mjs`, using `scripts/native-mentions.tauri.json` with its own absolute Cargo target and CDP port 19661. Build from Codex with `npm run tauri dev -- --config scripts/native-mentions.tauri.json --no-watch -- -- --check-startup`, then use the guarded Windows launcher. The startup probe exits without leaving a modal rejection window that could be mistaken for a running app. The smoke uses disposable files and existing CLI sign-ins, consumes model usage for file-read checks, and only inspects app availability; `--apps-only` retries the catalog without another model reply.

Live Windows verification on 2026-09-20 confirmed Codex 0.153.4 and Claude file search, quoted-path insertion and real file reads through the native composer. Codex structured reference metadata was saved, and Claude kept literal text. Native Windows `app/list` returned service HTTP 403; the same installed CLI returned accessible apps when invoked from the Codex task environment. The picker reports the denial without exposing the upstream HTML, changing credentials, or bypassing network policy. Native app-catalog success remains unverified in that environment; app selection and structured input are covered by controlled browser and Rust tests. Results and screenshots are under `artifacts/mentions-native/`.

## Reasoning display

Claude thinking text and Codex reasoning summaries appear where they happened: in the live activity while a reply runs, and in **Work history** after a completed, stopped, or failed reply, between the progress comments and tool groups around them. Each block is muted prose beside a brain mark, readable without opening another disclosure and distinct from progress comments and the final answer. Markdown and code highlighting use the same sanitized renderer as answers, and links open through the same safe-source check as progress comments. A reply whose only activity is reasoning still gets a Work history. Replies without reported reasoning show none, including older history.

The decoder accepts parent Claude `thinking` blocks and `thinking_delta` events, Codex app-server `reasoning` items and `item/reasoning/summaryTextDelta` / `textDelta`, and legacy Codex exec reasoning snapshots. Codex turns request automatic summaries. Indexed parts preserve paragraph boundaries, and complete snapshots replace streamed content by identity without duplication. Claude Code prints each content block of a message as its own `assistant` line, so a block's array index in a snapshot is not its position in the message: once a message's thinking has streamed (chats pass `--include-partial-messages`), its snapshot lines add no reasoning, and snapshots without a stream are numbered by position across the message's lines. Empty thinking blocks, such as the signature-only block that opens Fable messages, reserve no item. Replies saved before this was fixed hold each streamed Claude thinking block twice under the same message (`message:1` from the stream, `message:0` from the snapshot); the timeline shows identical text once per message. When Codex supplies both a summary and content, the summary is displayed. Signatures, encrypted or redacted payloads, child messages, and reasoning from another Codex turn are excluded.

Reasoning is saved as separate revisioned blocks, retained through workspace exports, relay events and same-run checkpoints. Every item a reply reports is kept whole. It never becomes final-answer text, prompt replay, title context, or an executable artifact.

Provider availability matters: live Windows checks on 2026-09-19 with Claude Code 2.1.277, Sonnet 5 and Sonnet 4.6 returned no thinking text despite reported thinking tokens. No disclosure is fabricated from tokens or signatures. This matches the [upstream headless thinking-display report](https://github.com/anthropics/claude-code/issues/82896). Claude's decoder and process/event path are covered by controlled thinking streams; live Codex GPT-6-Astra supplied a summary that streamed, rendered, and survived save/reload. The opt-in native check is `scripts/reasoning-native-smoke.mjs`, with results in `artifacts/reasoning-native/results.json`. Update the relay and Viewer alongside the native app to accept the new block type and expanded event envelope.

## MCP elicitation

Claude and Codex MCP servers can request input during a reply. The chat shows the server name and a form, or a URL flow with **Open page** and a separate **Continue** confirmation. **Decline** and **Cancel** return their distinct protocol actions. Defaults may populate fields, but nothing is submitted or opened automatically. Opening a URL or accepting its request does not confirm that authentication or another external action succeeded; the MCP server owns that confirmation. Form values are sent to the requesting server, so secrets belong in the server's external URL flow.

Supported forms use MCP's flat object schema: strings, finite numbers, integers, booleans, single-choice enums (including `oneOf` titles and legacy `enumNames`), and arrays of enum choices (including `anyOf` titles). Required/optional fields, defaults, length/numeric/item bounds, email/URI/date/date-time formats and Rust-compatible patterns are validated on the native host. Unsupported validation keywords, nested objects, invalid patterns and secret formats fail explicitly instead of silently dropping constraints. A reply's requests, a form's fields, a field's choices, text values and responses have no count or size limit. URL navigation accepts HTTPS and loopback HTTP only, without embedded username/password credentials.

The adapters handle Claude's snake_case `elicitation` control payload and Codex's `mcpServer/elicitation/request` form/URL union. Codex's stable `tool_call_mcp_elicitation` flag is enabled by the installed CLI; the extended OpenAI form capability is not advertised. Codex requests must match the bound parent thread and, when reported, the active turn. Claude rejects explicit child attribution and foreign session IDs; its current control schema does not include a tool-use ID for stronger child correlation. Responses go through structured stdin on the originating process, with native write acknowledgement. Cancellation, provider withdrawal, completion, process loss and stale connection/run identities close the live input channel. The normal composer draft and full-access execution are preserved. Codex requires the granular approval policy with only mcp_elicitations enabled: its never policy silently declines elicitation before emitting a request. Ordinary sandbox/rule/skill/permission approvals remain disabled. The host preserves full-access behavior for Codex-marked empty MCP tool-call approvals, but never automatically fills a nonempty form or accepts an explicit user-input, sensitive-action or strict-review request.

The native app and paired Viewer save only revisioned receipts containing request/run identity, server name, mode and outcome. Request messages, form definitions, URLs and responses remain transient and are excluded from workspace storage, exports, prompt replay and checkpoints. The Viewer fetches a pending request from its exact host/connection via authenticated relay jobs, including for desktop-started chats. Relay job bodies remain in the relay's in-memory job queue; they are not written to workspace files. Closed or restored history never recreates a provider input channel. Update the native app, relay and Viewer together.

`tests/elicitations.spec.ts` covers desktop and narrow-screen UI, failures/retries, explicit URL opening, cancellation, draft preservation and a real paired Viewer/relay roundtrip. Rust tests exercise both production stream runners with child-process protocol fixtures for form/URL accept/decline/cancel, plus validation, privacy and stale/withdrawn request rejection. An opt-in installed-CLI check is available with `cargo test --manifest-path src-tauri/Cargo.toml --lib elicitation_installed_clis -- --ignored --nocapture`; it uses a disposable MCP server and synthetic input, uses existing CLI authentication, and consumes model capacity.

Live Windows verification on 2026-09-19 with Claude Code 2.1.277 accepted a real MCP form and continued the reply, including through the native WebView and Tauri transport. Codex 0.153.4 accepted form input, declined URL input, and continued its real MCP call through the production runner. That CLI rejects URL mode before delivering a control request (`Client does not support URL-mode elicitation requests`); the Claude URL adapter is verified with a controlled native protocol stream until the CLI supports forwarding it. See the [upstream URL elicitation report](https://github.com/anthropics/claude-code/issues/88075). The repeatable native UI smoke is `node scripts/elicitation-native-smoke.mjs`, using `scripts/native-elicitation.tauri.json`, a separate Cargo target, Vite port 1461 and CDP port 19671; launch through `npm run start:windows -- -Executable <isolated binary>` after the `npm run tauri dev` build. Results and the reviewed form screenshot are under `artifacts/elicitation-native/`.

## Agent questions

Codex and Claude can ask questions during a running reply. A **Your input is needed** form appears in the conversation. Choose an option, select several when allowed, or type your own answer. **Send answers** returns all answers to the same running agent. No option is preselected or submitted automatically. **Skip questions** explicitly tells the agent you declined to answer. The normal message draft stays intact, and a delivery error leaves the form available to retry.

Multiple questions appear one at a time, with a **Question 1 of N** counter. Use the numbered buttons to jump directly to any question, or **Back** and **Next** to browse, even before answering. Checkmarks identify answered questions; you can revisit and edit them before submitting. Choices and text stay intact between steps. Each question uses radio buttons for one answer or checkboxes for multiple answers, according to the agent's question definition. Only **Send answers** on the final step requires and submits the complete set; **Skip questions** on any step skips the whole set. Single-question forms keep their direct submission action.

Claude writes a question call's input for a few seconds before Claude Code invokes the tool (a four-option question took Opus 2.2 seconds, after which the call arrived within milliseconds), so the form appears as soon as the call begins and fills in as Claude writes: the question text, then each choice. Until the call is recorded it reads **Writing…**, its controls cannot be used, and its live row reads **Writing a question**. The recorded question then takes over the same card in the same place, ready to answer, and the row reads **Waiting for your answer**. A call that ends without a question, such as one with invalid input, removes its card. The draft comes from the parent call's streamed input (`providers/questions/draft.rs` reads each prefix of the JSON; `src/lib/question-drafts.ts` holds it per reply in the window): it is display data only, never saved, synced, exported, answered or replayed. A remote run's relay job carries the latest draft of each call, so a Viewer that started the reply sees it too; a device that only follows a chat through sync sees the question once it is recorded. Codex reports a call only with its complete arguments (its app-server streams no tool input), so a Codex question's form appears with its call.

The form works in the native app and the paired Agent Studio Viewer, including for questions in a chat started on the desktop. Viewer answers go through the private relay to the connection that owns the original run; they do not start another reply. Submitted or skipped forms disappear without a **Your answers** card. Answer data remains in saved history and JSON exports and supplies earlier conversation context on later turns. Stopping a run or losing its process makes outstanding questions unavailable. Reopening saved history cannot revive an old provider process.

Question history is retained by reply/run identity and request revision even when an older relay or client omits it from a sync response. An omitted field cannot dismiss a waiting local form or erase a submitted answer; newer answer/cancellation revisions still win, and conversation deletion remains effective. Keep the relay and Viewer updated so they can store and display questions themselves.

A reload of the window stops nothing (2026-10-19): the reply runs on, including a provider waiting silently for an answer, and the reloaded window follows it again with its question, answered there as before (docs/NATIVE-SESSIONS.md). Navigation between chat, Connections, and Settings keeps the reply running too. A restart of the app interrupts it, and interrupted history does not restore the old answer channel or automatically replay the request.

The adapter supports Codex's `item/tool/requestUserInput` (including nonblocking requests) and Claude's `AskUserQuestion` permission callback. Both providers also receive `studio_ask_user`: a Codex dynamic tool and a Claude in-process SDK MCP tool, available in ordinary full-access chat modes. Claude question callbacks do not introduce approvals for unrelated tools. Integration follows the [Codex app-server request protocol](https://learn.chatgpt.com/docs/app-server) and [Claude Agent SDK user-input protocol](https://code.claude.com/docs/en/agent-sdk/user-input). Antigravity's currently installed print interface does not expose a supported interactive question/answer channel, so its questions remain ordinary conversation text.

Question and answer data are escaped text, not HTML or application commands. Only parent calls are accepted. Questions per call, choices, text, calls per reply and answers have no count or size limit. Secret-input requests are rejected; this form is not a credential-entry interface. The native registry validates the original run, account connection, request identity, and complete answer before writing structured data to the provider's owned stdin. Duplicate submissions cannot send another response. Claude and Codex runs, including pending questions, have no Agent Studio elapsed-time cutoff. Cancellation, startup failure checks, and ongoing relay heartbeats remain active; abandoned remote hosts still expire promptly. Update the relay and clients together to preserve the optional `questions` field and enable answer jobs.

Verification: `src/lib/questions.test.ts`, the Rust `providers::questions` tests, `tests/questions.spec.ts`, and `scripts/questions-native-smoke.mjs`. Native QA requires the isolated `scripts/native-questions.tauri.json` app, a separate Cargo target/WebView2 profile, and debugging port 9497. The native script checks the exact app identifier before touching its disposable workspace, then tests real provider calls and UI answers without accessing CLI credentials.

## Input templates

Choose **Templates** beside the composer, then **New template**. Give the template a name and write your reusable prompt. Add custom inputs with **Add input field** or type placeholders such as `Review {{change}} with a focus on {{areas to check}}`. Field names can contain letters, numbers, spaces, underscores, and hyphens. Repeating a field name reuses its value; prompts without fields are supported too.

Choose a saved template, fill each input, and review the message preview. **Insert into message** appends the filled text after the existing draft, with a blank line between them, and returns focus to the composer. It does not send, start an agent, restore a History conversation, or alter attachments and chat settings. Edit the draft as usual and press Send when ready. Cancel or Escape leaves the draft unchanged. All values are plain text and can span multiple lines; values containing placeholders or HTML remain literal text.

The library supports search, editing, and confirmed deletion. Definitions are stored in the optional `inputTemplates` field of workspace version 3, included in JSON exports, and synchronized through the existing private workspace relay. Filled values remain temporary until insertion and are not saved as template defaults. Signing out or changing workspaces clears the dialog and its values. Concurrent template edits retain a named conflict copy; an editor whose saved template has already changed on another device must reopen it before saving. Templates, their names, text and fields, and the message they fill have no count or length limit. Update the relay and paired apps together to retain the new optional field.

Verification lives in `input-templates.test.ts`, `tests/input-templates.spec.ts`, and `scripts/input-templates-native-smoke.mjs`. The native script requires the isolated `scripts/native-input-templates.tauri.json` app identity and WebView2 debugging port 9481 (`TEMPLATE_QA_PORT` can override the port). Use a separate Cargo target and WebView2 data folder. Wait for the Templates button to become enabled after reload: the chat shell renders before the workspace load completes, and its presence alone previously allowed the test to open an empty library. The button now stays disabled during loading. Native QA exercises actual save/reload and draft insertion; it deliberately makes no provider request.

The shared input focus ring extends 6px beyond a control (2px outline plus 4px offset). Keep at least that much space inside the template body's scroll boundary; its former 4px side padding clipped both sides of focused inputs. The body now uses 8px padding and scroll padding. Check focused search, editor, and fill inputs on desktop and narrow layouts, including controls scrolled into view.

## Interactive visualizations

Ask Codex or Claude to visualize a process, chart, comparison, or simulation. Both can call **visualize** to put an interactive HTML/SVG fragment between the paragraphs it explains. Visuals share the reply's typography, colors, and transparent background, with no enclosing card or repeated title bar. Their height follows their content, including interactions and narrow layouts. Restart, expand, and side-panel controls appear on hover or keyboard focus and stay visible on touch layouts. The larger viewer offers source inspection and downloads. Controls inside a visual stay local; follow-up questions go through the composer.

After accepting a visual, the tool tells the agent to place `<!-- visualize:ID -->` on its own line between blank lines in the explanation. Only a standalone top-level marker for an accepted visual positions it; quoted/code examples cannot create previews, and repeated markers do not duplicate a frame. Older replies without markers retain their visuals below the prose. Markers and exact source survive history/export/relay without changing the workspace schema. Authors should use natural-height fragments, the supplied CSS color variables, and no outer background, dashboard shell, or repeated prose heading.

Agent Studio supplies this tool through Codex app-server dynamic tools and Claude Code's SDK MCP stream (`mcp__agent_studio__visualize`). It uses the installed CLI and selected account, computer, and folder. This is an Agent Studio integration, not an embedded Codex or Claude chat application. Codex's installed visualization skill can guide content creation, but must submit its fragment through the tool rather than emitting a local-file reference. Agent Studio does not read files named in responses. The tool is not enabled for Gemini, titles, or other restricted background queries.

The tool takes `id`, `title`, and `html`. Reusing an ID updates that visual in the current reply. Only validated parent submissions are displayed; Claude submissions also require successful matching tool results. Visual source and revisions survive history, exports, and relay checkpoints. Completed visual source is provided as earlier context for follow-up edits, without replaying tool calls. Visual source has no size or count limit, per visual, reply or request history.

Visuals use the artifact sandbox with inline CSS/JavaScript, SVG, and data images. External scripts, styles, network calls, nested frames, local file access, application commands, and host follow-up APIs are unavailable. Include required data and code directly. The bundled chat font loads as data; it needs no network access. The renderer reports only its height to the owning frame, checked by window identity and a per-render token, and the frame takes that height, at least 24 pixels, however tall the content. It cannot issue application commands. Source inspection and downloads retain the original submitted source. Reloading restores the saved visual, resetting any temporary interactions such as a slider position.

Integration references: [Codex dynamic tool calls](https://learn.chatgpt.com/docs/app-server), [Claude Code custom tools](https://code.claude.com/docs/en/agent-sdk/custom-tools). Claude Code's SDK requires bidirectional stdin for custom tools; Agent Studio retains it until a result arrives with no delegated agent/workflow tasks pending, then waits for the owned process to exit. Persistent background shell tasks do not hold that input open.

## Files a reply shows

Codex and Claude can show a picture, a 3D model, a table, a document, a video or audio that already exists on the computer running the conversation — a render, a screenshot, a plotted chart, a diagram, a character they just generated, a CSV export, a workbook, a written report, a screen recording, a narration or a piece of music — instead of only naming its path. Both call **send_files** with a stable `id`, the absolute `files` paths, and an optional one-line `caption`. An accepted image appears inline in the reply as a thumbnail up to 320 pixels tall with its dimensions and size, and the caption sits below the group. Consecutive images form a gallery instead: rows of equal height that fill the reply's width, each tile the shape of its image so none is cropped. The rows are chosen from the images' reported shapes alone — two or three screenshots share a row, five make rows of two and three — so the gallery needs no measuring and nothing moves as the pictures load, and a row of tall images stops at 320 pixels. Single images sent one call at a time and placed side by side, with no prose between their markers, join one gallery too, each keeping its own call's caption under its tile; a call that sent several files keeps its gallery and caption to itself.

Clicking an image, or **Expand** on a model, a table, a document, a video or a sound, opens the file viewer. It covers the whole window (requested 2026-10-21: "make it open on the entire window not just a modal, with a backdrop covering the entire screen") on a dark scrim in every theme, as photographs are viewed, with the file's name, details, place and caption at its top left and **Close** at its top right, over a shade that keeps them readable over a zoomed picture. It connects every file the conversation's replies show, in the order the chat shows them: the **Previous file** and **Next file** arrows at its sides, the Left and Right arrow keys and, on an image seen whole, a horizontal swipe or drag step from one file to the next across groups and replies, while the heading names the file, its dimensions or format and size, and its place (3 of 11), with its group's caption below. An image covers the window, fitting whole within the room its controls leave (the heading, the arrows and the zoom controls floating at its foot), and zooms where the wheel turns, with a two-finger pinch, a double click or tap where it lands, the zoom buttons or + and -, from the whole image to 1,024 times it (requested 2026-10-21: "allow higher / any zoom level"), far enough that one pixel of the largest photograph covers more than the window; the point under the pointer stays there however deep, and the level reads as a percentage of its pixels up to ten times them and as a multiple past that (850×). **1:1** (or 1) shows its own pixels and **Fit to window** (or 0) the whole image again. A zoomed image pans by dragging, under the controls to the window's edges, and the arrow keys pan it instead of stepping; once zoomed past half again its whole size, any point of it, a corner included, can be brought to the middle ("walk more freely"), while just past the whole image it still covers the room from edge to edge, giving way gradually as it zooms, so nothing jumps. Past twice its pixels it is drawn with crisp pixels, which stays smooth at any depth in WebView2 and WebKit. The viewer reads the neighbouring images ahead, and shows an image the window already read at once, so stepping and opening show them without a moment's wait. It closes with Escape, **Close** or a click on the scrim around the file, beside a picture, a model's or a comparison's surface, a table, a page or a player, returning focus to what opened it; a press must begin on the scrim and end there, so a drag that begins on the file, such as one panning an image, never closes it, and a click on a picture never does. A click on the heading's empty middle passes through its shade to what lies below. A press beside a picture still arriving closes the viewer too. It also closes when its file's reply leaves the chat, with the conversation or on leaving chat. On a phone the arrows sit beside **Close**, above the file, which takes the screen's whole width.

After accepting a call, the tool tells the agent to place `<!-- files:ID -->` on its own line between blank lines where the files belong in the explanation, exactly like a visualization marker: only a standalone top-level marker positions a group, a repeated marker does not duplicate it, and a group whose marker never arrives stays at the end of the reply.

A glTF, GLB, OBJ, STL or FBX model opens in a viewer in the reply instead: drag to turn it, drag with the right button, with Shift held or with two fingers to pan it (or focus it and use the arrow keys to turn it and Shift with them to pan, with + and - to zoom and Home to reset), use the zoom buttons, and reset the view. Panning moves the point the view turns around, as far beside and beyond the model as the reader drags it (requested 2026-10-21: "walk more freely"), up to fifty times the model's reach from its centre so Reset always finds it again; a drag back moves the view at once, and Reset returns to the starting view even while a drag still glides. The wheel and a pinch zoom towards the very point of the model under the pointer, which stays under it: that point is read from the depth of the one pixel there, which the GPU draws in a moment however many triangles the model has, and off the model the zoom goes towards the plane facing the camera through the point it turns around. The camera comes from a hundred times the model's reach down to a hundred-thousandth of the model (requested 2026-10-21: "allow higher / any zoom level"), the near and far planes following it so a detail stays whole and surfaces never flicker into one another, and the zoom buttons and + and - zoom towards the middle within the same bounds. A double click on the model flies the view to the point it lands on, which the view then turns around, halving the distance to it (at once under reduced motion); one beside the model changes nothing. Shift with an arrow key moves the view by a tenth of its size the way the arrows move a zoomed image, so Shift and Right shows more of what lies to the right. Animations inside the file play there, with a pause control and, when a file carries several clips, a picker; a rigged character sent straight from a generator walks in the reply. Pausing holds the pose the animation reached, animations never start by themselves when the system asks for reduced motion, and an animation alone draws at most 60 frames a second. The inline viewer spans the reply's width in a 16:10 stage, between 220 pixels tall and the lower of 560 pixels or 70% of the window. **Expand** opens the model in the file viewer at full size with wheel zoom, beside the conversation's other files, while the inline one keeps its place in the chat, gives up its scene until the viewer moves on, and gets focus back on close. In the chat the wheel zooms a model once it is clicked (requested 2026-10-21: "if I click on the 3D view it focus on it and allow to scroll to zoom and if click elsewhere it focus on the chat and the scroll scrolls the chat"): a click on the model or one of its controls gives its card focus, which the card's border shows in the focus colour, and from then on the wheel over the model zooms it; a click anywhere else, or focus moving on, gives the wheel back to the chat. A pinch zooms the model under it either way, and a wheel the browser already scrolled the chat with never zooms (it arrives uncancelable, aimed at whatever the scroll brought under the pointer). Vertical swipes keep scrolling past a model; a horizontal swipe turns it, and with two fingers pans it. The viewer is built on three.js, which loads only when a reply actually shows a model. A model is read when its stage comes near the screen, and its scene is built once the stage has stayed on screen briefly, so scrolling past a group reads and builds nothing; one larger than the 64 MB a window keeps between scenes is read only when its scene is built, and again when it is rebuilt. Browsers keep only about sixteen drawing contexts per page and silently drop the oldest, so a window keeps at most eight scenes: one out of view for ten seconds gives its context back, as does the one out of view longest when another model needs a place, and each is rebuilt with its camera and animation time when it returns, as after the browser takes a context back. A group sent again under the same id shows the model it now names, **Retry** builds a failed model again, and a structured-output reply shows its files after its JSON. Model files are data: they are parsed, never executed, and the loader refuses every URL a file names, so a model reaches no other file and no network. That is also why a compressed model cannot open: the decoders for Draco, meshopt and Basis fetch their own decoder, so such a file is refused when it is offered rather than reaching the reader as an empty box. A texture still arriving is waited for, however long it takes; one that cannot load, such as an FBX texture kept beside the file, is dropped rather than drawn as black, and a model that carries no colour of its own takes the theme's `--model-surface`, so it stands out on either background.

**Lighting**, beside the zoom buttons, chooses how every model is lit. **Studio** is the even set of lights the viewer always had. **Flat** draws each surface unlit, in exactly its painted colours without tone mapping, as a texture's palette is checked: a surface of one colour shows as its silhouette. **Realistic** sets the model in a generated room, whose light physically based materials take and reflect, so metals and glossy paint show their sheen, under a sun high to the left of the starting view; its soft shadow falls on the model itself and on an unseen floor under the model's lowest point, which shows only the shadow, and both sides of a surface cast it, so planes and leaf cards facing the sun cast one too. The tone mapping is Khronos PBR Neutral, which keeps base colours true. The choice belongs to the device (`agent-studio.model-lighting` in local storage, Studio until one is made), lights every model in the window at once, the inline and expanded views alike, and lights the next model shown. A scene builds what a light needs when it is chosen, out of view only when it comes back, and keeps its last frame until the new light's shaders have compiled in the background: three.js compiles the room's light filters, its slowest shaders, the moment it builds the room, which held the window for half a second the first time. The sun's shadow map matches the canvas (512 to 2,048 texels a side) and is drawn again only when the model's pose or the light changes, not as the view turns. A textured FBX shows its painted colours in every light: three.js multiplies an FBX texture by the material's diffuse colour, which Blender writes as 0.8 grey, while FBX and Blender read the texture as replacing it.

On another device, a paired phone or browser or another computer, a model opens in the same viewer, read whole through one relay request whatever its size. Only when that read fails, as through a relay or device on the way that cannot carry it, does the computer that keeps the model draw eight views of it instead, a turn apart: the first where the viewer's camera starts and each next one turned as a drag to the right turns the viewer, with the viewer's Studio light, whichever light the reader chose, on a transparent background, an animated model in the opening pose of its first animation, and a model without colours of its own in a grey that reads on either theme. It draws them when a device first asks, one model at a time, as square WebP pictures of 1600 pixels (PNG where its engine cannot write WebP), keeps them beside the model until the model's result is pruned, and answers every later request with them; a new version of the drawing draws them again. The reply shows them as a turntable: drag across it, use the arrow keys, or use **Turn left** and **Turn right** to step through the eight, inline and expanded, which assistive technology reads as View N of 8. The size label adds 8 views, and its hover note says the whole model could not be read there. The views are read like any other result, so that computer must be online, and drawing a very large model occupies its window briefly.

Tables, documents and videos (requested 2026-10-21: "Allow for CSV, Markdown and XLSX (spreadsheet) and MP4 support") each take a card of their own in the reply, with the file's name, format and size below it and **Expand**, and open in the file viewer like any other file. A **table** — a CSV or TSV file, its separator found from its first line (a semicolon where a spreadsheet wrote decimal commas), or an XLSX or XLSM workbook — is parsed on the computer that keeps it (the `csv` crate, and `calamine` for workbooks, cells shown as a spreadsheet's General format shows them: numbers to fifteen significant digits, dates and times as ISO 8601, TRUE and FALSE, errors in their own words) and kept parsed while windows read it (eight tables or 256 MB). Its card shows its first nine rows and says how many rows and columns it has, or how many sheets; a click opens the whole sheet, its first row frozen above the others as the header, its rows numbered as its file numbers them (a worksheet from its first used cell), each worksheet a tab, numbers aligned to the right in either decimal convention, each column as wide as its longest cell up to 360 pixels (the computer keeping the table reports each column's longest cell with every page, so a larger number further down is never cut) with a longer cell's whole text on hover, and only the rows and columns in view drawn, so a sheet of millions of rows scrolls at once; its rows come 200 at a time as they scroll into view, and a sheet taller than browsers let an element be scrolls in proportion. A **document** — a Markdown file — shows its first 16 KB rendered in its card, fading where the card stops, and opens whole as a page to read, sanitized as a reply's text is, its links opening in the browser. A **video** — MP4, MOV or WebM, recognized by its own bytes, its picture size read from an MP4's track header — plays in its card; in the viewer it takes the room the window leaves it, its shape kept, and starts where the card stood, playing if it played, while the card waits and takes up where the viewer stopped. This computer's window streams a video in 2 MiB parts as it plays, through the `studio-file` protocol, which serves only kept files by run, place and call; another device reads it whole through the relay, once its reader presses **Play video**, since it may be large. Text is read as UTF-8, UTF-16 with its byte order mark, or Windows-1252 as spreadsheet programs save CSV. While a table, a page or a player has focus, the arrow keys scroll or seek it rather than stepping to another file. A group showing any of them is saved in the message's optional `extraSentFiles`, apart from `sentFiles`, which releases before them validate strictly and over which they would refuse the whole conversation; those releases drop the field and the group alone, a later revision moves a group between the fields, and the relay puts the field back when an earlier release's upload leaves it out.

**Audio** (requested 2026-10-23: "Add audio support for the send file") — MP3, after an ID3 tag or not, AAC frames, M4A, WAV, FLAC, Ogg with Vorbis or Opus, and WebM audio, each recognized by its own bytes, with an MP4, MOV or WebM file whose tracks hold sound alone taken as audio rather than a video without a picture — takes a card with a player of the app's own (`AudioView.svelte`): a round play button in the accent, the time, the position as a slider and the sound's length, and mute, with its format, length and size below. The card and the viewer, which shows the same player larger on the scrim, drive one audio element kept out of the page (`src/lib/audio-player.svelte.ts`), so opening the viewer, stepping past the sound or closing the viewer neither stops nor restarts it; starting one sound pauses any other. The slider takes a press or a drag anywhere along it, and while it has focus the arrow keys move five seconds, Page Up and Page Down a tenth of the sound, Home and End to its ends, and Space plays or pauses. A sound on this computer reads its length once its card nears the screen and streams through `studio-file` as a video does; another device reads it whole through the relay when its reader presses play, which starts it once it arrives. A file the engine cannot play, or one that could not be read, says so under the player with **Retry**. AIFF (as macOS `say` writes it), MIDI, Matroska audio and Ogg Theora video are refused with what to send instead. A group showing audio is saved in the message's optional `laterSentFiles`, since releases up to 1.0.1 validate `extraSentFiles` strictly in turn and drop a field they do not know. That field takes any media type: a kind of file a later release adds reaches this one there and shows as its name and size with Needs a newer Agent Studio, instead of refusing the conversation.

**compare_files** (requested 2026-10-16) shows two or more images or models side by side (tables, documents, videos and audio are refused with the reason, which tells the agent to send them with send_files): a stable `id`, the absolute `files` in the order to show them, optional `labels` (one single-line label per file, in the same order, such as Before and After) and an optional one-line `caption`. Its files are checked and kept exactly as send_files keeps them, and it shares send_files' `<!-- files:ID -->` markers and ids, so reusing an id replaces whichever group held it. A comparison needs two files that can be shown: with fewer the call fails with each file's reason, and with more the failed ones are named to the agent as send_files names them, each label staying with its own file. The saved group adds `compare` and each file's `label` to the send_files metadata; a release that does not know them shows the files as an ordinary group. Work history names the call Compare files.

Up to three panes stand in one row and four in two rows of two (requested 2026-10-16: "allow up to 4 files"), which keeps each pane half the comparison's width instead of a quarter; more files take rows of three, with no limit on how many. Where the comparison is narrower than 520 pixels, as on a phone, rows hold two. The rows share the window's height left by the chat's toolbar and composer, so a grid of four fits on screen whole, and no pane is taller than 520 pixels, 65% of the window, or shorter than 140 pixels. Every pane takes one shape, square when a model is among them and otherwise that of the widest image, from 3:4 to 2:1, and each is named below by its label, or its file name, with its dimensions or format and size. Every image fills its pane however small, so pictures of one scene at different resolutions show at one size, drawn with crisp pixels past twice their own. A bar below holds **Free** and **Synced**, one play and pause for every animated model (a model with several clips keeps its own Animation picker under its pane), Lighting when a model is shown, **Zoom in**, **Zoom out**, **Reset views** and **Expand comparison**. A model pane in the chat behaves as a reply's model does, the whole comparison taking the wheel once a model pane or one of its controls is clicked; an image pane then zooms with the wheel too, and with a touchpad pinch or two fingers, and with + - 0 1 while it has focus, pans by dragging or the arrows once zoomed in, and leaves vertical swipes to the chat until then. A click or tap on an image pane, or Enter while it has focus, opens the comparison in the file viewer, as a click on a single picture opens it (requested 2026-10-21: "I can't expand the image when it's a image comparison I need to click on the expand button"), and there a double click zooms. Panes zoom as deep and pan as freely as the viewer's pictures, the images of one kind together at every depth, since the deepest zoom is a share of each whole image.

**Synced**, the mode a comparison starts in, passes what the reader does to one pane to the panes of its kind: the models keep one camera, so one rotation, position and zoom (every model is centred and scaled to its longest side, so one view frames each alike), the images one zoom and position, measured as shares of each image, so a 64-pixel texture and its 256-pixel upscale show the same region, and the views another device shows of models it cannot read whole one turn. A model's glide after a drag ends with moves too small for three.js to report, so the view it comes to rest at is passed on once more and the panes end exactly together. In **Free** each pane turns, pans and zooms on its own; choosing Synced again gives each kind the view of its pane moved last. The bar's zoom and reset act on every pane in Free mode, and on one pane of each kind, which the others follow, in Synced. An image beside a model has no mode to choose. **Expand comparison** opens the comparison in the file viewer as one of the chat's files, named by its labels (Before vs After) with its kinds (2 images), its panes side by side at full size, or one above another on a screen taller than wide, where the wheel zooms. The mode chosen there holds in the chat too, the chat's models give up their scenes meanwhile, and the arrow keys in the mode switch choose a mode rather than another file. The mode stays in the window's memory, never saved or synced.

Paths are read only from the tool, never from prose, Markdown image links or another tool's output, and only for the conversation's own parent call: Claude submissions must match a registered parent `tool_use`, and Codex calls must come from the parent thread without a namespace. Each path is checked where the conversation runs — absolute, a regular file, and recognized by its own first bytes as an image, a model, a workbook, a video or a sound, or by its name and readable text as a CSV, TSV or Markdown file, which any text could be, of any size. A name asking for one of those is checked as one first, since a few lines of text can read like an OBJ model; a HEIF or AVIF picture, a Matroska file, an Ogg Theora video, AIFF audio and a MIDI file are refused with the reason, and a file that is none of them names every kind a reply can show. Agents are told to send a model at its full detail and never to decimate it, shrink its textures or compress it for the viewer. A glTF document or GLB that loads its buffers or textures from files beside it is refused with the advice to send a self-contained `.glb`, and so is one that needs a decoder the viewer does not carry -- Draco compression whenever the document lists it, since three.js prepares that decoder for any document naming it, and meshopt or Basis Universal compression when the document requires them -- with the advice to export it uncompressed, at full detail. A glTF or GLB document is read as it streams, keeping only where its buffers and images come from and the extensions it lists, so a document carrying hundreds of megabytes inline is never held whole; a glTF 1.0 container or a cut file is named as such; a model that still fails to open names the reason; OBJ, STL and FBX files appear untextured when their textures are separate files, since only the file itself is sent. A WSL conversation reports its Linux paths, which the owning Windows host translates through that distribution; a file name Windows would read differently (a backslash or colon in it, or a trailing dot or space) is refused rather than reaching another file. A check takes as long as the file system needs, and Stop ends it, so a share or mount that never answers cannot hold the reply's Stop. Files that fail return their reason to the agent, which is asked to tell you; a call whose files all fail shows nothing. A file that passes its check but cannot be kept afterwards, because it was removed meanwhile, says so in its place, and the files after it keep the numbers the reply gave them. The caption stays on one line: line breaks, tabs and other control characters become spaces. A call may send any number of files and a reply any number of groups; reusing an id replaces that group.

The bytes stay on the executing computer with the run's other tool results, under `tool-output/<run id>/<call>/` as `image-<n>` and `model-<n>` files, and are pruned with them (see [Tools and activity](#tools-and-activity)). The saved reply keeps only metadata — the run and call that hold them, each file's name, type, size and dimensions, and the caption — so the workspace, exports and relay sync never carry file contents, and the files are not replayed into later prompts. That computer's own window loads a model on demand as raw bytes, however large. Other windows load images and models, or a model's views when it cannot come whole, through the same transport as any other tool result, so a paired phone or browser reads them from the owning host when that computer is online, and a file that is no longer kept says so in place. Images and models are numbered within their own kind, so a group can mix them.

The tool is offered only to Codex and Claude chats with tools enabled; Gemini, background titles and other restricted queries never receive it. Other file types are not shown: mention their path in the reply instead.

## Slash commands and skills

Start a message with `/` to search commands and skills for the selected agent. Use the arrow keys and Enter or Tab to complete a choice, or click/tap it. Escape closes suggestions. Completing a native command or skill inserts its name and a space without sending, so you can add arguments before submitting. You can also type the full `/name arguments` directly. Namespaced Claude commands, including plugin skills and saved native workflows, keep their CLI spelling.

App shortcuts are `/help`, `/new`, `/model`, `/reasoning`, `/instructions`, `/context`, `/usage`, `/rewind`, `/undo`, and `/connections`. They open existing app controls without creating a provider reply; remaining text stays in the draft. `/reasoning` opens the Reasoning slider with focus, so its arrow keys step through the levels. `/new` starts a conversation on the selected computer and folder. `/rewind` and `/undo` open the Rewind and Undo edits confirmations described in docs/NATIVE-SESSIONS.md. Instructions remain editable between replies. Model and reasoning changes use their existing next-message behavior.

Claude suggestions use the command metadata returned by the selected CLI profile's initialization. Codex suggestions include only enabled, CLI-reported skills; selecting a duplicate name retains the exact source path. The app translates `/skill-name` into Codex's `$skill-name` spelling plus a structured `skill` input on stdin. The visible user message retains its slash spelling, with name/path metadata preserved through saved history, export, relay delivery, and retry. Earlier skill references are not injected again on subsequent replies. Selecting a skill does not claim it ran. See the official [Codex skill input contract](https://learn.chatgpt.com/docs/app-server#start-a-turn-invoke-a-skill) and [Claude command discovery and dispatch](https://code.claude.com/docs/en/agent-sdk/slash-commands).

Discovery shares the Model context cache and owning-host transport. It does not load file bodies into the composer or expose CLI initialization/account payloads. Switching agents, models, folders, or computers cannot reuse another selection's results. Failed refreshes preserve cached suggestions but block invocation until a fresh discovery succeeds. Offline or signed-out agents expose only app shortcuts. The installable PWA uses its selected computer's catalog and execution. Update the relay and execution computers together: older desktop hosts without command-catalog support show an update notice instead of silently discarding native skill references.

Terminal/session operations such as `/resume`, `/workflows`, and `/loop` remain unavailable in the composer. Agent Studio resumes its own Claude/Codex sessions automatically through their native protocols, without exposing terminal session controls or importing arbitrary CLI sessions. Use `/new` for a fresh app conversation. `/compact` is available for idle Claude and Codex chats, along with Compact context in usage details and Claude auto-compaction sizing. Unknown commands keep the draft and explain the problem. Absolute paths, fenced/inline code, and slash text inside ordinary prose remain ordinary messages. Gemini offers app shortcuts only. See [native session continuity](NATIVE-SESSIONS.md).

## Workflows, static and dynamic

Agent Studio's own workflows automate work across chats, agents, accounts and computers, listed under the sidebar's **Workflows** row, whose **+** starts a workflow chat, and made from any Claude or Codex chat with **Make a workflow**: static workflows are graphs of steps you and the chat's agent draw and edit, started by any of their triggers, and dynamic workflows give an orchestrator agent, the chat's own, a goal it pursues with its own agents for as long as it takes. Either can run the other and continue with its result. Both show live in a 2D graph in their chat's place, the chat a resizable card beside it on demand and the run's history a column on demand, with a numbered history of every step as it ran, and run on the computer chosen, handing over to the ones allowed when it goes offline. Runs in progress lead the Active tab. The chats a run starts belong to it: read-only, out of the chat lists, and alerting only through the run. Any chat can create, run and follow them with the workflow tools. See [Workflows](WORKFLOWS.md), which also compares them with Claude Code's Dynamic Workflows below.

## Claude workflows

Ask for a workflow directly in chat, or enter a saved `/workflow-name` command and its input in the composer. The selected Claude Code CLI uses its native `Workflow` tool and controls orchestration, branching, parallel agents, and intermediate results. There is no separate workflow toolbar button or launcher. See [Claude Code Dynamic Workflows](https://code.claude.com/docs/en/workflows).

Native saved scripts load from the selected project's `.claude/workflows/`, the selected CLI profile's personal workflow directory, and configured plugins. Include “save it for reuse,” a name, and a project or personal location in your request to have Claude save its script. Invoke that native command in later chats. These files belong to the execution computer and are not copied into workspace exports or relayed to another computer. Existing profile/organization workflow settings still apply. The app does not create a second library of Claude workflow scripts or run JavaScript itself; Agent Studio's own workflows (above) are a separate feature.

The panel tracks native run IDs, status, phases, agent labels/models, reported token/time counts, and reported result previews. The native launch acknowledgement is not completion: Agent Studio waits for the background task and subsequent CLI results. Only current human input gets `origin: {kind: "human"}`; earlier context is sent separately with `shouldQuery: false` so history cannot opt a new prompt into the `ultracode` keyword. Native `task_progress.workflow_progress` frames provide phase and agent metadata in Claude Code 2.1.267; older versions may report less detail. The SDK documents [Workflow inputs/outputs and background task notifications](https://code.claude.com/docs/en/agent-sdk/typescript).

Running requires the exact selected connection to be ready. The selected host owns the CLI process, account/profile, working folder, and captured parent model settings. Workflow scripts may choose their own agent models under Claude's native policy. **Stop response** cancels the owned process tree, including its workflow. Claude and Codex replies have no Agent Studio elapsed-time cutoff, including at startup and while waiting for answers; relay heartbeats still expire after 45 seconds without contact. There is no automatic replay after interruption. Retry resumes the same native transcript with an explicit continuation request to inspect existing results before repeating side effects. This preserves context; it cannot guarantee that every external operation is idempotent or revive killed background tasks.

The terminal `/workflows` menu, interactive pause/resume/restart controls, and resuming a previous native run across app replies are not exposed. Use the installed Claude CLI for those operations. Agent Studio renders every native run of a reply with all its phases and agents. Native progress persists through saved history, exports, and relay revisions. Legacy app-owned step definitions and their results remain readable/exportable, but the custom editor and sequencer have been removed; old execution requests are rejected.

## Plan and progress

A reply's provider plan, native workflow runs and background work appear as compact toggles in its footer row: after the live elapsed time while the reply runs, and after its timing, **Files edited** and **Memories** once it ends. The row wraps on narrow screens and keeps the space above the composer free. While the reply runs, the **Plan** toggle shows completed steps and names the step in progress when there is room; a workflow toggle shows its run status, and **Background work** counts what still runs. Click a toggle to open its steps, phases and agents, or running items in a panel below the row; one panel is open at a time, it renders on first opening, and an open panel stays open when the reply ends. Completed Work history sits directly below the model title, above the final answer. Retry is the last action below token/time. Workflow progress and the agent's current plan are labelled separately. A completed reply never automatically completes pending plan steps; stopped, failed, or unconfirmed work stays visibly unfinished. Plans remain out of the conversation text replay.

Codex plans come from [`turn/plan/updated`](https://learn.chatgpt.com/docs/app-server#turn-events). Claude supports both `TodoWrite` and the newer `TaskCreate`, `TaskUpdate`, `TaskGet`, and `TaskList` tools, applying updates only after successful tool results and associating task IDs from creation results. Child-agent plans cannot overwrite the parent's panel. Snapshots keep every step and are merged by revision through checkpoints and relay delivery.

Agent Studio also supplies Codex with `studio_update_plan` using the app-server's [dynamic tool API](https://learn.chatgpt.com/docs/app-server#dynamic-tool-calls-experimental). Codex 0.153.4 did not expose its built-in `update_plan` in live checks with GPT-5.5 and GPT-5.6 Sol. The app tool accepts a plan snapshot from the parent thread and updates the same panel; it executes no work or filesystem operations. Invalid arguments and child calls are rejected, repeated identical snapshots retain their revision, and tool activity records the invocation without arbitrary arguments. Models still choose when to report a plan; a plain-text checklist is not treated as a tool event.

Current Claude models disable todo tools by default. Agent Studio passes the process-local `--settings` override `{"env":{"CLAUDE_CODE_ENABLE_TODO_TOOLS":"1"}}` for tool-enabled chats, as documented in the [Claude Code release notes](https://platform.claude.com/docs/en/release-notes/claude-code). It does not edit profile settings, and background title/usage requests retain their restrictions. The override also travels as a fixed CLI argument through the WSL bridge. The decoder follows the [Claude task tracking protocol](https://code.claude.com/docs/en/agent-sdk/todo-tracking).

## Links

Links in replies, reasoning, progress comments and proposed plans carry the icon the linked site serves for itself, the way a browser tab shows one, before the link text in the accent color; hovering underlines it. Only addresses a browser would open as a page are marked. Relative paths, `mailto:` addresses, files and anything else keep their plain link, and a site whose icon is unknown, unreachable or still being read keeps a generic globe, so a mark never changes the space a link takes.

The computer showing the reply reads the icon, not the one that ran the agent. It asks the site's own origin for `/favicon.ico` and, when that serves none, reads the beginning of its page for the icons it declares and tries up to three of them. Nothing else is requested. An icon over 256 KB, or anything whose bytes are not an image, is refused, so a page served in place of a missing icon never becomes a mark; only the icon itself crosses IPC, as a base64 data URL the window CSP already allows. Readings stay in memory on that computer — twelve hours for an icon, thirty minutes for a site without one, 500 sites at a time and four reads at once — and no link, page or icon is written to the workspace, exports or prompts. A paired browser cannot read an icon itself — its window may load images from its own origin alone — so it asks its relay for one origin at a time, and the relay reads the site exactly the same way and answers with the same bounded data URL. Reading one needs that browser's own session, the response carries no workspace data, and the relay keeps a single reading for every device that asks. It also never reads its own network: each address is resolved before the request and private, loopback, link-local and multicast addresses are refused, including after a redirect.

Rendered Markdown carries one class per site and a single stylesheet rule supplies that site's icon once it arrives, so a streaming reply never re-walks its links, and a mark is never an image element inside sanitized Markdown.
## Code snippets

Fenced code blocks in replies and progress text use syntax colors for their declared language, including common aliases such as `js`, `ts`, `py`, `sh`, and `ps1`. Common languages such as JavaScript/TypeScript, Python, Rust, C/C++, C#, Go, Java, SQL, JSON, YAML, HTML/XML, CSS, and PowerShell are bundled locally, so highlighting works offline. Colors update while a reply streams and reappear in saved history. Inline code, unlabelled fences, unknown languages, and blocks longer than 65,536 UTF-16 code units keep plain code formatting. Highlighted output is sanitized before display; HTML snippets remain inert code until explicitly opened as artifacts.

### Copy and Run in console

Every fenced block has **Copy** at its top right corner, and a block written for a console has **Run** beside it. Both stay quiet until the block is hovered or holds keyboard focus; touch screens and phones always show them, in a row above the code. Copy puts the block's exact text on the clipboard and reads **Copied** for a moment. Replies, progress comments, reasoning, proposed plans and a sub-agent's messages all get the controls, and so does saved history. A block a streaming reply is still writing has none until its closing fence arrives, since half a command should not run.

**Run** opens a console window on the computer the chat runs on, in the chat's folder (its project folder, or a Standalone chat's own working folder), runs the block there and leaves the console open at its prompt. The window is yours from then on: Agent Studio reads nothing back from it and never closes it. Each console first shows the code it runs, up to twelve lines.

| Block label | Runs in |
| --- | --- |
| `powershell`, `pwsh`, `ps1`, `ps` | PowerShell: PowerShell 7 when `pwsh` is on PATH, otherwise Windows PowerShell. The code runs in the session itself, so what it defines stays for the prompt, and your profile loads as usual. |
| `cmd`, `bat`, `batch`, `dos` | Command Prompt, as a batch file, which echoes each command and then stays open. |
| `bash`, `sh`, `shell`, `zsh` | On Windows, Git Bash (PowerShell when Git for Windows is not installed). In a WSL distribution, for a chat that runs there. On macOS and Linux, a terminal. |

A POSIX block runs in an interactive login shell: your own when it is bash or zsh, otherwise bash. It reads your settings as your console does, so aliases, functions and PATH apply. When the code ends, however it ends, the same shell starts again at a prompt, in the folder the code changed to and with the variables it exported. `exit` and `set -e` in a block therefore end the block, not the window. Other languages and unlabelled blocks only copy: session transcripts (`console`, `shell-session`) mix prompts with output, and most other code is part of a file. So that the commands an agent gives get Run, every chat agent is told to name each fence's language: the shell a command is written for (`bash`, `powershell` or `cmd`), and `text` or `console` for output and transcripts (`GUIDANCE` in `src-tauri/src/console.rs`). An agent learns this when its native session starts, so a chat begun on an earlier release can still write commands in unlabelled blocks.

Run exists only where a console can open: in the desktop app, for a chat that runs on that computer or in a WSL distribution it manages. A chat another computer runs, and the Viewer, show Copy alone. A chat in a WSL distribution, or on macOS or Linux, offers Run for POSIX blocks only. Clicking Run is the decision to run, with no confirmation: the control reads **Opening…** and then names what opened (**Opened in PowerShell**, **Opened in Ubuntu**), and a console that could not open says why below its block until the next attempt. The code runs only in the chat's folder. A missing folder opens no console, shell settings that change folder (a `cd ~` in `.bashrc`, a `Set-Location` in a PowerShell profile) are followed by a return to the chat's folder before the code, and Command Prompt, which falls back to the Windows folder when started in a network folder, refuses a chat whose folder is one.

What runs is what the block shows. The controls go into the page after the Markdown is sanitized, in place of a mark each fence leaves there, and the sanitizer allows neither `<div>` nor `<button>`. Markup a reply writes can therefore never become a control, wrap one, or add hidden text to a block, and a link written around a block does not take its clicks. The host refuses code holding characters a block cannot show (control characters, and zero-width or bidirectional formatting characters such as a right-to-left override), naming the reason below the block; code of any length runs.

The code is data all the way. The window sends it with the chat's identity; the host resolves the folder itself from the chat's connection, location and conversation, as it does for a reply, and accepts no path. It writes the code to a file under `console/` in app data, or through stdin into a temporary folder of a WSL distribution, and starts the shell with constant scripts that read that file (`console-launch.sh` for POSIX shells). Neither the code nor a path is ever written into a command line. PowerShell and bash delete the file once they have read it, a batch file goes when its Command Prompt closes, and anything left behind is removed a day later. A console does not inherit the markers of an agent's session (`CLAUDECODE`, `CODEX_THREAD_ID`). Nothing about a run is saved, synced or sent to the agent, so a reply never learns that its code ran: say so in the chat when it matters.

Two opt-in Rust tests run the same consoles without windows. Browser tests cover the controls, their states, forged markup, where Run appears, phones and the Viewer. Not exercised: macOS and Linux terminals (their code is type-checked against the Linux standard library only), PowerShell 7, and a Windows computer without Git Bash.

## Artifacts and HTML previews

The **Source** tab uses the same syntax colors as chat for HTML and SVG, including embedded CSS and JavaScript, in both modal and side-panel views. It displays the original source as inert text and keeps downloads unchanged. Very large sources retain plain code formatting.

A block whose opening fence names it after the language (```` ```html Sales report ````), as Agent Studio asks models to write artifacts, or one holding a whole HTML page (a doctype or `html` element, after any comments) shows as that card in place of its code, wherever the answer or one of the reply's own comments has it (`shownAsArtifact` in `src/lib/artifacts.ts`, drawn by `src/lib/markdown.ts`). Open the card for the existing modal viewer, or use its side-panel button to preview beside the chat. The viewer header switches between modal and panel without restarting the live preview. Preview/Source, restart, and download are available in both. The panel leaves the composer usable on wide windows and becomes a right-side drawer on narrow screens; closing it preserves the draft. Drag its left divider to resize, or focus the divider and use arrow keys (Shift for larger steps), Home/End for its limits, and Enter or double-click to reset. The side panel belongs to its chat: another chat, Connections or Settings hides it, and it is open again when you return to its chat, its preview restarted, while every chat keeps its own. Shown again, a docked panel leaves focus where you put it, and the drawer of a narrow window takes focus as it does when opened. An artifact open in the modal closes when you leave its chat. Every complete block can be previewed, whatever its size and however many a reply has. Incomplete blocks remain available as code. Source is retained in the original reply, so saved history, exports, and relay updates preserve the artifact without reading local file paths. Parent-authored progress fences are also retained when a later native workflow completion summary follows the artifact; identical source is deduplicated. Tool output, arguments, and child results are never used as artifact source.

HTML previews support inline CSS and JavaScript, SVG, and embedded data images. The desktop and browser policies are kept identical (`src/lib/csp.test.ts`). The main chat continues to render only sanitized Markdown. The app sends source into the renderer once; it does not accept messages or commands from artifact code. The public routes serve only the empty bootstrap and are never used to store source or credentials. ## Image attachments

With Codex or Claude selected, click the paperclip below the message input, paste a screenshot, or drop image files anywhere in the chat area, including over the conversation. A highlighted drop area appears while dragging. Dropping adds the previews to your current draft and focuses the message input without sending. Click a thumbnail to inspect the image at a larger size; Escape, Close or a click outside the preview returns to the chat. Use its remove button to discard an attachment before sending. You can send images with or without a text message. Sent images appear above your message bubble, and an image-only message shows just its images. Thumbnails show only the image; hover one for its file name, which also heads the larger preview.

PNG, JPEG, and WebP files are supported, as many per message and as large as you like. Original image bytes are preserved; the app does not resize or recompress them. A conversation holds as many images as it likes, and a provider that accepts fewer or smaller ones reports its own limit. Images remain visible after reopening the conversation, are included on retries and later turns, and travel with workspace exports and relay sync.

Images are kept apart from the conversations that show them. A sent message keeps a small reference naming each image by its SHA-256; the bytes are kept once on each computer, in the app-data `images` folder, and once for the workspace on the relay. Sending first keeps the images there (**Saving images…** on a desktop, **Uploading images…** in the Viewer); if that fails, the message stays in the composer with its images. A saved chat, a sync or a reply therefore carries references rather than megabytes of base64. A computer that shows or runs a chat whose images it does not hold reads them from the relay and keeps them; the Viewer reads them from the relay when it shows them.

Before a chat with images syncs, or a reply with images is sent to another computer, the relay must hold them. The desktop that attached an image uploads it; until then, another device keeps that chat's latest changes to itself and says so in the sync status. A relay from before the image store cannot take chats with image references at all: update the relay first. It keeps serving older apps, storing the images they still send inline and handing them back inline. On the first start of this release, a desktop and a relay each move the images saved inside their workspace into the store and keep the previous file as `workspace-before-images.json`. The Viewer turns the copy it saved into the same references once the relay holds those images, uploading any only it had; one the relay refuses stays inline. Exports put the images' bytes back inline so a file stands on its own; an image neither the computer nor the relay holds keeps its reference, and the export notice counts it. Images no saved chat names any more (after deleting chats) leave a desktop's store an hour after they were kept and the relay's a day after.

Codex receives structured `image` inputs with data URLs through its app-server stdin; Claude receives base64 image content blocks using `--input-format stream-json`. Each image is labelled with its original message position. No attachment paths are passed to the CLI, and image bytes are excluded from the text prompt, background titles, token estimates, and activity cards. See the [Codex app-server reference](https://learn.chatgpt.com/docs/app-server) and [Claude streaming image input](https://code.claude.com/docs/en/agent-sdk/streaming-vs-single-mode). Gemini's current [Antigravity stream input](https://www.antigravity.google/docs/cli/headless/) accepts text blocks only, so its paperclip is disabled with an explanation.

Tauri's native file-drop interception is disabled to let the WebView deliver file drops to the chat. Drops outside chat cannot open the file in place of the app. Ordinary text drops keep their normal behavior. File contents stay inside the selected conversation and are delivered to its selected CLI/account through the existing transport. Provider-reported vision usage contributes to the usual context meter; the app does not estimate vision tokens from base64 length.

## Tools and activity

Tool cards and the rows of running calls show elapsed time (rows from the first second), and a collapsed group holding a running call, such as a sub-agent record that started another agent, shows its longest running tool (parallel durations are not added). The execution host advances observed time once per second even while a tool is quiet; this is elapsed time, never a completion percentage or a claim that output is arriving. Claude `tool_progress` can advance the clock with `elapsed_time_seconds`; Codex completion `durationMs` is retained when available. Older activity without timing stays unknown. Unfinished operations retain their last recorded time with the existing stopped/unconfirmed outcome after the reply ends.

Claude heartbeats and Codex `item/mcpToolCall/progress`, `item/commandExecution/outputDelta`, legacy `item/fileChange/outputDelta`, and `item/commandExecution/terminalInteraction` add fixed **Progress reported**, **Output received**, or **Terminal interaction** indicators. Expanded calls show when the last signal was recorded. No message, output delta, terminal input, process ID, or arbitrary progress text is stored or displayed; a call's output is shown once it finishes, as described under [Commands, inputs and results](#commands-inputs-and-results). Signals must match an existing running operation and its parent/child attribution; Codex also requires the exact thread, turn, and item kind. Late signals cannot revive finished calls. Repeated same-second signals are coalesced. Optional `elapsedMs` and `progress` fields survive workspace export, saved history, checkpoints, and relay reconciliation, outside prompt replay.

The interactive `command/exec/*` API is distinct from model-owned command execution: its processes and notifications are connection-scoped, without a chat/turn identity. Agent Studio does not create those sessions or offer terminal input/resize/stop controls. Unowned `command/exec/outputDelta` is ignored rather than assigned to the active chat. This feature is progress indicators only. Protocol references: [Codex app-server](https://learn.chatgpt.com/docs/app-server) and [Claude SDK tool progress types](https://app.unpkg.com/@anthropic-ai/claude-agent-sdk@0.3.220/files/sdk.d.ts).

Windows native verification on 2026-09-20 used `scripts/native-tool-progress.tauri.json` and `scripts/tool-progress-native-smoke.mjs` with real Claude and Codex logins in an isolated app. Both ran a twelve-second command, showed live elapsed time, and saved completion duration without its output; Codex also supplied output-progress signals. Claude's PowerShell task lifecycle now updates its command card instead of being mistaken for a sub-agent with a raw result. Controlled native-loop fixtures cover Claude heartbeats, quiet timers and stale/unowned Codex signals; decoder fixtures also cover MCP progress, legacy file-change output, terminal interactions, child attribution and late completion. Desktop/mobile browser tests cover expansion, drafts, stopped state and restored history. Live MCP progress and legacy file-change output were not induced against external servers; WSL and other operating systems were not exercised for this feature.

All chat providers run their tools with full access and without permission prompts. Claude and Codex chats can load the selected CLI profile's skills, search the web, and delegate work to sub-agents. Ask for these actions in the composer. Codex chat explicitly enables live web search and multi-agent tools. Claude loads its default built-in tools and configured project/profile resources. Gemini/Antigravity uses its default agent, configured resources, and `--dangerously-skip-permissions` in `accept-edits` mode; available tools depend on that CLI. Gemini's native skill catalog and MCP connection status are not inspected by Agent Studio.

Open **Model context → Skills** to inspect available resources. **Use in next message** inserts a skill request into the current draft and returns focus to the composer. Disabled skills cannot be selected. This action does not send a message or claim that a skill has loaded.

While a reply runs, reasoning, progress messages and tool activity appear inline in order. The chat follows new updates while you are at the bottom. Scrolling up holds your reading position, even just above the end; scroll back to the bottom to resume following. Once the end is more than a few lines below, a round **Jump to latest** button appears at the conversation's lower left, in the avatars' column rather than centered over the text, and wheel and touch scrolling pass through it. It shows the end at once and follows again; its arrow takes the accent color while the reply is still running, and pressing it from the keyboard continues in the composer. Sending a message from the end of the chat glides down to it and the start of the reply in about a third of a second instead of jumping, taking in whatever the reply writes meanwhile; scrolling, clicking or pressing a key in the conversation stops the glide where it is, and the move is instant when the system asks for reduced motion. Sending while you read above the end leaves your place alone: the message and its reply arrive below, and **Jump to latest** leads to them. Opening another chat shows its end and follows it, however far up you were in the previous one; choosing the chat that is already open keeps your place. Returning from Connections or Settings shows the end of a chat you were following, or else the message you were reading. Updates that arrive through the relay, such as a reply another computer runs or one this computer runs for another device, are followed like a reply running here, and so is content that sizes itself after it appears, such as a visual reporting its height. Expanding or collapsing Work history, tool groups, file lists, or reply details keeps what you see in place. Collapsing near the end leaves temporary blank space below the conversation instead of pulling it down; scrolling up removes that space, and it never lets you scroll further down than where you were. Expanding content past the end stops following it. The full conversation and expanded activity remain scrollable above the composer. The message input starts at three lines and grows with a longer draft until the composer box reaches half the window (four lines on phones), then scrolls; browsers without CSS `field-sizing` keep the fixed three lines. While you follow the end, a taller composer, a smaller window or an opened phone keyboard keeps the end in view; a reading position above the end stays where it is. When it finishes, a collapsed **Work history** item appears directly below the model title, above the final answer. Its header shows the label without activity counts or category filters. Expand it to review all reasoning, progress comments and tool calls in their recorded order. A compaction of the context during the reply is an entry there too, where it began, with the sizes the provider reported (see [native session continuity](NATIVE-SESSIONS.md#compaction)). Replies with only reasoning, progress comments or a compaction also have Work history; replies without recorded activity omit it. The disclosure starts collapsed again when reopening a saved conversation. Expanded history ends with a divider before the final answer, starting with **Collapse**, which closes the history from its end: unless the start of the history is still in view, the **Work history** row takes the control's place, under the pointer, and keyboard focus moves to that row. The startup notes "Starting the provider CLI" and "Connected to Claude" are hidden from live and saved activity.

Both live activity and expanded Work history group consecutive tool calls into quiet, collapsed rows that count what happened, such as **Read 12 files**, **Ran 2 web searches**, or **Edited 3 files, ran 4 commands, and used 2 tools**. Every kind of action in the group appears with its count, in the order it first ran. A file counts once however often it was read or edited, going by the paths the provider reported; a call without a reported path counts as its own file. Sub-agents count once each, even when resumed, and commands, file and web searches, web pages, agent messages, skills, images, hooks and other tools count every call. Reasoning, progress comments and compaction markers stay visible between groups in their recorded order. Expand a group to see its individual calls, then expand a call for details. Incoming calls and revisions keep an opened group open; completion and reopening saved chats start collapsed. Group labels use reported action metadata, with **Used N tools** for unrecognized tools. A group holding a running call reads like **Reading 3 files and running 1 command**. When a call failed, stopped, or has an unconfirmed outcome, the label switches to nouns that do not claim success, such as **Edits to 1 file and 2 commands**. A group holding a running call has a spinner, and failed, stopped, or unconfirmed outcomes remain visible on the collapsed row. A sub-agent's own calls are counted apart from the sub-agent: one that carried on past two failed commands reads **Worked with 1 sub-agent** with **2 calls failed** beside it, while a sub-agent that failed itself makes its group read **1 sub-agent** with **Failed**. A long label wraps beside its icon and chevron, and a running group's progress text wraps before its label on narrow screens.

**What runs now.** While a reply runs, each call that is still running has a row of its own below its group, saying what it does from the reported metadata: **Running** `npm test`, **Reading** `src/app.ts`, **Viewing** `screens/home.png`, **Searching for** `TODO`, **Searching the web for** a query, or **Working with** a sub-agent, with that sub-agent's latest call beneath it. A sheen crosses the verb while the call runs, and the row shows its progress signal and elapsed time. Commands show their first line, marked … when more lines follow, with the whole script on hover. The latest call of the reply's last entry keeps its row after it finishes, marked done or named with its outcome (**Command** `npm run lint` **Failed**), until the agent starts another call, thinks, or writes; every other finished call folds into its group's count. A folded row fades upward over the row that replaces it, the rows below slide up to close its gap, and the count updates with a small lift; the first call a group folds turns into its summary in place. Parallel calls keep their rows while they run, up to six per group with a count of the rest. Rows open like calls to show their details, and a row you opened stays until you close it. Only opacity and transforms animate, and nothing moves with reduced motion. When rows fold while the chat follows its end, blank space keeps the conversation in place until new content fills it. When the reply ends, all of it becomes Work history as before.

**Background work.** Claude can move work to the background: a command started with `run_in_background` (or moved there when a turn is interrupted or steered), a Monitor watch, or a sub-agent launched asynchronously. Its call returns to the model while the work continues, so history never shows it running. Groups count these launches as **started N background tasks** or **started N background sub-agents**, without a spinner or clock, and the call reads **In background** while the reply runs. A **Background work** toggle in the footer row of the reply that started the work counts the commands and monitors still running; open it to list each item, labelled by the reported description (the call in Work history shows its command), with the execution host's elapsed time. Sub-agents launched in the background are listed under the reply's **Sub-agents** toggle instead, marked **In background**. It stays after the reply ends: the executing computer keeps following each Claude task that the chat's CLI process still runs, including ones started by earlier replies, by observing the parked process's task notifications, the way live account usage is read. An entry leaves the card when the CLI reports its outcome, which then updates that call in the saved reply with the final duration, a Completed, Failed or Stopped mark, and a note that it ran in the background. Releasing the process (moving the chat to History, deleting it, a changed launch setting, or quitting the app; closing the window to the tray keeps it, and no time limit applies) ends the work it still ran, recorded as Stopped when the app is still open to save it. Until an outcome arrives, work still running when a completed reply ended, such as a dev server left for you, reads **Left running** and is not flagged as a problem; after a stop or failure it stays unconfirmed. A chat whose reply ended while a Monitor watch still runs stays marked in the executing computer's sidebar: its row ends with the pulse icon Work history gives Monitor calls, and its hover title and accessible name add **Monitor still running** (or the number of monitors), whether or not its reply has been read, until each monitor reports its outcome or the process is released. Background commands such as servers never mark a row, since they usually run until you stop them. The list is transient state on the executing computer: a window that loads later asks the host for it, and the Viewer shows background work only while its reply runs, with later outcomes arriving through sync. Only the CLI's explicit signals count: `backgroundTaskId` in a Bash or PowerShell result, `taskId` in a Monitor result, and `isAsync` in an Agent result. Codex reports no equivalent signal, so its commands keep their usual running state. The optional `background` flag on calls and sub-agents survives saved history, exports, and relay checkpoints. On 2026-09-24, with Claude Code 2.1.278 and Sonnet through the production runner, the opt-in `installed_claude_reply_waits_for_declared_tests_but_not_servers` test confirmed that a server launch stays running with the flag after the reply and that the declared tests finish complete with it, and `installed_claude_background_work_outlives_its_reply` confirmed that a job left running is reported complete by the parked process and that releasing the process stops the server. Monitor and background sub-agent results were checked against recorded CLI transcripts and decoder fixtures, not induced live; browser tests cover the card, history labels, stops and phone layouts.

Individual calls show running, completed, failed, stopped, or unconfirmed outcomes. Each operation has a stable identity; repeated searches with the same query remain separate inside their group. Headers identify the target when supplied. Call details include:

- Skill cards show an actual Claude Skill invocation or an observed direct read of a `SKILL.md` file. File reads do not establish that all instructions were followed. The context inspector remains an availability inventory rather than a reply's read history.
- Search cards show the query and provider-supplied HTTP(S) source links when available. Missing sources are stated explicitly; the UI does not manufacture links or turn a missing result into a successful search.
- Sub-agents are rows of their group, one per child, with its name, its task (or the sub-agent that delegated it) and its reported state; each row opens the child's conversation in the side panel described under [Sub-agents](#sub-agents). Child text and token usage do not overwrite the parent reply. Nested delegation retains the reported parent relationship.
- Each child's reported text is kept during the run and in saved history, and appears in its conversation. Claude chat launches enable `--forward-subagent-text`; completed text blocks are keyed by SDK UUID because multiple blocks can share an API message ID. When SendMessage resumes a sub-agent that finished, Claude Code reports the same task under the SendMessage call while the child keeps answering the call that started it, so the task stays with that sub-agent: it runs again under its own name and row rather than appearing as a second sub-agent, and a later start never renames a sub-agent its own call named. A later reply that resumes a sub-agent an earlier reply started has never seen the call that started it, so it records the sub-agent once its first line arrives, under that call, which the line answers, with the `agent_id` the line names (or, when a line names none, the one sub-agent it resumed), the description Claude Code reports again and the SendMessage summary as its task: the resumed run shows with that reply, its calls, messages and outcome included, instead of calls no row held (requested 2026-10-16). With Claude Code 2.1.301 and Sonnet, the opt-in `installed_claude_a_later_reply_records_the_sub_agent_it_resumes` test resumed a background agent from the next reply in the parked process and again from a fresh process resuming the session, and each reply recorded it under the call that started it, with its calls, messages and outcome. Codex `subAgentActivity` establishes ownership and lifecycle independently of legacy collaboration calls, and child message deltas reconcile against completed items. Duplicate lifecycle events cannot revive a finished child; known child turns reject mismatched updates. Thinking, signatures and raw tool output remain excluded.
- Claude **Message agent** cards show the recipient, reported short summary and supported message type. **List agents** cards show names/statuses/counts when the CLI supplies a structured `agents` result. Text-only directory output is not copied. A directory listing never establishes child ownership: listed peers may belong to other sessions. Message bodies are not displayed, and tool success does not assert that a peer acted on the message.
- Read cards show the file path and available line ranges/counts, then the lines read with their line numbers. Glob and Grep cards identify the pattern, folder, filters, and reported matching file paths/counts, then the matches. Tool search shows its query and returned tool names. Commands show their description, the command itself, structured file actions, working folders, and their output with its exit code. Edit and Write cards show that call's own recorded diff. Older calls whose metadata was not recorded show an explicit explanation; their missing details cannot be reconstructed.

### Sub-agents

A sub-agent's work belongs to its own conversation, which opens in a panel beside the chat instead of expanding inside the reply. Its calls never join the reply's own groups. Live activity says **Working with** it, with its latest call beneath; Work history lists each sub-agent as a row of its group, with its task (or **Delegated by** the sub-agent that started it) and its outcome. While a reply runs, a **Sub-agents** toggle in its footer row, beside the elapsed time and before **Background work**, counts the sub-agents still running, including those launched in the background, and those of the replies it took over, which it waits for (see [sending while a reply waits](NATIVE-SESSIONS.md#sending-while-a-reply-waits)): their records stay with the reply that started them, which has ended. Open it to list each one with what it does now, taken from its latest call (**Running** `npm test`, **Reading** `session.ts`), whether it runs in the background, and how many calls it has made; the toggle leaves when the last one finishes. A row or a list item opens that sub-agent's conversation and stays marked while it is shown. While the reply that took a reply over runs, that reply's sub-agents still running read **In background** in its Work history and their conversations read live, as if their own reply still ran (requested 2026-10-16).

The panel reads like a chat. The task the parent gave it comes first, as a message on the right; then its own messages, rendered as sanitized Markdown, among its calls in the order they came, grouped and opened exactly like the reply's (**Read 2 files**, a running call's own row with its sheen and elapsed time, each call's command, input, diff and result from the executing computer); then the sub-agents it started, whose rows open their own conversations in the same panel; and, once it has finished, its result below a divider. Closing messages that the result repeats appear once, as the result. The header names the sub-agent with its state (**Running**, **Running in the background**, **Completed**, **Failed**, **Stopped** or **Outcome unconfirmed**), who delegated it, and its number of calls. A running sub-agent opens at its latest update and follows new ones while you stay at the end; scrolling up or opening a call holds your place. A finished one opens at its task.

On wide windows the panel docks at the right of the chat, which stays usable beside it, with a divider that resizes it by pointer or keyboard and remembers its width on this device separately from the artifact panel's; narrower windows and phones show it as a drawer over the chat. Escape or its close button closes it. Like the artifact side panel, it belongs to its chat: another chat, Connections or Settings hides it, and it is open again when you return, at its latest update while the sub-agent runs and at its task once it has finished. It closes when the reply no longer holds the sub-agent, as after a rewind. The artifact side panel and the sub-agent panel take turns: opening one closes the other, while an artifact opened as a modal leaves the sub-agent panel in place. The panel reads the conversation's saved data, so it works the same in the Viewer and after a reload, and nothing of it is saved or synced beyond the reply's existing activity.

A message's place among the calls is the optional `after` count on it: how many of the sub-agent's own calls the execution host had recorded when the message began. The Claude decoder counts before the calls of the same output line, and Codex counts when a message's first delta or completed item arrives on the child's thread. Messages saved before this field existed follow the calls, and a place past the calls this reply recorded, as after the activity limit, ends the conversation. Older app versions and relays drop the field, so ordering needs the updated relay as well.

### Commands, inputs and results

Every call row has an icon for what it does. Commands are classified from their text, past folder changes, variable assignments and wrappers such as `sudo` or `timeout`: the Git logo for `git`, a pull request for `gh`, a flask for test runs (`npm test`, `vitest`, `cargo test`, `pytest`), a hammer for builds and type checks, a wand for linters and formatters, a package for installs, and separate icons for dev servers, scripts, containers, downloads, remote shells, listings, reads, searches, deletions, copies, processes, waits and other agent CLIs, with a terminal for anything else. Tools use file, code, image, edit, new-file, folder-search, text-search, web, link, skill, agent, connected-tool (a plug; a window or camera for browser automation and screenshots), plan, question, workflow and hook icons. A group shows the icon its first kind of action shares, such as the Git logo for a run of git commands, or that kind's general icon when its calls differ. Group labels are unchanged; images read by Claude and Codex count as **viewed N images**.

A command row reads as its description when Claude reports one, with the command below it, or as the command itself. Codex runs each command through the shell's own command line, like `"…\powershell.exe" -Command '<script>'`; the row and the details show the script and name the shell. A configured CLI hook can prepend lines, such as a `node …\hooks\…` call; the row names the first line after them, and the details show them quietly above the command. Records show the whole command, and the whole pretty JSON arguments of connected (MCP), dynamic and unrecognized tools. Skill arguments and web page prompts become facts; Agent Studio's own tools and Write/Edit bodies are never recorded as inputs.

Opening a call shows its command, input and result as one transcript: the shell and its prompt with the highlighted command, then **Output** or **File content** with the line count, **Exit code N** (green for 0, red otherwise), and **Copy** actions. File reads show line numbers from the reported first line and highlight by file extension up to 64 KB; **Standard error** appears separately, in red only when the call failed. Images returned by a tool (Claude image reads and screenshot tools, Codex image views, connected tools) load one by one as thumbnails with their dimensions and size, and open in the file viewer, where they zoom and pan like a reply's files and the arrows step through that call's images; tiny images are enlarged with crisp pixels. A long result starts in a scrolling box with **Show all**. Each stream arrives whole. A computer on an earlier release sends only the beginning and end of a long one, with a marker and **Show full output**, which loads up to 8 MB of each stream from it. Text is always shown as text, never HTML.

Results stay on the computer that ran the reply, complete and without size, count or age limits. They cannot live in the synced workspace: it is one JSON document that is saved whole after every change and uploaded or downloaded whole when it syncs, and a heavy local history produced about 35,000 shell calls averaging 2.2 KB and 4,500 image reads averaging 180 KB in 20 days, which every save and sync would then carry. The provider decoder hands each finished call's result, exactly as the provider sent it, to its run's recorder, which writes one folder per call under `tool-output/<run id>/` in the app data folder: `stdout.txt` and `stderr.txt`, `image-<n>.<ext>` for each image whose own bytes identify PNG, JPEG, GIF or WebP, and `meta.json`, written last, with the exit code, first line and image list. ANSI escape sequences and carriage-return progress redraws are cleaned when text is shown, not when it is kept. A Codex image view names a file, which is copied once when the call completes (a regular file of a supported type; a WSL path through the distribution's own path translation). The activity record keeps only the result's size: lines, bytes, images, whether it has errors, the exit code and whether the provider shortened it.

A window reads a result when its call is opened: through a native command on the computer that ran it, or as a transient relay job to that computer from other devices and the Viewer, naming only the run's UUID, the call's activity ID and, for an image, its index. A result's streams, a kept image, a model or a model's eight views each come in one relay request, which the relay carries whatever its size. The relay holds a read's result only until the requesting window has it, or a minute after it finished when that window never asks, and a window asks another computer for two images, models, models' views or full views at a time, so a group of large files loads in turn. A read lasts as long as that computer keeps reporting it, and one that fails, such as through an earlier relay that refuses a large result, ends with that reason rather than an expiry. Results are never synced, exported, checkpointed into relay state, or replayed into prompts, and no request can name a file path. While a result is being written, a request waits for it. Each window caches a bounded set of results and images. Results are kept as long as a saved chat references their run: when the app starts and after each run, only runs that the saved workspace no longer references are removed (after an hour, so a reply still being saved keeps its results). Deleted conversations therefore lose their results at the next pruning; forks keep their run identities and share them on the same computer. Other devices can read results only while that computer is online. Calls recorded before this version have no command or result to show, and a missing result says that it was not kept, with **Retry** for temporary failures such as an offline computer.

Completed activity remains in saved chats and workspace exports. Interrupted replies show stopped or unconfirmed outcomes for operations that never supplied a terminal event. Intermediate progress messages remain inside the expandable history and stay out of the next prompt's conversation replay. Plain activity blocks from older chats remain readable. Markdown response exports use the final answer.

## Implementation and limits

Codex chat uses the installed CLI's **app-server** stdio protocol with a persistent thread for each app conversation. Follow-ups use `thread/resume` with the exact host-owned ID and `excludeTurns: true`; the CLI retains its native transcript without returning raw earlier tool output to the renderer. Legacy callers without a conversation ID remain ephemeral. The validated process working directory and selected CLI profile are unchanged; JSON requests and prompts travel on stdin. Restricted title generation still uses `exec`, and usage/context inventory queries remain separate. The app-server stream also exposes measured last-request context input and the resolved model. Only the parent thread's usage contributes to the reply's meter.

The installed Codex 0.153.4 `exec --json` stream omitted modern `subAgentActivity` events in a live probe. Its app-server stream supplied those events and the child messages directly. Ephemeral threads reject `thread/read` with `includeTurns`, so the adapter consumes live child notifications and never reads another session's files. Protocol shapes were checked against the installed CLI's generated TypeScript schema and the [Codex exec event definitions](https://github.com/openai/codex/blob/main/codex-rs/exec/src/exec_events.rs).

Configured CLI hooks may prepend a command before a PowerShell skill-file read. In that case Codex can report an unknown command action. The fallback recognizes direct read statements after the hook, tracks quoting so echoed examples do not count as reads, and supports the observed `-Raw`/`-LiteralPath` form. A command can also read an ordinary file before a skill; the skill search continues past the ordinary read and retains that other target in the details. These cases have regression fixtures; hook scripts and skill bodies are never inspected by the activity decoder.

Claude tool inputs can arrive in fragments. Finishing the input block only updates metadata; a corresponding tool result or task notification establishes the outcome. Complete child messages carry their parent tool identity, as described in [Claude's streaming documentation](https://code.claude.com/docs/en/agent-sdk/streaming-output) and [sub-agent documentation](https://code.claude.com/docs/en/agent-sdk/subagents). Selected metadata fields, commands, arguments of connected and unrecognized tools, search source links, and child results are forwarded; results reach only the executing computer's store. Account payloads and configuration bodies are excluded.

The decoder records every operation a reply reports, however long the reply runs, with all its sources and metadata facts and its whole command and input, while results stay on the executing computer. Replies saved before 2026-09-29 kept only their first 200 operations; their activity ends with a note that later calls were not recorded. A reply keeps every sub-agent and progress message it reports. A remote run's relay job carries a window of its newest 160 calls and every running one with each update: the oldest finished calls leave the job 64 at a time, and a device that missed them receives them with the conversation the executing computer saves and syncs. Source links reject non-web schemes and embedded credentials. Result text is rendered as text, not provider HTML.

A child's messages are kept whole, however many it writes and however long each is, each with its place among the child's calls, and so are its task and result. Replies saved before 2026-09-29 kept 16 messages of up to 16,000 UTF-16 units in all, and their panel says that some of the sub-agent's text was not recorded. A Codex child's streamed text goes out at most four times a second while it grows, and its completed message at once. Partial Codex messages left at stop/failure are labelled incomplete. All child detail remains outside parent text, token usage, reasoning, plan and prompt replay. Older saved activity without messages remains readable.

Activity records are an additive optional field inside workspace v3 activity blocks. The execution host checkpoints them, relay delivery retains the newest revision per operation, and same-run reconciliation merges progress independently of answer text. Both app installations and the relay should run the updated version to preserve this metadata and support the expanded event envelope.

Claude progress resets at each streamed message start and reconciles against the corresponding assistant message identity; its final result is separate. Its reported child-agent identity also keeps resumed child sessions from inflating the sub-agent count, while preserving each invocation's task and tools. Codex agent-message items retain their identities, with `final_answer` phase used for the final response and the completed turn providing a fallback for older phase-less events. A final message already present in the progress stream is shown once. This avoids concatenating commentary into the final answer or losing it when the provider replaces its accumulated text.

## Files edited summaries

Each finished assistant response has **Files edited** beside elapsed and cumulative AI time in a compact footer row, followed by the reply's plan, workflow and background work toggles when it has them. All of them start collapsed. Clicking a label opens its panel and closes any other; clicking the open label collapses it. File scope and list expansion survive panel switches. Each scope initially shows five files, with Show all files and Show fewer files controls for longer lists. The routine response-scope, combined-chat, and coverage notes are omitted. **This response** shows its recorded file edits; **All chat changes** shows the combined result of recorded edits across the entire conversation, including later responses. Each file expands into a line-numbered code diff with additions and deletions. Repeated edits are composed rather than counted again, and fully reverted changes disappear from the combined view. The UI does not modify files. Individual diffs start collapsed inside subtle bordered file rows. Each row starts with the icon of its file type, so a stylesheet, markup, a component, code, a test, data, configuration, a shell script, a lock file, a build file, a container file, a Git file, an image or a document are told apart at a glance; the type comes from the file name alone, and an unrecognized name keeps the plain document icon. Added marks a newly created file in the selected scope and omits per-file line-change counts and hunk coordinate headers. Summary line-change totals cover existing files only; Edited marks a change to an existing file. A file created earlier and edited later remains Added in All chat changes. Paths are relative to the selected project, or a shared recorded directory when multiple absolute paths establish one; full paths remain available on hover, and unrelated roots stay explicit.

Codex native file-change completions and successful Claude Edit, MultiEdit, and Write results supply the source. This is a record of reported edits, not a scan of the working directory: shell commands, external edits, unsupported tools/providers, and older replies can lack diffs. A discontinuity, an unavailable source, or the recording limit of a reply an earlier release saved is shown explicitly rather than reconstructed from a guess. Older replies retain confirmed filenames from saved edit activity while marking their missing diffs unavailable. Common credential files omit their diff bodies. File text is displayed as inert text and is never executed or read from an arbitrary path.

Optional `message.fileChanges` snapshots are revisioned and keep every edit operation and file a reply records, whatever their size. A hunk has validated original/updated line ranges and signed lines; incomplete hunks are never silently truncated into valid-looking source. The combined viewer shows every file, whatever its line span. Snapshots survive local history, workspace exports, remote delivery, and same-run checkpoints; they are excluded from model prompt replay, title generation, and tool activity. Older clients that omit this field cannot erase a matching locally retained run's snapshot.

### Memories

Edits of the agent's own memory leave Files edited for a **Memories** toggle right after it, shown only on replies that changed a memory file, with the number of memory files beside it. Its card works like Files edited: This response and All chat changes, five files before Show all files, Added and Edited labels, and line-numbered diffs, with the full path on hover. A memory file is one in Claude's auto memory, `projects/<project key>/memory/` of a Claude configuration folder (`~/.claude`, `CLAUDE_CONFIG_DIR`, or an account's separate profile on Windows or in WSL), where the key is the project's path with every other character turned into a dash; in a sub-agent's memory, `agent-memory/` or `agent-memory-local/` of `.claude` or a separate Claude profile; or in Codex's `memories/` folder of `~/.codex` or a separate Codex profile. Those show within their memory folder (`MEMORY.md`, `feedback_tests.md`). Every `CLAUDE.md` and `CLAUDE.local.md`, which Claude Code loads as memory, is a memory file too, wherever it is, and shows as Files edited would show it (`CLAUDE.md`, `.claude/CLAUDE.md`): both cards share the selected project, or the folder their other paths share, and memory folders never widen it. The window decides this from the recorded path alone, so replies saved before Memories existed split too, and nothing new is saved or synced. A custom `autoMemoryDirectory` is not recognized and stays in Files edited, as do `AGENTS.md` and every other file. Undo edits still covers memory edits along with the other files of its reply.

## Day divisions

A chat that continues on another day shows where each day begins. Above the first message of a day, the day's name sits between two hairlines across the conversation, named as History names its days: **Today**, **Yesterday**, a weekday within the last week, then the date, with its year when that differs from this one. Hovering the name shows the full date. The first message is compared with today, so a chat written today has no division, a chat from another day opens with its day, and continuing it puts **Today** above the new message. An open chat gains its divisions when midnight passes.

Messages show only a time of day, so the divisions are what tells a reply from last week from one written this morning. Days are those of each message's recorded time on the clock of the device showing the chat, so the same chat can divide at another message in another time zone. A message without a readable time belongs to the day before it.

A division sits between messages, never inside one, and is a separator named by its day for assistive technology. The window derives them from the messages it already holds (`chatDays` in `src/lib/chat-days.ts`): nothing is saved, synced, exported or sent to a model, and chats saved before divisions existed, imported chats and forks show them too.

Verification: `src/lib/chat-days.test.ts` and `tests/chat-days.spec.ts`, whose layout scenarios also run in WebKit.

## Unsent drafts

Text typed in the composer but not sent stays with its conversation. Switching chats, opening Connections or Settings, forking, following a notification, reloading, and closing Agent Studio keep it, and reopening the chat restores it, including a chat that moved to History at startup. Sending, steering, or queuing the text removes the draft (queued messages stay session-only), as does clearing the composer. Deleting a conversation deletes its draft, including a deletion synced from another device.

### Scratch chats

Every new chat is a scratch chat of its own: a conversation that has not been sent yet. Starting one from the sidebar **+** of a computer, folder or Standalone, the header **+**, Ctrl+N or Connections opens an empty composer, so a folder can hold several scratch chats instead of one draft. Once you type, the scratch chat appears first in its folder in the Active tab, as a quieter row with a pen, named by its first line (or *Image conversation* for images alone). Leave it to write another, and click its row to continue: it returns with its text, mentions and attachments and with the computer, folder, agent, account, model, reasoning and chat instructions chosen for it. Choosing another folder or computer moves the scratch chat along with its text. A scratch chat left empty disappears.

Sending the first message turns the scratch chat into the conversation, in the same place. `/new` starts another scratch chat on the same computer and folder and carries the rest of its line there. To throw one away, hover its row and click the archive icon at its end, the **Move to history** button conversation rows have (keyboard users can Tab to it; touch screens always show it): a scratch chat has no history to move to, so the button, named **Discard draft**, discards it at once, without a confirmation. Or right-click its row (Shift+F10, the context-menu key, or a long press on touch screens), choose **Discard draft** and confirm. Discarding the open scratch chat empties it where it is. Scratch chats are not conversations: they are not counted in the Active tab, the pending chat badge or History, they never reach the workspace, and search matches their first line, folder and computer. After a restart, or when the Viewer signs in, Agent Studio continues the scratch chat you edited last, as it restored a new chat's draft before; the others wait in Active, and without any a fresh chat opens. A draft that an earlier release kept for a folder, Standalone location or computer becomes a scratch chat in the same place the first time the app loads it.

Drafts belong to the device and are never part of the workspace, exports, or relay sync. The desktop app saves their text and selected mention identity, and for a scratch chat its computer, folder and chat settings (account connection IDs, never credentials), in `drafts.json` in its app data through asynchronous native commands, at most every 300 ms while you type and immediately when the window loses focus, is hidden, or closes from the title bar or for an update. Attached images stay with a draft while the app is open but are not saved. The Viewer keeps drafts in browser storage scoped to its authenticated workspace; signing out, session expiry, or a workspace change removes them with the other cached data, and tabs of the same workspace merge their saved drafts per conversation and scratch chat, keeping the newest; a scratch chat started in another tab appears after a reload. Every draft is saved, whatever its length. Restored mentions stay selected only while the chat, account, and folder still match; otherwise they must be chosen again, as after any other account or folder change. An unreadable drafts file is reported and replaced by the next save.

Verification: `src/lib/drafts.test.ts`, `src/lib/browser-workspace.test.ts`, `tests/drafts.spec.ts`, the Viewer case in `tests/private-workspaces.spec.ts`, and Rust `drafts::tests`. `scripts/drafts-native-smoke.mjs` drives an isolated build (`npx tauri build --debug --no-bundle --config scripts/native-drafts.tauri.json`, WebView2 debugging port 19682) launched through `npm run start:windows -- -Executable`: it closes the window from the title bar right after typing, relaunches, checks that the scratch chat continues and the chat keeps its draft, and reads `drafts.json`. It seeds its chat directly and never sends a provider request.

## Message queue

While a reply is running, the composer keeps accepting input. Enter or the queue button holds the message for that conversation and lists it above the composer, in order, with a control that returns it to the draft. Any number of messages can wait. When the reply completes, the first queued message is sent automatically with its images and any selected skill; each later one follows its own completed reply. Each goes with the conversation's settings when it is sent, so an account, model or reasoning chosen while the reply ran applies to it. If the reply is stopped or fails, or the composer cannot send when the reply ends, the queued messages return to the draft, oldest first and ahead of any text already typed, with all their images. Queued messages live only in the open session: they are never saved, exported, or relayed, and they do not steer the running turn. See docs/NATIVE-SESSIONS.md for the persistent process behind this.

## Steers

**Steer now** sends the composer's text to the reply that is running, instead of holding it for the next one. Once the provider acknowledges it, the steer joins the conversation as a message of your own (requested 2026-10-13): your bubble at the right edge, like the message that started the reply, with a small **Steer** mark above it and a tinted border that tell it from an ordinary message. It stands where the reply took it. What the reply had done until then stays above it, and the reply goes on below under its own heading, with the time of the steer:

- While the reply runs, the calls and comments made before the steer keep their place above it, a call that was still running finishes there, and what the agent does next appears below. Until it does something, the part below shows the three waiting dots under **Responding**.
- Once the reply ends, each part keeps its own **Work history**, closed like any other, and the answer, the reply's times, **Files edited** and its actions follow the last part. A reply that was stopped or failed says so in its last part only.
- A steer the reply took before it had done anything stands above the reply, and steers taken one after the other stand together, with no empty heading between them.
- A reply steered on a release before this one recorded no place for its steer, so the steer follows the reply's work, with only the answer after it.

A steer is still part of its reply: it starts no reply of its own, offers no **Rewind here**, and a retry or a fresh native session sends it along as earlier context. See docs/NATIVE-SESSIONS.md for how its place is recorded and synced.
