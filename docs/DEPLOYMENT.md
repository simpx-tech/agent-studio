# Production VPS

Agent Studio was initially deployed on 2026-09-09 from application commit `12f2d6d`. Subsequent releases are selected by the `/opt/agent-studio/current` symlink; inspect it for the live revision. Since 2026-09-23 the server installs each published GitHub release by itself; see [automatic updates](#automatic-updates).

- Initial HTTPS endpoint: https://studio.72.61.63.95.sslip.io
- VPS: `72.61.63.95` / `srv1169603`, Debian 13.
- Windows SSH alias: `agent-studio-vps`. Use `ssh agent-studio-vps`; password authentication is not needed. The dedicated private key is in the local user's `.ssh` directory and must never be copied into this repository. Existing SSH identities were preserved.
- Initial release: `/opt/agent-studio/releases/12f2d6d`; release directories are selected by `/opt/agent-studio/current`.
- Runtime: `/opt/agent-studio/runtimes/node-v24.20.0-linux-x64`, downloaded from the official Node distribution and SHA-256 checked. No global Node or Docker installation was changed.
- Service: `/etc/systemd/system/agent-studio.service`, enabled on boot and running as the dedicated `agent-studio` system user. It listens on `127.0.0.1:4317` with no memory, CPU or task cap, and `NODE_OPTIONS=--max-old-space-size=32768` lets Node's heap grow to the machine's 32 GB (Node otherwise stops at 4 GB), so the relay stops only where the machine does.
- Persistent workspace: `/var/lib/agent-studio`, owned by the service user with mode 0700.
- Pairing configuration: `/etc/agent-studio/relay.env`, root-only mode 0600. A copy of the pairing key is in the Windows user's protected `.ssh/agent-studio-vps-pairing-key.txt`. Neither secret is committed. Do not print secrets in command logs.
- Desktop downloads: `/opt/agent-studio/downloads/agent-studio-windows-x64-setup.exe`, selected by `AGENT_STUDIO_DOWNLOADS_DIR` in the service's `downloads.conf` drop-in. After each automatic relay update, the release's signed Windows NSIS installer replaces it atomically (installed copies then update themselves; see [desktop updates](UPDATES.md)), and the previous package is kept in `/var/backups/agent-studio`. This directory contains only public installers; the relay streams its fixed allowlisted package separately from the public shell and private workspace files. No macOS or Linux installer is currently published.
- HTTPS: the existing Caddy service imports `/etc/caddy/sites-enabled/agent-studio.caddy`. Caddy obtained a trusted Let's Encrypt certificate and manages renewal. The original Caddyfile backup path is recorded in `/etc/agent-studio/caddy-backup-path`.

## Connect a desktop and phone

To share this VPS with another person while keeping chats and computers separate, create a member workspace from **Settings → Workspace administration** in the sole admin workspace. The existing owner starts as admin. Transferring administration makes the target the only admin and the previous admin a member atomically. [Workspace administration and CLI recovery](PRIVATE-WORKSPACES.md) cover roles and key management. Keep the original owner key private. Preserve the complete `/var/lib/agent-studio` tree on upgrades and backups, including `workspaces.json` and each additional `workspaces/<id>/` directory. Creating, transferring administration, rotating keys, and disabling member workspaces do not require a service restart.

Open **Connections → Set up sync** in the desktop app, enter the HTTPS endpoint and pairing key, and keep the desktop app open. Open the same endpoint on the phone and pair with that key. A desktop's accounts sign in on that desktop; the VPS's own accounts sign in from any device ([server host](#server-host)). Deploying the server does not automatically upload or switch an existing desktop workspace.

The IP-based hostname needs no user-managed DNS record. To use `studio.simpx.net`, point its A record at `72.61.63.95`, confirm public resolution, then add that hostname to the dedicated Caddy site, validate, and reload Caddy. Preserve the previous hostname during migration. Browser storage and sessions are scoped to the origin, so pair the new origin separately.

## Automatic updates

`agent-studio-update.timer` runs [`scripts/vps/update.ts`](../scripts/vps/update.ts) as root every five minutes. It reads the repository's latest GitHub release through the public API and installs each new release once, usually within fifteen minutes of publication, including build time. GitHub holds no credentials for this server, and a merge to `main` without a new version publishes no release, so it changes nothing here.

1. **Authenticate.** The release must contain `Agent-Studio_<version>_x64-setup.exe` and its `.sig`. The installer must match GitHub's SHA-256 digest and carry a valid updater signature for exactly that version from the trusted key, the same check installed apps make. Only the signing release pipeline can therefore deploy. The trusted key is stored in `/var/lib/agent-studio-update/state.json`, seeded from `src-tauri/tauri.conf.json` at installation, and follows a key rotation after activating a release that ships a new public key.
2. **Build.** The tagged commit's source is built as the unprivileged `agent-studio-build` user in `/opt/agent-studio/releases/.building-<commit>`, one sandboxed `systemd-run` step at a time: `npm ci --ignore-scripts` (the only step with network access), `npm run build` and `npm test`. The sandbox cannot read the relay's data, backups, the updater state or `/etc/agent-studio`, may write only that directory and `/var/cache/agent-studio-build`, and runs at low CPU and I/O priority beside the other workloads, with no memory, task or time limit. The finished release becomes root-owned, not writable by others, and is renamed to `releases/<commit>`.
3. **Activate.** A stopped relay is left alone, unless nothing is at `/opt/agent-studio/current` yet: a [new server](#set-up-another-server) starts its relay with its first release, without waiting for replies, and keeps it stopped and without a release when that one fails its health check. While any workspace checkpoint shows a running reply, activation waits up to two hours, then proceeds; a reply whose computer stopped publishing stays marked running and holds it those two hours too, since the files do not tell it from one that runs. Then, while the relay still runs, the updater **tries the release**: it copies `/var/lib/agent-studio` to `/var/lib/.agent-studio-trial` and starts the release's relay on the copy as `agent-studio-trial`, a transient unit with the service's user, its `Environment=` entries and its environment files (read from systemd entry by entry through `busctl`, so values with spaces or quotes stay whole), no network but a loopback of its own (so it reaches no device and sends none of the phone alerts the data holds queued) and no sight of the data itself, and gives it the health check below. systemd lets an environment file override `Environment=`, so where the trial reads and listens is set by `env` in its command, after both: a `relay.env` that names the data folder or the port cannot send a trial to the real data. A trial shows that the release's relay starts on this data and answers an unauthenticated request; it does not show more. The copy is made while the relay writes, file by file, so it is not a snapshot of one moment (each file is whole, since the relay replaces its files by renaming), and nothing a signed-in device does is tried. The trial's unit is bound to the updater's own (`BindsTo=`), so it ends when the updater is killed, and every check first removes a trial left behind, the unit and then its copy; a trial whose unit does not stop keeps its copy, and that check ends there with `Nothing is activated while a trial left behind cannot be removed`: it looks for no release, tries none and takes up no activation, an interrupted one included, until a check has cleared the trial. A release that fails its trial is marked failed with what its relay did and logged, and the relay is never stopped. Before stopping it the updater also checks that a backup can be written and that the disks have room for what an activation can need at once (`spaceShort`): the archive, and the two restores of a release that fails when the one before no longer starts either, each unpacked beside the data while the folders they replace are kept. The data's disk needs the data twice over and the backups' disk once, and where they are one disk (as here, by `st_dev`) all three count together; compressing the backup later is not counted, since a backup that cannot be compressed stays as it is. Only then it stops `agent-studio`, archives `/var/lib/agent-studio` (without the `.npm` cache earlier manual builds left there) to `/var/backups/agent-studio/pre-<commit>.tar`, uncompressed, points `current` at the release, starts the service and checks it again. When that check fails it restores the data backup and the previous release and restarts the service; the replaced data stays in `/var/lib/.agent-studio-failed-<short commit>-<time>`. When the previous release no longer starts either, it may have written to the restored data before it ended: what it left is kept in a folder of the same kind named after its own commit, the backup is put back once more, and the new release is started a second time, on the data as it was before the switch. It is kept when it serves, with what happened in the release's `note` in `state.json` and in the journal; only when that fails too is the relay down, with each relay's reason in the release's `error` and `Intervene manually` in the journal. When the backup cannot be written although the check before said it could, the relay is already stopped: the previous release is started again on its data, which nothing touched, and when it no longer starts, the new one, which read a copy of that data in its trial, is started on it without a backup, with a `note` saying so.
   - **Backups.** A backup is the archive and its manifest, `pre-<commit>.tar.manifest.json`: the archive's size and SHA-256, and every file, folder and link that was backed up with each file's size. Writing the 822 MB of 2026-11-20 with the SHA-256 and the flush takes 3.4 seconds of a stopped relay (compressing them took 24, which is why the archive is compressed only once the relay runs). The archive is written under a name of its own, flushed, its manifest written and flushed, and only then given its name; the state names it after that. Before a backup is put back, its file must have the recorded size and SHA-256, and what it unpacks to, beside the data, must be exactly what the manifest lists; only then does the data make way for it. GNU tar ends well on an archive that was cut at the end of a file and unpacks the files before the cut, which is why. A backup that is missing, has no manifest, is not the archive that was made or does not unpack to everything is never put back and nothing is moved aside for it: the activation records `restoreError`, the release before is started on the data as the failed release left it, and when that one no longer starts the new one is started once more on the same data, each with exactly that in the release's `error` or `note` (`could not be put back (…), so the private data stayed as it was, with nothing moved aside`). Compressing happens in `tidy`, at the end of an activation and again at later checks until it is done, at most three times: the copy is written beside the archive, flushed, unpacked and compared with the archive's SHA-256, recorded in the manifest and named `pre-<commit>.tar.gz`; the state then names the copy and lists the archive in `cleanup`, and only then is the archive removed. An updater killed anywhere in that leaves the state naming a file that is there.
   - **Interrupted activations.** Each step is written to the release's `activation` in `state.json` before anything it does (`trial`, `backup`, `candidate`, `previous`, `again`, `abandon`), with when it was written (`entered`), the backup and the names of the folders that will keep replaced data, and each step can be done again from its start: a restore under a name already used finishes what was begun and never replaces the data twice, and a backup made for the activation that the state does not name yet is used rather than made again, while the data is still as it holds it. An updater that ended in the middle (killed, stopped by someone, ended by its watchdog, the server restarted) is therefore taken up by the next check, before any newer release is looked at. A step that starts a relay first stops whatever runs, with one exception: when the relay that runs is the one that very step started, it is checked as it runs and not started again, so no device is cut off a second time. That is taken as shown only when the service is active and never started its process again, the process's working directory is the release's own (read from `/proc/<pid>/cwd`, so the release it runs whatever `current` selects by now), `current` selects it too, the process began after the step was written (so after that updater's own stop; the kernel tells a start to the second) and the restore the step does first is finished. Anything else, and the step is done from its start. That `current` selects a release never counts as its relay serving: a release becomes `active`, and its installer and host follow, only after its relay passed the health check in the same run. A release selected by hand is recorded the same way, once its running relay passes the check.
   - **What survives what.** An updater that is killed loses nothing: the state, a backup, its manifest and its compressed copy are each written under a name of their own (`<name>.<pid>-<random>.partial`, cleared by the next writer, which holds the lock) and renamed into place, so a reader finds the file from before or the whole new one. A power loss, or a kernel that stops, also loses what was written and had not reached the disk, so these are flushed in the order a recovery reads them: the state's file and then its folder at every write, before the step it announces is taken; a backup and its manifest before the state names them; what a restore unpacked (`sync --file-system`) before the data is renamed aside, and each of the two renames before the next; the `current` and host links after they change; a built release before it is named. `state.json.previous` is the generation before each write. When `state.json` is missing or not whole, the check uses that generation and says so: it is at most one step behind, which doing every step again from its start covers, and when it names no activation and the relay is not running, what `current` selects is started and health-checked before anything else, since nothing says whether an updater stopped it. A file that could not be read is kept as `state.json.unreadable-<time>`. With neither generation readable the state is lost: the check starts and checks a stopped relay the same way, writes an empty state and fails with `No updater key is trusted any more … run scripts/vps/install.sh again`, and installs nothing until that is done. A relay that does not start in either case is said again at every check, with `Intervene manually`. Not covered: a disk that reports a flush it did not do, and the relay's own files, which the relay writes without flushing.
   - **Health check** (`healthy` in `update.ts`; since 2026-11-20). The relay answers an unauthenticated `/v1/state` request with 401. It reads its whole state before it listens, so the check waits for the first answer as long as the relay's own process runs and works, with no limit of time, by what systemd reports of its service (`ActiveState`, `NRestarts`, `MainPID`, `CPUUsageNSec`) and the kernel of its process (`/proc/<pid>/io` and its page faults). Only evidence ends the wait: a process that ended, or that its service started again, fails the check at the next look, about a second for a crash loop; and one that does not answer and in two minutes used less than a second of CPU time and read or wrote less than a megabyte fails as stuck. A relay that works on is waited for however long it takes, and the journal says so once a minute. Once it answers, it must answer five more times five seconds apart, each probe waiting up to 30 seconds, and the same two rules apply while an answer is missing. When systemd does not answer about the service (each `systemctl show` and `journalctl` is given a minute, each stop and start ten), that says nothing of the relay: the check goes on asking both and never fails or rolls back for it. Before, the check gave the relay 30 seconds to listen and one 3-second probe: on 2026-11-13 the server was slow, the relay needed longer than that to read 465 MB, and v1.3.2 and v1.3.3 were rolled back while they were starting. The owner's 537 MB take 13 to 20 seconds to listen, 46 to 104 at a third of a core, and saves and whole reads hold the relay's event loop for 4 to 16 seconds.
   - **Why the trial.** A rollback needs a previous release that still starts. On 2026-11-20 production's v1.3.1 could no longer read its own data, which had passed what one text holds while it ran (below), so a failed switch would have ended with the relay down. The trial makes the switch a checked one, and the second start of the new release covers what a trial cannot see.
4. **Publish the installer.** The verified installer replaces the public Windows download only after a successful activation. The updater confirms the relay serves the new file and restores the previous package otherwise.

Download and build failures are retried after 10 and 60 minutes, three attempts in total. An untrusted installer, a failed trial, a disk without room for the backup or a failed health check marks the release failed without automatic retries. A newer release replaces one that has not been activated yet, removing its unused build. Older releases are never installed. The updater keeps the five most recent releases it activated, with their data and installer backups, and removes older ones it activated: when a release drops out of that history, `prune` deletes its release directory (unless it is the current or the previous one), its data backup with the manifest, and its installer backup. A data backup is therefore gone five activations later; copy one elsewhere to keep it. Releases and backups deployed by hand are left alone.

- **Status:** `systemctl list-timers agent-studio-update.timer`, `journalctl -u agent-studio-update` and `/var/lib/agent-studio-update/state.json`, which holds no secrets. Quiet runs log nothing.
- **Check now:** `systemctl start agent-studio-update`.
- **Retry a failed release:** `/opt/agent-studio/runtimes/node-v24.20.0-linux-x64/bin/node /opt/agent-studio/updater/vps/update.ts retry`. The release's `error` in `state.json` says what its relay did and the last error it logged; a trial's own log is `journalctl -u agent-studio-trial`. A release with an `activation` in `state.json` is in the middle of one: the next check goes on with it, and `systemctl start agent-studio-update` runs that check now (the unit reports its start at once; add `--wait` to wait for its end).
- **The lock.** Everything that changes the state or a deployment holds `/opt/agent-studio/.deploy.lock`: `update.ts` takes it itself for `check`, `retry` and `trust` (it runs itself again under `flock`), and `install.sh` holds it while it replaces the updater and trusts the key. A check skips its run while the lock is held (`A deployment holds the lock; this check is skipped.`); `retry`, `trust` and `install.sh` wait for a running check to end, and say that they wait. Manual deployments hold the same lock: `flock /opt/agent-studio/.deploy.lock <command>`.
- **A check that hangs.** The unit has no deadline (`TimeoutStartSec=infinity`, no `RuntimeMaxSec`): until 2026-11-20 its `TimeoutStartSec=2h` ended a run that was still working, which began a trial again from its start and restarted a relay that served. It is `Type=notify` with `WatchdogSec=5min` instead. The process systemd starts reports the start, runs the check as a child and answers the watchdog every 30 seconds for as long as the check shows signs of life: its own code ran (a byte on a pipe every ten seconds, which also arrives while it waits for a build, a download or a relay), or the commands it waits for used at least five seconds of CPU time or moved a megabyte on the disk (the unit's own `cpu.stat` and `io.stat`, which cover `tar`, `gzip`, the flushes and the copy for a trial). After fifteen minutes of neither (`AGENT_STUDIO_UPDATE_HUNG_AFTER`, in seconds) it says `it is hung`, stops answering, and systemd ends the unit five minutes later; the next run goes on from the state. This is a check of liveness, not a limit of time: no length of work ends a check. What it does not notice: a build or an installer that runs forever in its own unit while the updater waits for it, since the updater's own code still runs; `systemctl stop agent-studio-update` ends such a run, and the build begins again at the next check. A oneshot unit cannot have a watchdog (systemd ignores `WatchdogSec` for it, checked on systemd 257), which is why the unit's type changed.
- **Pause:** `systemctl disable --now agent-studio-update.timer`; `enable --now` resumes.
- **Install or update the updater:** it never updates itself, because release code only ever runs as unprivileged users. When a release changes `scripts/vps/update.ts`, `scripts/vps/state-file.ts` or `scripts/release.ts`, its journal says so. Copy the repository's `scripts` directory and `src-tauri/tauri.conf.json` to the server and run `bash scripts/vps/install.sh <scripts directory> <tauri.conf.json>` as root. It waits for a running check to end (the lock above), creates the build user and state directories, installs the files under `/opt/agent-studio/updater` (`release.ts`, `vps/update.ts` and `vps/state-file.ts`) and the units, and enables the timer, leaving the relay, its data and releases unchanged.
- **End-to-end check:** `node scripts/vps/smoke.mjs` packages the committed HEAD and runs the updater on the VPS against an isolated relay instance on port 4399 and a local stand-in for GitHub signed with a throwaway key. It builds and installs a release, waits for a running reply and for a relay that works 45 seconds before it listens, kills an updater while its trial runs (the trial must end with it and the next check clear its copy), refuses a release whose relay ends on a copy of the data without stopping the relay, rolls back a release whose relay ends in a loop as the service, refuses an installer from another key, activates a relay whose answers take eight seconds, starts a release once more on the data from before the switch when the one before it no longer starts and wrote to its data as it failed, kills an updater right after it selected a release whose relay then ends (the next check must check it and go back, not record it) and one whose relay serves (the next check finishes it), ignores a downgrade, confirms production is unchanged and removes everything it created. Every check runs under the settings of the repository's `agent-studio-update.service` (all but its `ExecStart`), so the unit's type, watchdog and missing deadline are what is tested. It also kills an updater once the relay it started answers (the next check must check that process and not start another), holds the lock (a check must skip its run and `retry` wait without touching the state), and on three gigabytes of data kills an updater while `tar` archives them (no backup may have its name, and the next goes on), while `gzip` compresses the backup (the state must still name the archive, whole by its manifest, and the check after it must end with the compressed copy alone) and while the backup is put back (the next check must finish the restore once). It cuts a backup to 1,024 bytes before a rollback (the backup must be refused, the data left alone and nothing moved aside), stops an updater's process while it waits for a trial with the watchdog shortened (systemd must end the unit and the trial, and the next check, under the same short watchdog, must run for minutes without being ended), and interrupts a host switch twice (a host that runs the version must be watched on with its process unchanged, and one older than its link restarted). The QA relay's environment file names its data folder and a second file holds a quoted value, so every trial also shows that it reads its copy with the whole environment of the service. Only the first release is built from source; the others are that build with another `relay/start.ts`. Results are written to `artifacts/vps-update-qa/result.json`.

Both units pin the Node runtime path; update `agent-studio.service` and `agent-studio-update.service` together when changing it.

## Server host

The VPS also runs Agent Studio itself, so chats can run on it (requested 2026-10-10). It appears as the computer **VPS**, with the server icon, in Connections, the chat's Computer picker and the sidebar of every device of the owner workspace, and works like any other computer: start a chat on it, browse its folders, read its accounts' usage and context, open its screens. Its replies go on when every other device is closed, and reach phones through the relay like any other.

- **What runs.** `agent-studio-host.service` runs the release's Linux AppImage, extracted under `/opt/agent-studio/host/<version>` (`current` selects one), in server mode (`AGENT_STUDIO_SERVER=1`, see `src-tauri/src/server.rs`) under its own session bus (`dbus-run-session`) and a virtual display (`xvfb-run`), as the `claude` user. Its agents work with full access as that user, and `/etc/sudoers.d/agent-studio-host` lets them run anything as root without a password: they can administer the whole server, its other services and the relay's private data included. The app keeps its data in `~claude/.local/share/com.vinicius.agentstudio`; Claude Code and Codex live in `~claude/.local/bin`, and the app updates them as it does on any computer. It takes about 750 MB of memory and almost no CPU while idle.
- **Pairing.** The service hands the app the relay's own key as a systemd credential (`LoadCredential=relay-key:/etc/agent-studio/host.key`, root-only, copied from `AGENT_STUDIO_RELAY_TOKEN` in `relay.env`), and the app connects over loopback (`http://127.0.0.1:4317`), so the host belongs to the owner workspace. When the relay's key is rotated, the updater gives the host the new one and restarts it; a different key written into `host.key` by hand (to put the host in another workspace) stays.
- **Accounts.** The `claude` user's own terminal logins appear by themselves. On any device, **Connections** shows the VPS card: **Open sign-in** on an account starts its sign-in on the VPS and shows the page there on your device. Codex shows a code to enter on OpenAI's page; Claude's page ends with a code you paste back on your device, which travels to the VPS through the relay in memory. **Add account** creates another separate profile on the VPS, **Manage account → Connect on VPS** brings an existing account label to it, and **Disconnect** removes one.
- **Updates.** The updater deploys the host with each release it activates. It checks the AppImage's signature and version like the installer's, installs the packages the host needs and is missing (Xvfb, xauth, dbus, sudo, curl, and the libraries the AppImage leaves to the system, such as ALSA, fontconfig, HarfBuzz, EGL and GLES, which a new server lacks), has `agent-studio-build` extract it in the sandbox without network, and asks the app whether it runs as a server (`--server-check`); releases from before server mode leave the host as it is. Before the first start it creates what else the host needs: the user, its sudo rule, Claude Code and Codex (with their own installers) and the unit. It restarts the host once no reply runs, waiting at most two hours, and a host that does not stay up for 20 seconds gives way to the previous version without being retried (`update.ts retry` tries it again). The switch is written to the host's `activation` in `state.json` before it is done (`switch`, then `back` when the version does not stay up), so an updater that ended between setting the link and restarting the host is taken up by the next check; that the link selects a version never counts as the host running it. A host counts as running a version (`hostRuns`) when the link selects it, the service is active with the process first seen and no restart of its own, and its processes show the version: a program of theirs lies in that version's folder (`/proc/<pid>/exe` of the processes in the unit's cgroup, which the real app's are), or, when none does, the service's main process began after the link was last changed (the unit's command names the link, which is resolved when it starts). A host an earlier updater had restarted on the version is watched for the 20 seconds and not restarted again. Not verified: that the app paired with the relay and takes work. The relay tells that only to a signed-in device (`POST /v1/heartbeat` registers one), and the updater does not sign in as a device; a host that runs and stays up but cannot reach the relay is therefore recorded as active, and shows as offline in Connections.
- **Settings.** `AGENT_STUDIO_UPDATE_HOST=off` runs no host; `AGENT_STUDIO_UPDATE_HOST_USER` (default `agent-studio-host`), `AGENT_STUDIO_UPDATE_HOST_SUDO=on` (default off) and `AGENT_STUDIO_UPDATE_HOST_NAME` (default `VPS`, used when the host first starts) choose the rest. Production sets the user and sudo in `/etc/systemd/system/agent-studio-update.service.d/host.conf`, which `install.sh` writes from `AGENT_STUDIO_HOST_USER`, `AGENT_STUDIO_HOST_SUDO`, `AGENT_STUDIO_HOST_NAME` and `AGENT_STUDIO_HOST` when given.
- **Status:** `systemctl status agent-studio-host`, `journalctl -u agent-studio-host` and the `host` entry of the updater's `state.json`. `systemctl disable --now agent-studio-host` stops it until the next release; `AGENT_STUDIO_UPDATE_HOST=off` keeps it stopped. A restart of the host ends the replies it runs, as quitting the app on a desktop does; the updater's restarts wait for running replies first. A host whose page stops answering for five minutes ends, and its service starts it again.

## Set up another server

[`scripts/vps/setup.sh`](../scripts/vps/setup.sh) sets up a new server the way this VPS runs (requested 2026-10-12): the relay and web viewer behind Caddy's HTTPS, the updater, and the server host. It needs an x86-64 Debian (or Debian-based) server running systemd, with ports 80 and 443 open. From a checkout, logged in as root over SSH (with a sudo user, put `sudo` before `bash`):

```sh
git -c core.autocrlf=false archive --format=tar HEAD scripts src-tauri/tauri.conf.json |
  ssh root@<server> 'dir=$(mktemp -d) && tar -x -C "$dir" && bash "$dir/scripts/vps/setup.sh" --domain <name> </dev/null; rm -rf "$dir"'
```

- **Options.** `--domain` is the HTTPS address, whose DNS must point at the server; without it, the server's public IPv4 address through sslip.io (`studio.<address>.sslip.io`), which needs no DNS record. `--host-user` (default `claude`), `--no-sudo` and `--name` (default `VPS`) choose the host as `AGENT_STUDIO_HOST_USER`, `_SUDO` and `_NAME` do, so the defaults match this VPS: the host runs as `claude` with passwordless sudo. `--no-host` sets up the relay alone.
- **What it does.** With the host, it first checks that systemd passes credentials to services, the way the host's service hands the app its pairing key; Docker containers cannot, so it stops there before changing anything and asks for `--no-host`. It installs curl, xz-utils, ca-certificates and Debian's Caddy when missing, and Node.js 24.20.0 under `/opt/agent-studio/runtimes`, checked against its published SHA-256. It creates the `agent-studio` user, `/var/lib/agent-studio`, a new pairing key in `/etc/agent-studio/relay.env`, and the relay's unit from [`agent-studio.service`](../scripts/vps/agent-studio.service), whose `memory.conf` drop-in lets Node's heap grow to the machine's memory. It adds the Caddy site, installs the updater with `install.sh`, and runs the updater once while showing its log, which installs the latest release as above and then the host. It waits for the host's computer to reach the relay, checks HTTPS, and prints the address and the command that shows the pairing key, never the key.
- **Running it again** keeps what is set up: the pairing key, the relay's unit, its data and releases stay, Caddy changes only with the domain, the updater is reinstalled from the copy given, with the options given, and a release or host that failed is tried again.

## Inspect and update

Read status with `systemctl status agent-studio` and logs with `journalctl -u agent-studio`. Do not print `relay.env` or `host.key`. The relay service holds no provider CLI credentials; the host's CLI logins are in the `claude` user's home, where its CLIs keep them.

The relay keeps each workspace in one `workspace.json`, which it writes and reads a conversation at a time ([`scripts/vps/state-file.ts`](../scripts/vps/state-file.ts), since 2026-11-13): one text of a file holds at most 536,870,888 characters, which the owner's 465 MB file was days from, and past it no change could have been saved and a restarted relay could not have read its data. The file is the same JSON document as before, so an earlier release still reads it while it is smaller than that. The whole-state routes answer the same way. The updater reads the file to count the replies still running before it activates a release, with the same module, which `install.sh` puts beside `update.ts`: an updater installed before 2026-11-13 reads the file as one text and stops activating releases once the file outgrows it, so reinstall it.

The relay loads each workspace whole when it starts, so its memory grows with the chats. It has no resource caps (requested 2026-10-10): only the machine's memory limits it, and when that runs out Linux ends the largest process, which may be another workload. Until then the service was capped at 512 MiB. Activating v0.8.1 on 2026-10-09 restarted it with a 61 MB `workspace.json` that no longer fit its 259 MB heap (startup peaks at 602 MB on v0.8.0 and 852 MB on v0.8.1), so the relay and its rollback logged `JavaScript heap out of memory` and restarted every few seconds for 21 hours: the Viewer stayed on sign-in with Server unavailable, desktops stopped syncing and the updater logged `Intervene manually`.

To deploy something other than a published release, pause the timer or hold the deployment lock. Build and test the final candidate before deployment. Create a new release directory, install dependencies using its lockfile, build the frontend, and run tests as an unprivileged user. Keep release files root-owned after building. Checksum source archives after transfer. Point `current` at the new release and restart only `agent-studio`. Keep the previous release for rollback. Never overwrite persistent data or generate a replacement pairing key as part of an ordinary update.

The single-admin upgrade writes version 2 of the private workspace registry at startup. Keep the pre-upgrade registry backup: older relay releases cannot read version 2. If startup fails and a rollback is needed, stop the service, restore only the registry from that private backup (or remove the new registry if none existed), then restart the previous release. Preserve the current chat and session files.

A restart preserves browser sessions when `/var/lib/agent-studio` and the pairing key are retained. Sessions are saved separately in `browser-sessions.json` with mode 0600 and keyed ID digests; keep it outside release directories and public assets. Pairing-key rotation invalidates these sessions. The first upgrade from the older memory-only implementation requires devices to pair once again; subsequent releases retain them. Unreadable session files fail startup without overwriting the file.

Transient relay jobs still do not survive a restart; check for active replies and coordinate maintenance before restarting. Durable workspace checkpoints and push-delivery queues survive. Back up `/var/lib/agent-studio/workspace.json`, `browser-sessions.json`, `web-push.json`, the `images/` store, and the pairing configuration with restricted access, keeping pairing configuration separate. A relay with the image store moves the images saved inside a `workspace.json` into that workspace's `images/` store when it first loads the workspace, and keeps the previous file beside it as `workspace-before-images.json`; earlier releases cannot read the references that replace them, so a manual rollback past it restores that file (images sent since are lost to it). `web-push.json` contains private VAPID signing material and push subscriptions; retain it across releases and never serve or export it. The relay creates it automatically, so no new environment secret is required. A scheduled/off-server backup is not configured by this deployment.

Validate a Caddy change before reloading with `caddy validate --config /etc/caddy/Caddyfile`. Use `systemctl reload caddy` rather than stopping it: the VPS also serves `deck.simpx.net`. The `deck-server`, `minecraft`, and `atm10sky` services belong to other workloads and must remain untouched.
