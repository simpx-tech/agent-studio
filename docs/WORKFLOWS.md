# Workflows

Workflows automate work across chats, agents, accounts and computers (requested 2026-10-16). They come in two modes, shown in the same 2D graph:

- A **static workflow** is a graph of steps you or an agent draw and edit, like n8n or Make: start a chat with an agent, send a message to a chat, read a chat's history, branch on a condition, loop over items, wait, ask you, ask you to approve, notify you, set values, build or use a screen, run another workflow. Each run starts at one of its triggers and follows the graph.
- A **mission** (a dynamic workflow) gives an orchestrator agent a goal. The orchestrator plans, spawns agents on the computers and accounts it chooses, reviews their work, asks you when it needs to, keeps shared notes and drives the work until the mission is complete, over as many sessions, computers and days as it takes. Its plan and every agent it starts appear live in the graph.

Both keep a history of what happened. The **Workflows** row above the sidebar's Active, History and Screens tabs (requested 2026-10-17; a quiet row like a chat's since 2026-10-19) opens the Workflows page (`WorkflowsHome.svelte`): what waits for you, what runs (runs and missions, with what they do now, where and for how long), your workflows as cards (description, triggers, last run) and recent runs, with a search and **New**. The row counts what is in progress, in the warning colour while something waits for you, and stays marked while a workflow, its chat or a run is open. There is no slash command, since Claude Code's own `/workflows` is a different feature.

These are Agent Studio's own workflows. Claude Code's native Dynamic Workflows (its `Workflow` tool, run inside one Claude chat) are unrelated and work as before ([CAPABILITIES.md](CAPABILITIES.md)).

## Workflows start from a chat

**New** on the Workflows page opens a new chat whose welcome chooses **Workflow** or **Mission** (the kind chosen last) under its heading, with the usual Computer, Folder, Agent, Model and Reasoning controls. Workflow chats start with Claude at its maximum reasoning, then with the agent, account, model and reasoning chosen last in a workflow chat or step, kept on this device (`src/lib/workflow-preferences.ts`) apart from the choices new chats remember. The first message creates the workflow or mission (`bindWorkflowChat` in `+page.svelte`):

- **Workflow**: a new workflow, named from the message's first line, and the chat becomes its **assistant**, an agent told which workflow it changes (`assistantInstructions` in `src/lib/workflow-prompts.ts`). It builds and changes the graph with the workflow tools while you watch, and you keep talking to it as in any chat.
- **Mission**: the message is the mission, and the chat becomes its orchestrator, whose role and rules are its instructions (`ORCHESTRATOR_INSTRUCTIONS`). A **Runs on** button beside the composer chooses where it runs; one another computer runs starts its orchestrator chat there, and the mission opens as a page until that chat arrives.

The chat of a workflow or mission is named by it and shows its graph in a panel beside it (`WorkflowPanel.svelte`). On wide windows the panel is docked and keeps its share of the space as the window grows or shrinks (half at first; dragging or the arrow keys on its divider change it, remembered on this device: requested 2026-10-19). On narrow windows it waits behind a bar above the chat, which would otherwise be covered, and opens from it as a drawer. **Expand** shows it as a page of its own, whose chat button returns to the chat; closing the panel leaves the bar. Opening a workflow from the Workflows page opens its assistant chat (a new one, if it has none yet), a mission its orchestrator's current chat, and a run of a saved workflow that workflow's chat with the run in its panel; a run whose workflow is gone opens as a page. Messages the engine writes in a chat, such as a mission's updates, show as **Workflow** updates rather than your own messages (`sentBy: 'workflow'`); a mission update lists its events one a line before the agents' replies, and its summary names the first without the chat ids written for the orchestrator.

## Static workflows

The workflow's panel or page shows its **Graph** or its **Runs**. The graph flows from top to bottom (requested 2026-10-19, `src/lib/workflow-layout.ts`): a step's next steps go below it, its branches side by side in its ports' order (True before False, Approved before Rejected, each before done), its error branch leaves from its side, shown once connected or while the step is selected or hovered, and a connection that skips rows takes a lane beside the steps between instead of running behind them (`edgeDetour`, `WorkflowEdge.svelte`). A graph laid out from left to right before is laid out again when opened, and one too big to read whole shows its top at a readable size. It is edited beside the assistant chat or on its page: **Add step**, over the graph, adds a step below the one selected; dragging a connection from a step's output to empty space opens the step menu there and connects the new step; **Arrange** lays the steps out again. Selecting a step opens its settings over the graph's right side (beside it on a wide page); **Workflow settings** hold the description, where its triggered runs run, what keeps it from running (also named in the header, which opens them) and **Delete workflow**. Your edits save by themselves a moment later. When the assistant saved meanwhile, they are merged over its save (`mergeDefinition` in `src/lib/workflow-merge.ts`): each field, step and connection takes the side that changed it, a step both changed takes each of its fields that way with yours winning where both changed one, a step either side deleted stays deleted, and a step you added under a key the other side took gets a key of its own. **Run** starts a run at once when there is nothing to choose (one trigger without inputs, one computer to run on); otherwise it asks for the trigger, its inputs and the computer. The run then shows in the workflow's place, live, with Back to the **Runs**, which list the workflow's runs, newest first, with what started each and how long it took.

### Triggers

Each Trigger step starts its own runs (requested 2026-10-17, `triggerKinds`), and its card shows its kind's icon:

| Trigger     | Starts a run when                                                                                                                     | Hands over (`{{trigger.json}}`)                                      |
| ----------- | ------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------- |
| Manual      | you press Run, or an agent calls `workflow_run`. Its inputs keep their defaults whichever trigger starts the run.                     | its inputs                                                           |
| Schedule    | a slot of one of its schedules comes (every N minutes or hours, daily at a time, weekly on chosen days, in the editor's time zone)    | `scheduledFor`                                                       |
| Chat        | a reply ends, fails or stops, or asks you something, in a chat that matches its computer, folder, agent and title (empty matches any) | the chat, its event, the reply's text or error, its agent and folder |
| Workflow    | a run of a chosen workflow, or of any other workflow or mission, completes, fails or is stopped                                       | the run, its title, status and kind                                  |
| Webhook     | its URL on the relay receives a POST                                                                                                  | the request's JSON body, or `{ body }` for other text                |
| Computer    | a computer, or any, comes online or goes offline                                                                                      | the computer and the event                                           |
| Usage reset | an account, or any account, has room again after reaching its 5-hour or weekly limit                                                  | the account                                                          |

The computer that runs a workflow's triggered runs watches its triggers (`src/lib/workflow-triggers.ts`). What it saw when it began watching starts nothing, so a restart never replays the past. Each event has a key, and the run it starts an id derived from it (as a schedule's slot does), so two computers seeing one event start one run. Chats workflows start never fire a chat trigger unless it asks for them, and a workflow trigger never fires on runs of its own workflow unless it names it. A schedule starts with the slots after it was set (its `since`, which the editor and `workflow_save` set when a schedule is added and keep after), so a slot earlier that day never starts a run at once; a computer that was off starts the latest missed slot once, when it is less than a day old. A deleted run stays deleted: the store never accepts its id again.

A webhook's URL is `<relay>/v1/hooks/<workflow>/<trigger step>/<secret>` (`startFromHook` in `relay/workflows.ts`). The relay checks the secret before reading the request, limits requests whose address names no webhook as it limits pairing attempts, and records a pending run, which the computer that runs the workflow builds from the workflow as saved and drives. **New URL** makes another secret. Webhooks need a relay with the workflow store.

A step's text fields are templates: `{{input.topic}}` is a manual trigger's input, `{{trigger.output}}` and `{{trigger.json.path}}` what the trigger that started the run handed over, `{{research.output}}` the output of the step whose key is `research`, `{{research.json.items}}` a part of its JSON, `{{research.chat}}` its chat's id, `{{item}}` and `{{index}}` the current loop item, `{{previous.output}}` what the step before handed over, and `{{run.title}}`, `{{now}}`. The step settings list what is available. Each step has a key (letters, digits and `_`), unique in its workflow.

When a step fails, its **If it fails** setting stops the run, continues as if it succeeded, or follows its **error** port (also taken whenever that port is connected), after the retries it allows. An interrupted reply (the app closed, its computer went away) and a reply stopped at a usage limit never count as failures: the step waits and runs again.

Runs follow the graph as tokens: when a step ends it hands its output to each step its chosen port connects to, and every such hand-over runs that step once, so several outgoing connections run branches in parallel and a connection back to an earlier step repeats it (a review loop). A Merge step joins branches. A loop item ends when nothing of it is still queued, running or waiting, so its steps need no connection back to the loop. A run completes when nothing is left to do, and fails when a step that stops the run fails. A finished run lists each of its chats as done, failed or stopped.

A run keeps a copy of the definition it started with, so editing a workflow never changes runs already going.

## Missions

A mission starts from a chat (above). From then on the orchestrator manages everything through its mission tools:

- `mission_state` returns the mission, the plan, every agent and its status and result, the notes, open questions, timers, the computers with their online state and folders, and every account with its 5-hour and weekly usage, pace and resets.
- `mission_plan` adds, changes or removes plan tasks (title, description, status, dependencies, phase), which the graph shows live.
- `mission_spawn` starts an agent: a new chat with its task, on the computer, folder, agent, account, model and reasoning it chooses (the least used account when it names none), with the mission and notes included unless told otherwise. It returns at once; the agent may wait for its computer, sign-in or usage first.
- `mission_message` sends a chat (an agent's or any other) its next message or a steer; `mission_stop` stops a chat's reply; `mission_read` reads its latest reply, last messages or whole history; `mission_chats` lists the workspace's chats.
- `mission_ask` asks you questions without blocking: other work goes on, and your answer arrives as an event.
- `mission_note` writes, changes or deletes shared notes: decisions, conventions, progress, learnings. Notes outlive sessions and are how any later session or agent continues.
- `mission_wait` sets a timer, such as a usage reset.
- `mission_screen` runs an allowed screen action or loads or saves a screen's data; the orchestrator also has `save_screen` for its own screens.
- `mission_run_workflow` runs a static workflow; `mission_complete` ends the mission with a summary.

The orchestrator works in turns. After starting work it ends its turn, and the engine wakes it with a message listing what happened since (an agent finished, with its reply; an answer arrived; a timer fired; a computer went offline or came back; a usage limit reset; you wrote a note or resumed the mission). You can also write to it in its chat at any time: its instructions treat your messages as instructions and feedback for the mission. A turn that leaves nothing running, waiting or scheduled is followed by a reminder, at growing intervals, so a mission never just stops. A reply that fails is retried after a growing wait, each failure counting once; three in a row start a new session. Its instructions ask for the most complete, professional result: plan, iterate with separate reviewers, never shortcut, use time freely, and pace by the accounts' limits, slowing down near them but never stopping because of them.

The graph shows the orchestrator, each plan task with its dependencies, and inside each task the agents that worked on it, each with its status and what it is doing now (Running `npm test`, Writing, Thinking), read from its chat. Questions and timers appear beside the orchestrator. Selecting an agent opens its details; opening it shows its chat. In the panel, the run's details open with **Details**, and by themselves when it asks you something.

## Chats a workflow creates

Every chat a workflow starts is an ordinary conversation on its computer: it syncs, its reply runs and is saved as any other, and you can open it from the graph, read it and type into it (a message of yours never completes the step that started the chat). Workflow chats, assistant and orchestrator chats included, stay out of the Active and History lists, the pending badge and chat alerts, unless an Agent step lists them; the run or workflow names them (`conversations` in its summary). A chat a workflow step or agent uses shows **Workflow · title** above it, which opens the workflow. A worker's process is released when its reply ends, since a mission may start hundreds, and an orchestrator's once the reply that ended its session or mission ends; the next message resumes its native session.

Deleting a finished run can delete its chats too, and deleting a workflow its assistant chat.

## Usage and limits

Before a step or mission agent starts a reply, the engine checks the account: a 5-hour or weekly limit at 100%, or a refusal at a usage limit, makes it wait until the reset the account reports (re-reading the account, and again every 15 minutes while no reading tells), then go on. An account that needs sign-in, or a computer that is offline, makes it wait and say so. Without a chosen account, the step takes the least used ready account of that agent on that computer (`src/lib/account-balance.ts`), and an exhausted one gives way to another with room. The orchestrator's own account works the same way: at a limit it waits, or continues with another account of its agent on the driving computer that has room.

Nothing in a workflow is capped by count, size or time: steps, triggers, agents, loops, notes, history and runs may grow as the work needs, and a run goes on until it ends or you stop it.

## Where workflows live

Definitions and runs are documents in the **workflow store**, never in the workspace: a run changes every few seconds while it works and its history grows for days, and the workspace syncs as one document. The store keeps each document with a revision, an append-only history per run, and the lease of the computer driving each run (`src/lib/workflow-store.ts`):

- Paired with a relay that has the store (its revision answer says `workflows`), every device reads and writes it there (`relay/workflows.ts`: `POST v1/workflows/list`, `POST v1/workflows/read`, `PUT v1/workflows/<id>`, `POST v1/workflows/<id>/delete`, `POST v1/workflows/<id>/lease`, and the webhook route above), under the workspace's own data directory, so it is shared across computers and reachable while any one of them is off. A change bumps the store revision the relay's poll already reports, so other devices notice it without another request.
- Unpaired, or paired with a relay without the store, a desktop keeps its own store in app data `workflows/` through native file commands, and moves its documents up once it meets a relay with the store. The Viewer needs the relay's store, so a relay released before workflows shows the Viewer none, and runs stay on the computer that started them until the relay is updated.

Writes are compare-and-set on the document's revision. A conflicting write of a run merges both sides (`mergeRun`): commands, questions, notes, tasks, agents and steps by id, each by its own revision, so the driver's progress, your answers, commands and notes never overwrite each other. A definition saved over a newer revision is merged as described above. A workflow's summary names its assistant chat, and a mission's its orchestrator's current chat (`chat`).

## Which computer drives a run

One desktop page (a desktop app or a server host, never the Viewer) drives each active run: it holds the run's lease, renewed every 15 seconds for 60, and executes it. A run has **Runs on**, the computer it prefers (the VPS's server host included), and **Continue on**, the computers that may take it over while that one is offline (every other one by default; `DriverPicker.svelte`), chosen when it starts and changeable in its details while it runs; a workflow's settings choose them for its triggered runs. When the driver's lease lapses (the computer slept, closed or lost its connection) and the preferred computer is offline, a computer it may continue on claims it, servers at once and desktops after 30 seconds; after two minutes without a driver any of them claims it. Triggers follow the same choice: the computer a workflow runs on watches them, and while it is offline one it may continue on (servers, when it names none). The new driver reconciles the run from what it can see (each step's and agent's chat, its reply's status), continues waits and timers, and for a mission starts a new orchestrator session on its own computer, briefed with the mission, plan, agents, notes, questions and recent history. Agents keep running where they run; replies another computer runs go on without the computer that requested them. A driver that cannot renew its lease stops starting work until it can, so two computers never drive one run. Other computers, the VPS included, are listed only on a device paired with the relay.

## Agent tools

Every Claude and Codex chat with tools gets the workflow tools, Claude through the `agent_studio` SDK server (`mcp__agent_studio__workflow_save`, …) and Codex as dynamic tools (`src-tauri/src/providers/workflow_calls.rs`): `workflow_list`, `workflow_read`, `workflow_save` (create or replace a definition: nodes, edges, triggers; the description documents every step), `workflow_run` (at its first manual trigger or one it names), `workflow_status` and `mission_start`. An orchestrator chat also gets the mission tools above. Only the conversation's own call reaches them (Claude's registered parent tool use, Codex's parent thread without a namespace).

The executing computer's own page answers them: the host sends each call to its window (`studio-workflow-call`), the page acts through the store and the engine, and `answer_workflow_call` returns the result to the CLI, as an answered question does. A reloaded page picks up calls still waiting (`pending_workflow_calls`); a reply that ends leaves its waiting calls unanswered and refuses late answers. Mission tools answer only the current orchestrator of a run this page drives (a mission started here a moment ago is waited for while it is being claimed); another session hears where the mission continues. A run request names its mission role (`mission`: the run and `orchestrator`), which is part of the parked-process identity, since it changes the tools.

## Notifications

A question of a run, a Notify step and a run's end alert you once on each desktop (device-local receipts) and on paired phones through the relay, with the workflow's title and one line. Chat alerts of workflow chats stay quiet; a question a worker asks in its own chat still alerts.
