# Workflows

Workflows automate work across chats, agents, accounts and computers (requested 2026-10-16). They come in two kinds, shown in the same 2D graph:

- A **static workflow** is a graph of steps you or an agent draw and edit, like n8n or Make: start a chat with an agent, send a message to a chat, read a chat's history, branch on a condition, loop over items, wait, ask you, ask you to approve, notify you, set values, build or use a screen, run another workflow. Each run starts at one of its triggers and follows the graph.
- A **dynamic workflow** gives an orchestrator agent a goal. The orchestrator plans, spawns agents on the computers and accounts it chooses, reviews their work, asks you when it needs to, keeps shared notes and drives the work until the goal is reached, over as many sessions, computers and days as it takes. Its plan and every agent it starts appear live in the graph. (Saved runs and the code still call a dynamic workflow a mission: `mission` in a run, `src/lib/workflow-mission.ts`. The interface says static and dynamic, as requested on 2026-10-19.)

Both keep a history of what happened, step by step. The sidebar has two modes, switched by the **Agent** and **Workflow** tabs under its wordmark (requested 2026-10-20, in place of a Workflows row that unfolded the list, which had replaced a Workflows page): Agent shows the Active, History and Screens tabs and their lists, with the pending chats badge, and Workflow the list of your workflows in their place, however many there are: each saved workflow and each dynamic workflow you started, the newest first, with its kind's icon and, while it runs, the time it has run (the question mark while it waits for your answer, a pause mark while paused). The sidebar's search filters the list of the mode shown, and the workflow on screen is marked. The Workflow tab counts what is in progress, in the warning colour while something waits for you. The mode follows what is on screen (a workflow's graph, its chats and its run pages are Workflow's, every other chat Agent's), and switching returns to what the mode showed last, while it is still there, else to a new chat or a new workflow chat; on a phone the drawer stays open on the list of the mode it switched to. The **+** beside the tabs starts a chat in Agent and a workflow in Workflow. Runs in progress also lead the Active tab (below). There is no slash command, since Claude Code's own `/workflows` is a different feature.

## Compared with Claude Code's Dynamic Workflows

Claude Code's native Dynamic Workflows (its `Workflow` tool and the scripts in `.claude/workflows`) run inside one Claude chat: one CLI session on one computer and one account, for as long as that reply and its background work last, with progress shown in that reply ([CAPABILITIES.md](CAPABILITIES.md)). They are unrelated to these workflows and work as before.

Agent Studio's workflows live outside any one chat or process. A run is a document of the workflow store that any desktop of the workspace can drive and hand over (the VPS's server host included), so it survives restarts, sleep and offline computers, and can last days. Its agents are ordinary chats with Claude, Codex or Gemini, on any computer and any account, chosen by usage and limits. Runs start from triggers (schedules, chats, other runs, webhooks, computers, usage resets), wait for answers and approvals, keep notes, call other workflows, and show as a live graph with a history. A static workflow's steps are a graph you edit; a dynamic workflow's orchestrator decides its steps as it goes, across as many orchestrator sessions as it needs.

## Workflows start from a chat

The Workflow mode's **+** opens a new chat whose welcome chooses **Static** or **Dynamic** (the kind chosen last) under its heading, with the usual Computer, Folder, Agent, Model and Reasoning controls. Beside it, from the start, lies the graph the workflow starts with (requested 2026-10-20, `WorkflowDraft.svelte`): a static workflow's manual trigger, or a dynamic one's orchestrator with the computer and account it will run on, following the choices beside the composer. The chat stays open beside it, without its **×**, and the first message puts the workflow's own graph in its place, where the new one was. Workflow chats start with Claude at its maximum reasoning, then with the agent, account, model and reasoning chosen last in a workflow chat or step, kept on this device (`src/lib/workflow-preferences.ts`) apart from the choices new chats remember. The first message creates the workflow (`bindWorkflowChat` in `+page.svelte`):

- **Static**: a new workflow, named from the message's first line, and the chat becomes its **assistant**, an agent told which workflow it changes (`assistantInstructions` in `src/lib/workflow-prompts.ts`). It builds and changes the graph with the workflow tools while you watch, and you keep talking to it as in any chat.
- **Dynamic**: the message is the goal, and the chat becomes its orchestrator, whose role and rules are its instructions (`ORCHESTRATOR_INSTRUCTIONS`). A **Runs on** button beside the composer chooses where it runs; one another computer runs starts its orchestrator chat there, and the workflow opens as a page until that chat arrives.

A chat of yours becomes a workflow from its toolbar too (requested 2026-10-19): **Make a workflow** in a Claude or Codex chat offers **Static**, which saves a new workflow named by the chat, makes the chat its assistant and asks it to build the workflow from what you discussed (`STATIC_FROM_CHAT` in `src/lib/workflow-prompts.ts`), and **Dynamic**, available while the chat runs on this computer, which starts a dynamic workflow whose goal is your last message there and makes the chat its orchestrator (`DYNAMIC_FROM_CHAT`; `workflowFromChat` in `+page.svelte`). The chat keeps its messages and its own instructions, leaves the Active and History lists, and shows the workflow's graph. A chat that belongs to a workflow offers neither Move to history nor Snooze.

A workflow's chat is named by it. A workflow, static or dynamic, shows its graph in the chat's place, and its chat (a static workflow's assistant, a dynamic one's orchestrator) as a card at the graph's left only when you want it (requested 2026-10-19): **Chat** in the graph's header opens and closes it, the card's **×** closes it, and a workflow opens with its chat closed, except a new one, before and right after its first message, and one a chat just became. The card is the whole chat, its toolbar of computer, folder, agent, model and reasoning included, whose actions fold into **…** while the card is narrow (`chat-area` container), and the gap between it and the graph resizes it by pointer or arrow keys, an invisible handle but for its cursor, keeping its share of the space as the window grows or shrinks (36% at first, remembered on this device; `PanelResize` with `gutter` and `side`). On narrow windows the open card covers the graph. Opening a workflow from the sidebar opens it on its graph (a static workflow's chat, a new one if it has none yet, waits for **Chat**), and a run of a saved workflow on that workflow's graph with the run in its place; a run whose workflow is gone, or a dynamic workflow another run started, opens as a page. The chats a run started open in the card, the window then named by that chat, with **Assistant** or **Orchestrator** to go back (requested 2026-10-19). Messages the engine writes in a chat, such as a dynamic workflow's updates (`[Workflow update]`), show as **Workflow** updates rather than your own messages (`sentBy: 'workflow'`); an update lists its events one a line before the agents' replies, and its summary names the first without the chat ids written for the orchestrator.

## One view: the graph, its runs and their history

A static workflow's graph has one header (requested 2026-10-19: the tabs and the run's own tabs made too many steps): its name and what keeps it from running, **Run**, the **Runs** picker, settings and **Chat**; a run's header has **History** in place of the settings. **Run** starts a run at once when there is nothing to choose (one trigger without inputs, one computer to run on); otherwise it asks for the trigger, its inputs and the computer. The run then shows in the workflow's place, live, with a back arrow to the graph. **Runs** lists the workflow's runs, newest first, with how each ended or what it does, how long it took and what started it, and opens one in place; in a run it moves to another.

A run, static or dynamic, shows its graph, and its history as a column beside it only on demand (requested 2026-10-19: **History** in the header opens and closes it, and so does its **×**; choosing a card on the graph opens it on that card's entries, and something new the run waits for you on opens it, the button counting what waits; the column narrows beside a narrow graph and covers the graph only where there is no room for both; `WorkflowRunPanel.svelte`):

- **Waiting for you** at the top: the run's questions and approvals (an Ask or Confirm step, an orchestrator's question) and what the chats of its agents ask (their questions, plan approvals and MCP forms), each answerable there, with the agent's name and its chat.
- What it set out to do and what came of it: a dynamic workflow's goal or a static run's inputs, its result once it ended, when it started, how long it took and where it runs (**Change** moves it while it runs), and its **Notes**.
- **History**: every step as it ran, in order and numbered, a loop's items (Item 2) and steps a run returned to (Again) each in their own entry (`staticTimeline` in `src/lib/workflow-view.ts`), with the run's own events (pauses, a computer taking over, its end). A dynamic workflow's history is what it recorded: sessions, plan changes, agents started and finished, questions, notes, timers, other workflows, computers and usage (`dynamicTimeline`). Each entry opens on what it did: a step's input and output, error, attempts and duration, Retry and Skip, its chat or the run it started; an agent's task or the reply it finished with. A followed history stays at its end as entries arrive. Choosing a card on the graph shows its entries alone, and choosing an entry shows its card.

The graph marks what ran: a step or task done, skipped (a muted check: settled without running), failed or stopped, and once a run ends, the steps it never reached and the tasks it never began fade back. When a dynamic workflow completes, its plan settles: a task whose agents all finished is done, and one still going is cancelled.

## Static workflows

The graph flows from top to bottom (requested 2026-10-19, `src/lib/workflow-layout.ts`): a step's next steps go below it, its branches side by side in its ports' order (True before False, Approved before Rejected, each before done), its error branch leaves from its side, shown once connected or while the step is selected or hovered, and a connection that skips rows takes a lane beside the steps between instead of running behind them (`edgeDetour`, `WorkflowEdge.svelte`). A graph laid out from left to right before is laid out again when opened, and one too big to read whole shows its top at a readable size. It is edited where it shows, its assistant's chat beside it while open: **Add step**, over the graph, adds a step below the one selected; dragging a connection from a step's output to empty space opens the step menu there and connects the new step; **Arrange** lays the steps out again. Selecting a step opens its settings beside the graph, wider when there is room (over its right side when narrow); the gap between the graph and the panel at its right (a step's settings, the workflow's, a run's history) resizes that panel, which keeps one width for all three on this device (requested 2026-10-19); **Workflow settings** hold the description, where its triggered runs run, what keeps it from running (also named in the header, which opens them) and **Delete workflow**. An Agent or Screen step, and a Run workflow step's orchestrator, may take **Same as workflow chat** as their account (requested 2026-10-19, `WORKFLOW_ACCOUNT`): the account of the orchestrator of the nearest dynamic workflow that started the run, else of the workflow's assistant (or the nearest one up the runs that started it), where that account is connected on the step's computer for the step's agent, else the least used one (`workflowAccount` in `src/lib/workflow-engine.ts`). Your edits save by themselves a moment later. When the assistant saved meanwhile, they are merged over its save (`mergeDefinition` in `src/lib/workflow-merge.ts`): each field, step and connection takes the side that changed it, a step both changed takes each of its fields that way with yours winning where both changed one, a step either side deleted stays deleted, and a step you added under a key the other side took gets a key of its own.

A right-click on the graph opens a menu where it was pressed (requested 2026-10-19): on empty space, the steps to add there, **Arrange** and **Fit to view**; on a step, **Settings**, **Duplicate** (a copy beside it with a key, schedule ids and webhook address of its own) and **Delete**, disabled for a workflow's last trigger; on a connection, **Delete connection**; and on a run's card, its chat, its history and the run it started. The menu takes the keyboard (the arrows, Home and End move through it, Escape closes it and gives focus back) and closes on a press elsewhere.

The settings' text fields show each `{{…}}` value in the colour of what it names (requested 2026-10-19; `TemplateField.svelte`, `templateParts` in `src/lib/workflow-templates.ts`): an input, the trigger, the previous step, another step by its key, a loop's item or index, or the run, with a wavy red underline for one that names no step; the values offered for insertion below carry the same colours. A Set step lists each value as a card, its name and **JSON** on one line and its value below it across the settings, growing with its text. **Starts when** shows each kind of trigger with its icon.

### Triggers

Each Trigger step starts its own runs (requested 2026-10-17, `triggerKinds`), and its card shows its kind's icon:

| Trigger     | Starts a run when                                                                                                                     | Hands over (`{{trigger.json}}`)                                      |
| ----------- | ------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------- |
| Manual      | you press Run, or an agent calls `workflow_run`. Its inputs keep their defaults whichever trigger starts the run.                     | its inputs                                                           |
| Schedule    | a slot of one of its schedules comes (every N minutes or hours, daily at a time, weekly on chosen days, in the editor's time zone)    | `scheduledFor`                                                       |
| Chat        | a reply ends, fails or stops, or asks you something, in a chat that matches its computer, folder, agent and title (empty matches any) | the chat, its event, the reply's text or error, its agent and folder |
| Workflow    | a run of a chosen workflow, or of any other workflow, static or dynamic, completes, fails or is stopped                               | the run, its title, status and kind (`static` or `dynamic`)          |
| Webhook     | its URL on the relay receives a POST                                                                                                  | the request's JSON body, or `{ body }` for other text                |
| Computer    | a computer, or any, comes online or goes offline                                                                                      | the computer and the event                                           |
| Usage reset | an account, or any account, has room again after reaching its 5-hour or weekly limit                                                  | the account                                                          |

The computer that runs a workflow's triggered runs watches its triggers (`src/lib/workflow-triggers.ts`). What it saw when it began watching starts nothing, so a restart never replays the past. Each event has a key, and the run it starts an id derived from it (as a schedule's slot does), so two computers seeing one event start one run. Chats workflows start never fire a chat trigger unless it asks for them, and a workflow trigger never fires on runs of its own workflow unless it names it. A schedule starts with the slots after it was set (its `since`, which the editor and `workflow_save` set when a schedule is added and keep after), so a slot earlier that day never starts a run at once; a computer that was off starts the latest missed slot once, when it is less than a day old. A deleted run stays deleted: the store never accepts its id again.

A webhook's URL is `<relay>/v1/hooks/<workflow>/<trigger step>/<secret>` (`startFromHook` in `relay/workflows.ts`). The relay checks the secret before reading the request, limits requests whose address names no webhook as it limits pairing attempts, and records a pending run, which the computer that runs the workflow builds from the workflow as saved and drives. **New URL** makes another secret. Webhooks need a relay with the workflow store.

A step's text fields are templates: `{{input.topic}}` is a manual trigger's input, `{{trigger.output}}` and `{{trigger.json.path}}` what the trigger that started the run handed over, `{{research.output}}` the output of the step whose key is `research`, `{{research.json.items}}` a part of its JSON, `{{research.chat}}` its chat's id, `{{research.run}}` the run a Run workflow step started, `{{item}}` and `{{index}}` the current loop item, `{{previous.output}}` what the step before handed over, and `{{run.title}}`, `{{now}}`. The step settings list what is available. Each step has a key (letters, digits and `_`), unique in its workflow.

When a step fails, its **If it fails** setting stops the run, continues as if it succeeded, or follows its **error** port (also taken whenever that port is connected), after the retries it allows. An interrupted reply (the app closed, its computer went away) and a reply stopped at a usage limit never count as failures: the step waits and runs again.

Runs follow the graph as tokens: when a step ends it hands its output to each step its chosen port connects to, and every such hand-over runs that step once, so several outgoing connections run branches in parallel and a connection back to an earlier step repeats it (a review loop). A Merge step joins branches. A loop item ends when nothing of it is still queued, running or waiting, so its steps need no connection back to the loop. A run completes when nothing is left to do, and fails when a step that stops the run fails. A finished run lists each of its chats as done, failed or stopped.

A run keeps a copy of the definition it started with, so editing a workflow never changes runs already going.

## Workflows calling workflows

A **Run workflow** step (requested 2026-10-19) runs either a saved static workflow, given values for its manual trigger's inputs, or a dynamic workflow with a goal of its own (a template, so earlier steps can fill it in), a title, and its orchestrator's computer and folder, agent, account, model and reasoning, as an Agent step chooses them. With **Wait for it to end** (the default) the step waits and continues with the other run's result: its End step's output, or the dynamic workflow's summary, as `{{key.output}}`, and as `{{key.json…}}` when that text is JSON; a run that fails or stops fails the step, whose error port can take it. Without waiting, the step continues at once with the run's id. `{{key.run}}` names the run either way. A retried step starts another run once the earlier one ended.

A dynamic workflow's orchestrator does the same with `dynamic_run_workflow`: a saved workflow by id with its inputs, or a child dynamic workflow with a goal (and optionally a title, folder and orchestrator, else its own folder and choice); with `wait` its result arrives with a later turn.

The run another run starts names it as its parent (`parent` in the run), runs where its parent runs and may continue where its parent may, and opens from the step's card or from its history entry. It is not listed in the Active tab on its own, since its parent stands for it, and a dynamic workflow another run started has no chat of yours: its orchestrator's chats are the workflow's too.

## Dynamic workflows

A dynamic workflow starts from a chat (above), from a Run workflow step or another orchestrator, or from an agent's `dynamic_start`. From then on the orchestrator manages everything through its tools:

- `dynamic_state` returns the goal, the plan, every agent and its status and result, the notes, open questions, timers, the computers with their online state and folders, and every account with its 5-hour and weekly usage, pace and resets.
- `dynamic_plan` adds, changes or removes plan tasks (title, description, status, dependencies, phase), which the graph shows live.
- `dynamic_spawn` starts an agent: a new chat with its task, on the computer, folder, agent, account, model and reasoning it chooses (the least used account when it names none), with the goal and notes included unless told otherwise. It returns at once; the agent may wait for its computer, sign-in or usage first.
- `dynamic_message` sends a chat (an agent's or any other) its next message or a steer; `dynamic_stop` stops a chat's reply; `dynamic_read` reads its latest reply, last messages or whole history; `dynamic_chats` lists the workflow's chats, or every chat of the workspace.
- `dynamic_ask` asks you questions without blocking: other work goes on, and your answer arrives as an event.
- `dynamic_note` writes, changes or deletes shared notes: decisions, conventions, progress, learnings. Notes outlive sessions and are how any later session or agent continues.
- `dynamic_wait` sets a timer, such as a usage reset.
- `dynamic_screen` runs an allowed screen action or loads or saves a screen's data; the orchestrator also has `save_screen` for its own screens.
- `dynamic_run_workflow` runs another workflow (above); `dynamic_complete` ends the workflow with a summary.

The orchestrator works in turns. After starting work it ends its turn, and the engine wakes it with a message listing what happened since (an agent finished, with its reply; an answer arrived; a timer fired; a computer went offline or came back; a usage limit reset; another workflow ended; you wrote a note or resumed the workflow). You can also write to it in its chat at any time: its instructions treat your messages as instructions and feedback. A turn that leaves nothing running, waiting or scheduled is followed by a reminder, at growing intervals, so a dynamic workflow never just stops. A reply that fails is retried after a growing wait, each failure counting once; three in a row start a new session. Its instructions ask for the most complete, professional result: plan, iterate with separate reviewers, never shortcut, use time freely, and pace by the accounts' limits, slowing down near them but never stopping because of them.

The graph shows the orchestrator, each plan task with its dependencies, and inside each task the agents that worked on it, each with its status and what it is doing now (Running `npm test`, Writing, Thinking), read from its chat. Questions and other workflows appear beside the orchestrator.

## Chats a workflow creates

Every chat a workflow run starts (an Agent or Screen step's, an orchestrator's agents, its sessions after the first, a child dynamic workflow's) belongs to that run (requested 2026-10-19): it stays out of the Active and History lists and the pending badge, raises no alerts of its own, and is the workflow's to drive. You read it from the graph or the history: it shows without a composer, Rewind, Retry, Fork, Snooze or settings, with **Part of** its workflow in the composer's place and, when the workflow has a chat of yours, **Assistant** or **Orchestrator** to return to it (`readOnly` in `src/lib/workflow-client.svelte.ts`). What it asks you is the run's: its question shows with the run (also in the chat's own reply), the run counts it among its questions and alerts once under the workflow's title. The chat stays an ordinary conversation on its computer: it syncs, its reply runs and is saved as any other. Chats that runs before 2026-10-19 listed because an Agent step or an orchestrator asked (`listed`) belong to their run too.

Two chats stay yours to write in, also kept out of the lists: a static workflow's assistant, and the chat you started a dynamic workflow in (its current orchestrator), whose alerts end quietly while the run reports what matters. A chat of yours a dynamic workflow writes to with `dynamic_message` stays yours, listed and answering you, with **Workflow · title** above it. A worker's process is released when its reply ends, since a dynamic workflow may start hundreds, and an orchestrator's once the reply that ended its session or workflow ends; the next message resumes its native session.

Deleting a finished run can delete its chats too, and deleting a workflow its assistant chat.

## Running workflows in the Active list

While a run you or a trigger started is running or paused, it leads the Active tab, above snoozed chats and the computers (requested 2026-10-19), as a row with its kind's icon and title and the time it has run (the question mark while it waits for your answer, a pause mark while paused). The row opens it where it is worked on, as the sidebar's Workflows list does, and is marked while it is on screen; a search filters these rows too. Runs another run started appear under their parent instead.

## Usage and limits

Before a step or dynamic workflow agent starts a reply, the engine checks the account: a 5-hour or weekly limit at 100%, or a refusal at a usage limit, makes it wait until the reset the account reports (re-reading the account, and again every 15 minutes while no reading tells), then go on. An account that needs sign-in, or a computer that is offline, makes it wait and say so. Without a chosen account, the step takes the least used ready account of that agent on that computer (`src/lib/account-balance.ts`), and an exhausted one gives way to another with room. With **Start on the least used account** on in Settings, the accounts it leaves out take part only when no other can, and a new Agent step starts on **Least used** rather than the account chosen last. The orchestrator's own account works the same way: at a limit it waits, or continues with another account of its agent on the driving computer that has room.

Nothing in a workflow is capped by count, size or time: steps, triggers, agents, loops, notes, history and runs may grow as the work needs, and a run goes on until it ends or you stop it.

## Where workflows live

Definitions and runs are documents in the **workflow store**, never in the workspace: a run changes every few seconds while it works and its history grows for days, and the workspace syncs as one document. The store keeps each document with a revision, an append-only history per run, and the lease of the computer driving each run (`src/lib/workflow-store.ts`):

- Paired with a relay that has the store (its revision answer says `workflows`), every device reads and writes it there (`relay/workflows.ts`: `POST v1/workflows/list`, `POST v1/workflows/read`, `PUT v1/workflows/<id>`, `POST v1/workflows/<id>/delete`, `POST v1/workflows/<id>/lease`, and the webhook route above), under the workspace's own data directory, so it is shared across computers and reachable while any one of them is off. A change bumps the store revision the relay's poll already reports, so other devices notice it without another request.
- Unpaired, or paired with a relay without the store, a desktop keeps its own store in app data `workflows/` through native file commands, and moves its documents up once it meets a relay with the store. The Viewer needs the relay's store, so a relay released before workflows shows the Viewer none, and runs stay on the computer that started them until the relay is updated.

Writes are compare-and-set on the document's revision. A conflicting write of a run merges both sides (`mergeRun`): commands, questions, notes, tasks, agents and steps by id, each by its own revision, so the driver's progress, your answers, commands and notes never overwrite each other. A definition saved over a newer revision is merged as described above. A workflow's summary names its assistant chat, and a dynamic workflow's its orchestrator's current chat (`chat`); a run's names the chats that belong to it (`conversations`), counted with its questions those its agents ask (`asking` on each agent). A page that drives a run reads the history it writes back for the view that shows it.

## Which computer drives a run

One desktop page (a desktop app or a server host, never the Viewer) drives each active run: it holds the run's lease, renewed every 15 seconds for 60, and executes it. A run has **Runs on**, the computer it prefers (the VPS's server host included), and **Continue on**, the computers that may take it over while that one is offline (every other one by default; `DriverPicker.svelte`), chosen when it starts and changeable with **Change** while it runs; a workflow's settings choose them for its triggered runs. When the driver's lease lapses (the computer slept, closed or lost its connection) and the preferred computer is offline, a computer it may continue on claims it, servers at once and desktops after 30 seconds; after two minutes without a driver any of them claims it. Triggers follow the same choice: the computer a workflow runs on watches them, and while it is offline one it may continue on (servers, when it names none). The new driver reconciles the run from what it can see (each step's and agent's chat, its reply's status), continues waits and timers, and for a dynamic workflow starts a new orchestrator session on its own computer, briefed with the goal, plan, agents, notes, questions and recent history. Agents keep running where they run; replies another computer runs go on without the computer that requested them. A driver that cannot renew its lease stops starting work until it can, so two computers never drive one run. Other computers, the VPS included, are listed only on a device paired with the relay.

## Agent tools

Every Claude and Codex chat with tools gets the workflow tools, Claude through the `agent_studio` SDK server (`mcp__agent_studio__workflow_save`, …) and Codex as dynamic tools (`src-tauri/src/providers/workflow_calls.rs`): `workflow_list`, `workflow_read`, `workflow_save` (create or replace a definition: nodes, edges, triggers; the description documents every step), `workflow_run` (at its first manual trigger or one it names), `workflow_status` and `dynamic_start`. An orchestrator chat also gets the dynamic workflow tools above. Only the conversation's own call reaches them (Claude's registered parent tool use, Codex's parent thread without a namespace).

The executing computer's own page answers them: the host sends each call to its window (`studio-workflow-call`), the page acts through the store and the engine, and `answer_workflow_call` returns the result to the CLI, as an answered question does. A reloaded page picks up calls still waiting (`pending_workflow_calls`); a reply that ends leaves its waiting calls unanswered and refuses late answers. Dynamic workflow tools answer only the current orchestrator of a run this page drives (one started here a moment ago is waited for while it is being claimed); another session hears where the workflow continues. A run request names its orchestrator role (`mission`: the run and `orchestrator`), which is part of the parked-process identity, since it changes the tools.

## Notifications

A question of a run (its own, or one its agents ask in their chats), a Notify step and a run's end alert you once on each desktop (device-local receipts) and on paired phones through the relay, with the workflow's title and one line, unless the run is on screen. The chats that belong to a run raise no alerts of their own on the desktop or through the relay (`isolated`, `runChats`), and a workflow's other chats end quietly.
